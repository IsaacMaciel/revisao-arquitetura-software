Tópico 07 · Microsserviços

Dados, Negócio & Deploy

Cada microsserviço é dono dos seus dados, organiza sua lógica com padrões de domínio e pode ser deployado independentemente. Esse conjunto de decisões — Database per Service, CQRS, Event Sourcing, testes de contrato e estratégias de deploy — é o coração do módulo e a maior fonte de questões de múltipla escolha.

🎯 Como dados e deploy de microsserviços caem na prova

Espere: (1) Database per Service — por que isolar, consequências; (2) CQRS — separação comando×query, read models, quando usar; (3) Event Sourcing — eventos como fonte da verdade, replay, relação com CQRS; (4) consistência eventual × forte — qual cada padrão oferece; (5) API Composition × CQRS para queries distribuídas; (6) testes de contrato/Pact — quem define o contrato; (7) Transaction Script × Domain Model; (8) deploy independente e estratégias blue-green/canary. SAGA é mencionada aqui mas aprofundada no Tópico 09.

Aula 1 · Lógica de negócioOrganizando a lógica de domínio num serviço

Dentro de cada microsserviço, a lógica de negócio precisa de organização. Richardson apresenta dois grandes padrões para estruturar essa lógica, que diferem em sofisticação e adequação conforme a complexidade do domínio:

Dois extremos do espectro

  • Transaction Script — lógica procedural em scripts lineares; cada operação de negócio é um procedimento que lê e atualiza o banco diretamente.
  • Domain Model — objetos ricos com estado e comportamento; baseado em DDD (entidades, agregados, value objects, domain events).

PadrõesTransaction Script × Domain Model

A escolha entre os dois depende da complexidade da lógica de negócio. A prova costuma explorar as trocas (trade-offs):

Critério Transaction Script Domain Model
Organização Procedimentos / funções lineares Objetos com estado e comportamento (OO/DDD)
Adequado para… Lógica simples, CRUD-heavy, sem regras complexas Lógica complexa, muitas regras de negócio entrelaçadas
Duplicação de lógica Alta — regras se repetem em scripts diferentes Baixa — regras encapsuladas nos objetos
Testabilidade Depende de banco/infra; difícil isolar Objetos testáveis em isolamento (unitário)
Curva de aprendizado Baixa — intuitivo Alta — exige entendimento de DDD
Manutenção a longo prazo Degrada — "big ball of mud" em sistemas grandes Escala bem em domínios complexos
⚠ Pegadinha — Transaction Script não é sempre inferior

A prova pode apresentar Transaction Script como "anti-padrão". Não é: para microsserviços com lógica simples (CRUD, poucos estados), Transaction Script é a escolha pragmática correta. O problema surge quando o domínio cresce e o padrão não escala.

DDD dentro do serviçoAgregados do DDD no microsserviço

Quando se usa Domain Model, os conceitos táticos do DDD entram em cena. O Agregado é o padrão-chave — veja Tópico 01 · DDD para aprofundamento tático. Em microsserviços, os agregados têm papel adicional:

Papel do Agregado em microsserviços

  • Unidade de consistência transacional: uma transação ACID toca apenas um agregado (banco local do serviço).
  • Fronteira natural de dados: o banco do serviço guarda os agregados daquele bounded context.
  • Publicação de Domain Events: ao mudar estado, o agregado emite eventos que outros serviços consomem para manter consistência eventual — é o elo entre Domain Model e arquitetura orientada a eventos.
  • Tamanho dos agregados importa: agregados grandes = maior risco de conflito e lock; agregados pequenos = mais eventos, mais consistência eventual a gerenciar.
💡 Domain Events → integração

Um Domain Event como PedidoConfirmado é publicado no message broker quando o agregado muda. Outros serviços (estoque, notificação) subscrevem e reagem — sem chamada síncrona, sem acoplamento direto. É o mecanismo que permite consistência eventual entre serviços.

Aulas 2–3 · DadosDatabase per Service — o padrão central

O padrão mais importante do capítulo e o mais cobrado em prova. Cada microsserviço tem seu próprio banco de dados (ou schema), e nenhum outro serviço pode acessá-lo diretamente:

✗ Anti-padrão: banco compartilhado entre serviços

Compartilhar um banco entre microsserviços parece conveniente mas destrói o isolamento: (1) acoplamento de schema — qualquer mudança na tabela quebra todos os serviços; (2) acoplamento de runtime — um serviço sobrecarregado degrada todos; (3) impossibilidade de evolução independente; (4) impossibilidade de escolher o banco mais adequado para cada serviço (polyglot persistence). É o distributed monolith mais perigoso.

Por que Database per Service

  • Encapsulamento fraco seria compartilhar: qualquer dev de outro serviço poderia fazer queries diretas, criando acoplamento implícito invisível.
  • Polyglot persistence: cada serviço escolhe o banco ideal — relacional para pedidos, documento para catálogo, grafo para recomendações.
  • Deploy independente: migrar o schema é decisão interna ao serviço; nenhum outro serviço para para isso.
  • Escalonamento independente: o banco do serviço de alto tráfego escala sozinho.
Questão 1

Por que o padrão Database per Service é considerado fundamental em arquiteturas de microsserviços?

  • APorque reduz o custo de infraestrutura ao usar menos instâncias de banco de dados.
  • BPorque garante consistência forte entre todos os serviços, eliminando transações distribuídas.
  • CPorque encapsula os dados de cada serviço, permitindo deploy independente, polyglot persistence e evolução isolada do schema.
  • DPorque permite que qualquer serviço leia os dados de outro serviço com menor latência.
O Database per Service é sobre encapsulamento e autonomia, não sobre custo ou consistência forte. (B) é o oposto do que acontece — o preço é a consistência eventual. (D) descreve exatamente o anti-padrão de banco compartilhado. (A) é irrelevante — normalmente cada serviço tem seu próprio banco, o que pode aumentar o número de instâncias.

Dados distribuídosConsistência eventual × forte

Com bancos isolados, transações ACID que abrangem múltiplos serviços são impossíveis. A resposta é aceitar consistência eventual e usar padrões compensatórios (SAGA, Event Sourcing).

Critério Consistência Forte (ACID) Consistência Eventual
Garantia Todos os leitores veem o mesmo dado imediatamente após a escrita Em algum momento no futuro todos os nós convergem para o mesmo valor
Viável em Dentro de um único serviço (banco local) Entre múltiplos serviços com bancos separados
Mecanismo Transação ACID, lock, 2PC Eventos assíncronos, SAGA, idempotência
Disponibilidade Pode bloquear (menor disponibilidade) Alta disponibilidade (sem lock global)
Complexidade Simples de programar; limitada a escopo local Maior complexidade: compensações, idempotência, reordenação de eventos
⚠ Pegadinha — consistência eventual não é "dados errados"

Consistência eventual significa que o sistema converge para um estado correto — não que fique inconsistente para sempre. O intervalo de inconsistência é transitório e gerenciado. Em prova, se uma questão diz que microsserviços "nunca têm consistência", está errada.

Padrão de dadosCQRS — Command Query Responsibility Segregation

O CQRS separa as operações de escrita (Commands) das operações de leitura (Queries) em modelos distintos. É a resposta arquitetural ao problema de queries complexas em sistemas com Database per Service.

Cliente
→ command →
Command Side
Aggregate + DB write
→ evento →
Event Bus
Kafka / RabbitMQ
→ projeta →
Read Model
DB otimizado p/ query
← query ←
Cliente
Command → muda estado do agregado e emite evento; evento alimenta o Read Model; Query lê o Read Model sem tocar no lado de escrita.

Command × Query — distinção precisa

  • Command: intenção de mudar estado (CriarPedido, CancelarPedido). Não retorna dados (ou só confirma). Vai para o Command Handler → Aggregate → persiste.
  • Query: leitura de estado; nunca muda dados. Vai para o Read Model — banco separado, desnormalizado, otimizado para exibição.
  • Read Model / Projection: visão materializada construída consumindo os eventos do Command Side. Pode ser um banco relacional, Redis, Elasticsearch — o que a query precisar.
Aspecto Prós do CQRS Contras do CQRS
Escalabilidade Leitura e escrita escalam independentemente Mais recursos de infra (dois bancos ou mais)
Queries complexas Read Model desnormalizado — queries simples e rápidas Read Model desatualizado por um instante (eventual)
Domínio Command Side fica limpo (sem query "poluindo" o domínio) Mais complexidade: dois modelos, sincronização
Testabilidade Command handlers e projeções testáveis separadamente Mais código a manter
Questão 2

No padrão CQRS, o que acontece quando um Command é processado com sucesso?

  • AO Command Handler retorna imediatamente os dados atualizados para o cliente consultar o Read Model.
  • BO agregado muda de estado, persiste no banco de escrita e publica um evento; o Read Model é atualizado de forma assíncrona a partir desse evento.
  • CO Command atualiza diretamente o Read Model para garantir consistência forte.
  • DO CQRS exige que o mesmo banco de dados seja usado para leitura e escrita, apenas com queries diferentes.
No CQRS, o Command Side (aggregate + banco de escrita) e o Query Side (Read Model) são separados e comunicam via eventos assíncronos — por isso existe consistência eventual. (A) confunde CQRS com uma chamada síncrona simples; (C) viola a separação; (D) descreve o oposto do padrão.

Padrão de dadosEvent Sourcing — eventos como fonte da verdade

No Event Sourcing, em vez de persistir o estado atual do agregado, o sistema persiste a sequência de eventos que levou a esse estado. O estado é sempre derivado do replay dos eventos.

jsonEvent Store — sequência de eventos de um Pedido
[
  { "type": "PedidoCriado",    "data": { "pedidoId": "p-123", "clienteId": "c-99" },  "seq": 1 },
  { "type": "ItemAdicionado",  "data": { "sku": "ABC-01", "qty": 2, "preco": 49.90 }, "seq": 2 },
  { "type": "ItemAdicionado",  "data": { "sku": "XYZ-07", "qty": 1, "preco": 129.0 }, "seq": 3 },
  { "type": "PedidoConfirmado","data": { "total": 228.80, "ts": "2024-03-01T10:00Z" }, "seq": 4 }
]
// Estado atual = aplicar os 4 eventos em sequência sobre um agregado vazio.
// Replay = reprocessar a partir do seq 1 para reconstruir qualquer ponto no tempo.

Conceitos-chave do Event Sourcing

  • Event Store: o banco onde os eventos são gravados de forma append-only (nunca se edita nem deleta um evento passado).
  • Replay: reprocessar todos os eventos de um agregado para reconstruir seu estado atual. Permite também "voltar no tempo" para depurar.
  • Snapshot: otimização — salvar o estado em um ponto para evitar replay completo do histórico a cada leitura.
  • Projection: consome eventos do Event Store para construir Read Models (aqui o CQRS e o Event Sourcing se unem naturalmente).
  • Auditoria nativa: o histórico completo de mudanças está no Event Store por construção — sem triggers ou audit tables extras.
⚠ Pegadinha — CQRS e Event Sourcing não são a mesma coisa

São padrões complementares, não sinônimos. Você pode ter CQRS sem Event Sourcing (usando um banco relacional no Command Side e projetando para um Read Model via eventos de integração). E pode ter Event Sourcing sem CQRS (embora seja incomum). Na prática, combinam bem: o Event Store alimenta naturalmente as projeções do Read Model.

Questão 3

Qual é a principal diferença entre persistência tradicional e Event Sourcing?

  • ANa persistência tradicional, salva-se o estado atual; no Event Sourcing, salva-se a sequência de eventos que levou ao estado, permitindo replay.
  • BEvent Sourcing é apenas uma forma de implementar CQRS — sem CQRS não é possível usar Event Sourcing.
  • CEvent Sourcing garante consistência forte entre todos os serviços, eliminando a consistência eventual.
  • DEvent Sourcing elimina a necessidade de um banco de dados, pois os eventos ficam em memória.
A distinção fundamental é estado versus eventos: Event Sourcing é append-only de eventos; o estado é sempre derivado via replay. (B) confunde os dois padrões — são independentes. (C) é falso — Event Sourcing com múltiplos serviços ainda implica consistência eventual nas projeções. (D) é absurdo — o Event Store é um banco persistente.

Queries distribuídasAPI Composition × CQRS para queries

Com banco por serviço, como responder a uma query que precisa de dados de vários serviços? Duas soluções principais:

Critério API Composition CQRS com Read Model
Como funciona Um API Composer consulta múltiplos serviços e une os resultados na memória (join em código) Um Read Model pré-agrega dados de múltiplos serviços via eventos; query vai a um único lugar
Consistência Depende do momento — dados dos serviços podem divergir entre chamadas Eventual — o Read Model é atualizado via eventos assíncronos
Complexidade Simples de implementar; ruim para grandes volumes Mais complexo; escala bem para queries pesadas
Adequado para Queries simples, poucos serviços, dados pequenos Queries complexas, grandes volumes, alta frequência de leitura
Problema típico Joins em memória ineficientes; dependência de disponibilidade simultânea dos serviços Read Model desatualizado (lag); mais infra
Questão 4

Uma plataforma de e-commerce precisa exibir uma tela de "Meu Perfil" com dados de três microsserviços: Pedidos, Avaliações e Endereços. A consulta é complexa e executada milhares de vezes por minuto. Qual abordagem é mais adequada?

  • AAPI Composition: o front-end chama os três serviços em paralelo e monta a tela no cliente.
  • BCriar um banco compartilhado entre os três serviços para simplificar a query.
  • CAPI Composition com um Aggregator no backend que faz o join em memória.
  • DCQRS com Read Model pré-materializado: eventos dos três serviços alimentam um Read Model dedicado para esta visão.
Para alta frequência e query complexa, o CQRS com Read Model é a solução escalável: os dados são pré-agregados e a leitura é barata. (A) e (C) são API Composition — adequada para casos simples, mas sofre com volume. (B) é o anti-padrão de banco compartilhado.
💡 E o SAGA?

O SAGA resolve o problema das escritas que abrangem múltiplos serviços (transações distribuídas) — enquanto API Composition e CQRS resolvem as leituras. SAGA é aprofundado no Tópico 09.

Aula 4 · TestesPirâmide de testes em microsserviços

A pirâmide de testes em sistemas distribuídos tem uma camada extra de complexidade: testar a integração entre serviços sem precisar subir todo o sistema. A estratégia clássica — e a que a prova adota — segue quatro níveis:

Nível O que testa Velocidade / Custo Dependências externas
Unitário Classe / função isolada (lógica de domínio, use cases) Muito rápido / muito barato Mocks/stubs — nenhuma real
Integração Serviço + seu banco/cache/fila (infra própria) Médio / médio Banco real do serviço (Testcontainers)
Contrato (Consumer-Driven) API entre dois serviços — sem subir o serviço provedor real Rápido / baixo Mock do provedor gerado pelo contrato
End-to-End (E2E) Fluxo completo do sistema real Lento / caro Todo o sistema rodando
⚠ Pegadinha — testes E2E não escalam em microsserviços

Em sistemas distribuídos, testes E2E são frágeis e lentos: qualquer serviço instável derruba o resultado. A estratégia recomendada é maximizar unitários e de contrato, minimizar E2E. Testes de contrato (Pact) são a grande inovação para substituir a integração via serviço real.

Testes de contratoConsumer-Driven Contract Testing (Pact)

O desafio clássico: como o serviço A sabe que o serviço B não vai quebrar sua API? A resposta é o Teste de Contrato Orientado ao Consumidor (consumer-driven contract test), popularizado pela ferramenta Pact.

Como funciona o Pact

  • Consumer (quem chama): escreve testes que definem o que espera receber do Provider. O Pact gera um arquivo de contrato (JSON/YAML) a partir desses testes.
  • Provider (quem é chamado): valida que sua implementação satisfaz o contrato gerado pelo Consumer — sem precisar que o Consumer esteja rodando.
  • Pact Broker: repositório central onde os contratos são publicados e compartilhados entre equipes.
  • O "driver" do contrato é o Consumer — não o Provider. Essa é a distinção-chave que cai em prova.
Consumer
escreve contrato
→ publica →
Pact Broker
repositório de contratos
→ verifica →
Provider
valida a implementação
O Consumer define o que precisa; o Provider prova que entrega. Cada lado testa independentemente — sem ambiente compartilhado.
💡 Relação com F.I.R.S.T. (Clean Architecture)

Testes de contrato são Fast, Independent, Repeatable — cumprem os critérios F.I.R.S.T. de bons testes que o Clean Architecture define (ver Tópico 02 · Clean Architecture). São rápidos porque não dependem do serviço real em execução; são independentes porque cada lado valida separadamente.

Questão 5

Em testes de contrato com Pact (consumer-driven), quem define o contrato e o que ele especifica?

  • AO Provider define o contrato — especifica tudo que sua API expõe; o Consumer valida que está usando corretamente.
  • BO time de QA define o contrato manualmente em um documento compartilhado.
  • CO Consumer define o contrato — especifica o que espera receber do Provider; o Provider valida que sua implementação cumpre esse contrato.
  • DO contrato é gerado automaticamente por análise estática do código do Provider sem intervenção do Consumer.
"Consumer-Driven" significa que o Consumer escreve os testes que definem suas expectativas sobre o Provider — é o consumidor que guia o contrato. (A) inverte a direção: no Pact, o Provider valida contra o contrato do Consumer, não o contrário. (B) descreve um processo manual que não é o Pact. (D) é falso — não existe geração automática por análise estática.

Aulas 5–6 · DeployPadrões de deploy de microsserviços

O deploy independente é um dos principais benefícios de microsserviços. Para realizá-lo, existem padrões de empacotamento e execução:

Padrão Descrição Vantagem Desvantagem
Serviço por Container Cada serviço = uma imagem Docker; orquestrado por K8s/ECS Isolamento, portabilidade, densidade (muitos containers por host) Overhead de orquestração; curva de aprendizado do K8s
Serviço por VM Cada serviço roda em sua própria VM dedicada Isolamento completo; sem conflito de runtime Uso ineficiente de recursos; lento para subir
Serviço por Host (bare metal/process) Cada serviço = um processo no host, sem containerização Simples de operar Sem isolamento; conflitos de porta e dependência
Serverless (FaaS) Cada operação = função invocada sob demanda (AWS Lambda, GCP Functions) Zero provisionamento; paga por execução; escala automático Cold start; limitações de execução longa; vendor lock-in
💡 Container como padrão dominante

Na prática, serviço por container com K8s tornou-se o padrão de fato para microsserviços em produção. Ver Tópico 04 · Docker para o modelo de container e Tópico 05 · CI/CD para o pipeline que faz o deploy acontecer automaticamente.

Questão 6

Qual é o principal benefício do padrão "Serviço por Container" em relação ao "Serviço por VM" para deploy de microsserviços?

  • AContainers garantem isolamento completo de kernel, equivalente ao de VMs, com zero overhead.
  • BContainers permitem maior densidade (múltiplos serviços por host), startup mais rápido e imagens portáteis, com menos desperdício de recurso que VMs.
  • CContainers eliminam a necessidade de orquestração — cada container se auto-gerencia.
  • DServiço por VM é sempre preferível porque oferece maior segurança e sem cold start.
O ponto forte do container é densidade e velocidade de startup — muitos containers por host com baixo overhead. (A) está errado: containers não têm isolamento de kernel total como VMs (compartilham o kernel do host). (C) é falso — containers precisam de orquestração (K8s, ECS). (D) inverte — VMs são mais pesadas e lentas para escalar.

Deploy · infraestruturaService Discovery & Configuração Externa

Com serviços deployados dinamicamente (IPs que mudam, múltiplas instâncias), dois problemas emergem: como um serviço encontra outro (discovery) e como configura-se sem hardcode de valores de ambiente:

Service Discovery — dois modelos

  • Client-side discovery: o cliente consulta o Service Registry (ex.: Eureka/Consul), obtém os IPs disponíveis e faz load balancing localmente. Mais controle, mas o cliente acumula lógica.
  • Server-side discovery: o cliente envia a requisição para um Load Balancer/API Gateway, que consulta o Registry e roteia. O cliente fica simples; a lógica de roteamento fica no servidor.

Configuração externa

  • Princípio: configuração (URLs, credenciais, feature flags) nunca deve ser hardcoded — deve ser injetada via variáveis de ambiente, arquivos externos ou serviços de configuração (Spring Cloud Config, AWS SSM Parameter Store, Vault).
  • Benefício para deploy independente: o mesmo artefato (imagem Docker) pode ser deployado em dev/staging/prod com configurações distintas sem rebuild.

Deploy · estratégiasBlue-Green & Canary Release

Deploy independente só é seguro com estratégias que minimizam risco. As duas mais cobradas em prova:

Estratégia Como funciona Rollback Risco
Blue-Green Dois ambientes idênticos (Blue=atual, Green=novo). Deploy vai para Green; tráfego é redirecionado instantaneamente ao Green via load balancer Imediato — basta redirecionar para Blue Custo de manter dois ambientes; troca brusca (100% de uma vez)
Canary Release Nova versão recebe uma fatia pequena do tráfego (ex.: 5%); se saudável, a fatia cresce gradualmente até 100% Remover a fatia canary — apenas pequena % afetada Menor impacto se falhar; mais complexo para gerenciar
⚠ Pegadinha — Blue-Green não é Canary

Blue-Green faz a troca de uma vez (tudo ou nada); Canary faz a troca gradual (percentual crescente). Em prova, a opção que diz "5% do tráfego vai para a nova versão primeiro" descreve Canary, não Blue-Green. Veja mais em Tópico 05 · CI/CD & DevOps.

Mnemônico — Database per Service e suas consequências
"Isolei o banco, Perdi o JOIN, Ganhei a autonomia"
  • Isolamento — cada serviço tem seu banco
  • Perda do join — joins distribuídos precisam de API Composition ou CQRS
  • Ganho — polyglot persistence, deploy independente, escala isolada

clique

clique
Transaction Script: lógica simples, CRUD — pragmático e direto. Domain Model: lógica complexa, muitas regras de negócio — escala melhor, mais testável, mas exige DDD.

O que é consistência eventual no contexto de microsserviços?
clique
O estado entre serviços converge para o mesmo valor em algum momento futuro via eventos assíncronos — mas há uma janela transitória de inconsistência. Não é dado errado permanentemente.
O que é um Agregado e qual seu papel em microsserviços?
clique
Cluster de objetos com consistência transacional. Em microsserviços: fronteira de consistência local (uma transação = um agregado) e publicador de Domain Events para integração eventual com outros serviços.
O que é polyglot persistence?
clique
Cada serviço escolhe o tipo de banco mais adequado à sua carga — relacional, documentos, grafos, chave-valor. Possível porque cada serviço tem seu próprio banco isolado (Database per Service).

Referência rápidaGlossário

Database per Service
Padrão onde cada microsserviço possui seu banco exclusivo — nenhum serviço acessa o banco de outro diretamente.
Polyglot Persistence
Uso de diferentes tipos de banco de dados para diferentes serviços conforme a necessidade de cada um.
CQRS
Command Query Responsibility Segregation: separação entre operações de escrita (Command Side) e leitura (Query Side / Read Model).
Command
Intenção de mudar estado de um agregado. Processado pelo Command Handler; não retorna dados de leitura.
Read Model / Projection
Visão materializada construída consumindo eventos do Command Side; otimizada para queries de leitura.
Event Sourcing
Padrão onde o estado é derivado do replay de uma sequência de eventos armazenados no Event Store (append-only).
Event Store
Banco append-only que persiste a sequência de eventos de domínio; nunca edita ou deleta eventos passados.
Replay
Reprocessar eventos sequencialmente para reconstruir o estado atual (ou histórico) de um agregado.
API Composition
Padrão de query distribuída: um Composer chama múltiplos serviços e une os resultados em memória.
Consistência Eventual
Garantia de que todos os nós/serviços convergem para o mesmo estado em algum momento — mas não imediatamente após a escrita.
Consumer-Driven Contract Test
Teste onde o Consumer define o contrato de API esperado; o Provider valida sua implementação contra esse contrato (ex.: Pact).
Transaction Script
Padrão de organização de lógica de negócio como procedimentos lineares que leem e atualizam o banco — adequado para domínios simples.
Blue-Green Deploy
Dois ambientes idênticos; o tráfego é redirecionado instantaneamente de Blue (atual) para Green (novo) via load balancer.
Canary Release
Nova versão recebe um percentual pequeno do tráfego que cresce gradualmente — limita o impacto de falhas na nova versão.

Véspera da provaPegadinhas & checklist final

🎯 Releia antes de entregar a prova
  • Database per Service = cada serviço tem seu banco exclusivo; acesso direto por outro serviço é anti-padrão (banco compartilhado).
  • Polyglot persistence só é possível porque cada serviço isola seu banco.
  • CQRS ≠ Event Sourcing — são complementares, não sinônimos. CQRS separa leitura×escrita; ES persiste eventos em vez do estado.
  • No CQRS, o Command Side muda estado; o Query Side (Read Model) apenas lê — nunca o contrário.
  • Read Model é atualizado por eventos de forma assíncrona — há inconsistência eventual entre o Command Side e o Query Side.
  • Event Sourcing: o Event Store é append-only; o estado é derivado por replay; snapshot é otimização, não obrigação.
  • API Composition = join em memória (simples, não escala). CQRS com Read Model = dados pré-agregados (complexo, escala).
  • Consistência eventual ≠ dados errados permanentemente — é uma janela transitória de convergência.
  • No Pact, o Consumer define o contrato; o Provider valida. "Consumer-driven" = guiado pelo consumidor.
  • Transaction Script não é anti-padrão — é adequado para domínios simples. O problema surge quando o domínio cresce.
  • Blue-Green = troca instantânea (tudo ou nada); Canary = troca gradual por percentual de tráfego.
  • SAGA resolve escritas distribuídas (transações) — não queries. Aprofundado no Tópico 09.
  • Testes E2E são frágeis em sistemas distribuídos — prefira testes de contrato para integração entre serviços.
