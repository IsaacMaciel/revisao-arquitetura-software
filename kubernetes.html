Kubernetes

Kubernetes (K8s) é o orquestrador de containers de fato do mercado — nascido do Borg do Google e doado à CNCF. Sua ideia-mestra é o modelo declarativo: você descreve o estado desejado e o cluster, por meio de control loops, converge o estado atual para ele — escalando, curando e atualizando suas aplicações sozinho. Esta revisão cobre da arquitetura do cluster ao AWS EKS na prática, segurança e CI/CD.

🎯 Como Kubernetes cai na prova

Espere: (1) papéis dos componentes — quem é Control Plane × Node, o que faz etcd/scheduler/kubelet (invertem isso de propósito); (2) distinções pareadas — Label × Annotation, ConfigMap × Secret, liveness × readiness, Deployment × StatefulSet × DaemonSet, HPA × VPA × Cluster Autoscaler, Role × ClusterRole; (3) tipos de Service e quando cada um expõe (ClusterIP × NodePort × LoadBalancer); (4) armazenamento — emptyDir × PV, binding PVC/PV; (5) EKS — o que a AWS gerencia × o que é seu, IRSA, Fargate; (6) segurança — RBAC autoriza × IAM autentica, NetworkPolicy (default libera tudo), Secret é base64 ≠ criptografia.

Parte I — Aulas 1 e 2Fundamentos e Arquitetura do Kubernetes

Kubernetes (K8s) é uma plataforma open-source de orquestração de containers que automatiza implantação, escalonamento e operação de aplicações conteinerizadas. Nasceu da experiência interna do Google com o sistema Borg (que gerencia bilhões de containers por semana) e foi doado à CNCF (Cloud Native Computing Foundation) em 2016. A proposta central é simples: você declara o que quer e o cluster converge para isso — indefinidamente.

O que o Kubernetes resolve

  • Escala horizontal — sobe e desce réplicas automaticamente (HPA/VPA)
  • Self-healing — reinicia containers com falha, substitui Pods não saudáveis
  • Rollout / Rollback — atualização gradual sem downtime; desfaz com um comando
  • Service Discovery & Load Balancing — DNS interno e roteamento de tráfego automático
  • Gestão de configuração e segredos — ConfigMap e Secret desacoplados da imagem
  • Bin packing — aloca Pods nos nós otimizando CPU/memória declarados

Conceito CentralEstado Desejado × Estado Atual

O modelo de Kubernetes é declarativo: você escreve um manifesto descrevendo o estado desejado e o cluster executa um reconciliation loop (control loop) contínuo para convergir o estado atual ao estado desejado. Isso contrasta com o modelo imperativo, onde cada ação deve ser comandada explicitamente.

ArquiteturaControl Plane × Worker Nodes

Um cluster Kubernetes é dividido em dois planos: o Control Plane (cérebro) e os Worker Nodes (músculos). O Control Plane toma decisões globais; os nós executam as cargas de trabalho.

Componente Onde roda Responsabilidade Detalhe crítico
kube-apiserver Control Plane Front-end da API REST; única porta de entrada para todo estado do cluster Valida e persiste objetos no etcd; é stateless — pode escalar horizontalmente
etcd Control Plane Banco de dados chave-valor distribuído; armazena TODO o estado do cluster Consenso via Raft; precisa de quorum (maioria ímpares: 3, 5…); backup crítico
kube-scheduler Control Plane Decide em qual nó um Pod não agendado será colocado Avalia resources, affinity, taints/tolerations — NÃO executa o Pod
kube-controller-manager Control Plane Roda os controllers (ReplicaSet, Deployment, Node, Job…) em um único processo Cada controller monitora um tipo de objeto e age para convergir ao estado desejado
cloud-controller-manager Control Plane Integra com APIs do provedor de nuvem (LoadBalancer, volumes, rotas) Presente em clusters executados em provedores de nuvem (gerenciados ou self-managed)
kubelet Worker Node Agente no nó; recebe PodSpec e garante que os containers estejam rodando Faz health checks (liveness/readiness); reporta status ao apiserver
kube-proxy Worker Node Mantém regras de rede (iptables/ipvs) para rotear tráfego dos Services Implementa o IP virtual do Service; NÃO é o único responsável por DNS
Container Runtime (CRI) Worker Node Executa os containers de fato (containerd, CRI-O) Docker foi removido como runtime padrão no K8s 1.24 (dockershim deprecated)
⚠ Pegadinha — etcd × scheduler × kubelet
  • etcd é o banco de dados do cluster — NÃO é o scheduler, NÃO toma decisões de agendamento.
  • kube-scheduler decide onde o Pod roda, mas quem realmente inicia o container é o kubelet.
  • kubelet roda em cada Worker Node — NÃO faz parte do Control Plane. Questões de prova frequentemente invertem isso.
  • O kube-controller-manager não é um controller único — é um binário que hospeda múltiplos controllers (Node Controller, ReplicaSet Controller, etc.).
Nuvem EKS / GKE / AKS — cloud-controller-manager + infraestrutura gerenciada
Control Plane kube-apiserver · etcd · kube-scheduler · kube-controller-manager
Worker Nodes kubelet · kube-proxy · Container Runtime (containerd)
Workloads Pods → Containers → sua aplicação

API e ManifestsObjetos da API e YAML

Todo recurso do Kubernetes é um objeto da API descrito em YAML (ou JSON). Os quatro campos raiz são obrigatórios e identificam o objeto de forma única.

Campos raiz de todo manifesto

  • apiVersion — grupo/versão da API (v1, apps/v1, batch/v1…)
  • kind — tipo do objeto (Pod, Deployment, Service…)
  • metadata — nome, namespace, labels, annotations
  • spec — estado desejado declarado pelo usuário

Exemplo mínimo de manifest para um Pod:

apiVersion: v1
kind: Pod
metadata:
  name: meu-pod
  namespace: default
  labels:
    app: demo
spec:
  containers:
    - name: app
      image: nginx:1.25
      ports:
        - containerPort: 80

Comandos kubectl essenciais:

# Declarativo — aplica/atualiza a partir do manifesto
kubectl apply -f pod.yaml

# Imperativo — cria sem arquivo (não rastreável em GitOps)
kubectl run meu-pod --image=nginx:1.25

# Inspecionar
kubectl get pods -n default
kubectl describe pod meu-pod
kubectl logs meu-pod
kubectl exec -it meu-pod -- /bin/sh

# Deletar
kubectl delete -f pod.yaml
kubectl delete pod meu-pod

⚠ Pegadinha — apply × create

kubectl create -f falha se o recurso já existe. kubectl apply -f cria OU atualiza (patch three-way merge). Em prova, "qual comando é idempotente e adequado para pipelines CI/CD?" — a resposta é sempre apply.

Isolamento LógicoNamespaces

Namespaces dividem um cluster em espaços virtuais isolados. Recursos como Pods, Services e Deployments vivem dentro de um namespace; recursos como Nodes e PersistentVolumes são globais (cluster-scoped).

Namespaces padrão

  • default — namespace padrão quando nenhum é especificado
  • kube-system — componentes internos do K8s (kube-dns, kube-proxy…)
  • kube-public — leitura pública sem autenticação (raramente usado)
  • kube-node-lease — heartbeats de nós para detecção de falha
# Listar namespaces
kubectl get namespaces

# Criar namespace
kubectl create namespace homologacao

# Operar em namespace específico
kubectl get pods -n homologacao

# Definir namespace padrão no contexto atual
kubectl config set-context --current --namespace=homologacao

RevisãoQuestões de Prova

Questão 1

Qual componente do Control Plane é responsável por decidir em qual nó um Pod recém-criado será executado, levando em conta recursos disponíveis, taints e affinity rules?

  • Akube-controller-manager, pois gerencia o ciclo de vida dos objetos do cluster.
  • Bkube-scheduler, pois avalia os nós elegíveis e vincula o Pod ao nó selecionado.
  • Ckubelet, pois é o agente que efetivamente inicia os containers nos nós.
  • Detcd, pois armazena o estado desejado incluindo a alocação de Pods.
B é correto. O kube-scheduler observa Pods sem nó atribuído (nodeName vazio) e escolhe o nó via algoritmos de filtragem e pontuação. — A errada: o kube-controller-manager reconcilia estado de objetos (ex.: garante N réplicas), mas não faz scheduling. — C errada: o kubelet executa o container após o scheduler já ter decidido o nó — ele não escolhe. — D errada: o etcd é apenas o banco de dados; não toma nenhuma decisão.
Questão 2

Um engenheiro executa kubectl create -f deployment.yaml com sucesso. Ao executar o mesmo comando novamente, sem alterar o arquivo, o resultado é:

  • AO Deployment é atualizado silenciosamente com as novas configurações do arquivo.
  • BUma segunda instância do Deployment é criada com nome gerado automaticamente.
  • CO comando falha com erro "AlreadyExists", pois create não é idempotente.
  • DO comando é idempotente e retorna sucesso sem nenhuma alteração no cluster.
C é correto. kubectl create é imperativo e não idempotente — falha com Error from server (AlreadyExists) se o recurso já existe. Para comportamento idempotente use kubectl apply. — A errada: isso descreveria o comportamento de kubectl apply. — B errada: K8s não gera nomes automáticos a partir de create -f com name já definido. — D errada: create nunca é idempotente; a opção idempotente por design é apply.
Questão 3

Qual afirmação sobre o etcd no contexto de um cluster Kubernetes é CORRETA?

  • AÉ um banco de dados chave-valor distribuído que armazena todo o estado do cluster; apenas o kube-apiserver se comunica diretamente com ele.
  • BÉ o componente que agenda Pods nos nós disponíveis com base em políticas de recursos.
  • CRoda em cada Worker Node para garantir que os containers definidos nos PodSpecs estejam em execução.
  • DPode ser substituído pelo kube-controller-manager em clusters de desenvolvimento para reduzir overhead.
A é correto. O etcd é o único armazenamento persistente do cluster; todos os outros componentes lêem e escrevem estado somente através do kube-apiserver. — B errada: isso descreve o kube-scheduler. — C errada: isso descreve o kubelet, que roda no Worker Node. — D errada: o etcd e o kube-controller-manager têm responsabilidades completamente distintas; um não substitui o outro.
TL;DR
  • K8s = orquestrador declarativo — você define o estado desejado; o control loop converge o cluster.
  • Control Plane: apiserver (porta de entrada) · etcd (banco do cluster) · scheduler (decide onde) · controller-manager (reconcilia estado) · cloud-controller-manager (nuvem).
  • Worker Node: kubelet (executa Pods) · kube-proxy (regras de rede) · container runtime (containerd).
  • etcd ≠ scheduler ≠ kubelet — confundi-los é a armadilha favorita da prova.
  • apply = idempotente (declarativo, GitOps); create/run = imperativo (falha se já existe).
  • Docker cria imagens e containers individuais; K8s orquestra containers em múltiplos hosts.
  • Local: Minikube (desenvolvimento), kind (CI), k3s/k3d (edge); Gerenciado: EKS, GKE, AKS.

Aulas 3 e 4 — Parte IPods, Rótulos, Services e ConfigMap/Secret

Esta seção cobre as unidades fundamentais de execução do Kubernetes e os mecanismos de descoberta de serviços e injeção de configuração. São tópicos de altíssima incidência em provas de múltipla escolha porque envolvem distinções sutis que confundem até profissionais experientes.

Unidade MínimaPods

Um Pod é a menor unidade deployável do Kubernetes. Ele encapsula um ou mais containers que compartilham o mesmo network namespace (mesmo IP e porta) e podem montar os mesmos volumes. Containers dentro de um Pod se comunicam via localhost. O Pod é efêmero — quando morre, não retorna; quem o recria é um controlador (Deployment, StatefulSet etc.).

Anatomia de um Pod

  • Pause container (infraestrutura): container "fantoche" criado pelo kubelet antes de todos os outros; mantém o network namespace vivo enquanto os containers de aplicação sobem/reiniciam. Invisível ao usuário mas essencial.
  • Init containers: rodam sequencialmente e até o fim antes de qualquer container principal. Usados para pré-condições (seed de banco, wait-for-service). Se falhar, o Pod reinicia.
  • Sidecar containers: rodam paralelamente ao container principal. Padrão para logging, proxy (Istio Envoy), sync de segredos.
  • Containers principais: a carga de trabalho em si.
Pod (namespace de rede compartilhado)
Init containers (sequenciais, terminam antes)
Pause container (mantém o netns)
App container + Sidecar containers (paralelos)

⚠ Pegadinha — Pod vs Container

A prova costuma perguntar "qual é a menor unidade deployável". A resposta é Pod, não container. Você não deploya containers diretamente no Kubernetes; você deploya Pods que contêm containers.

⚠ Pegadinha — Init × Sidecar

Init containers terminam antes dos containers principais iniciarem. Sidecars rodam em paralelo. Uma questão que diz "roda em paralelo com o container principal para fornecer proxy" descreve um sidecar, não um init container.

MetadadosLabels (Rótulos) × Annotations (Anotações)

Labels são pares chave/valor usados para identificar e agrupar recursos; eles são a base dos selectors que conectam Services a Pods, Deployments a ReplicaSets etc. Annotations também são pares chave/valor, mas carregam metadados descritivos/operacionais e não podem ser usadas em selectors.

Critério Label selector Annotation não selecionável
Finalidade Identificar, agrupar, selecionar recursos Metadados descritivos / operacionais
Pode ser usada em selector? Sim Não
Restrição de tamanho de valor 63 caracteres (sem espaços) Sem limite prático (URLs, JSON, textos longos)
Exemplos típicos app=frontend, env=prod, version=v3 URL de build, hash de commit, contato do time, checksums
Quem as usa internamente kube-scheduler, Services, Deployments, HPA Ferramentas externas (Helm, Argo CD, Prometheus)
✗ Anti-padrão — Usar annotation como selector

Nunca use annotations em selector. O campo selector de um Service aceita somente labels. Tentar filtrar por annotation não produz erro, mas simplesmente não funciona — o Service não encontrará nenhum Pod.

Tipos de Selector

Tipo Sintaxe (kubectl) Equivalente YAML
Equality-based -l app=demo,env=prod matchLabels: {app: demo, env: prod}
Set-based — in -l 'env in (prod,staging)' matchExpressions: [{key: env, operator: In, values: [prod,staging]}]
Set-based — notin -l 'env notin (dev)' operator: NotIn
Set-based — exists -l 'tier' (chave existe) operator: Exists, values: []
✓ Dica de prova — matchLabels vs matchExpressions

matchLabels só aceita equality-based. Para usar In, NotIn ou Exists, você precisa de matchExpressions. Services mais antigos (v1) usam apenas o campo selector equality-based.

⚠ Pegadinha — ClusterIP não é acessível de fora

ClusterIP é estritamente interno. Nenhum tráfego externo alcança um ClusterIP diretamente. Para expor externamente você precisa de NodePort, LoadBalancer ou Ingress. Uma questão que diz "o Service está configurado como ClusterIP mas o cliente externo não consegue acessar" — a resposta é que o tipo de Service está errado, não que há bug no Pod.

🎯 Prova — Headless Service

O Headless Service (clusterIP: None) não tem IP virtual. O CoreDNS retorna diretamente os IPs dos Pods que correspondem ao selector. Isso permite que clientes descubram e se conectem individualmente a cada Pod — padrão obrigatório para StatefulSets onde cada réplica tem identidade própria.

# Service ClusterIP (padrão) — conecta via label selector
apiVersion: v1
kind: Service
metadata:
  name: backend-svc
spec:
  selector:
    app: backend      # seleciona Pods com este label
    env: prod
  ports:
  - port: 80          # porta do Service
    targetPort: 8080  # porta do container
  type: ClusterIP     # poderia omitir — é o default
---
# NodePort — expõe externamente
apiVersion: v1
kind: Service
metadata:
  name: frontend-svc
spec:
  selector:
    app: frontend
  ports:

    targetPort: 3000
    nodePort: 31000   # fixo (opcional); range 30000-32767
  type: NodePort

Configuração ExternalizadaConfigMap × Secret

Ambos desacoplam a configuração do código da imagem de container. A diferença fundamental é a natureza dos dados: ConfigMap para configuração não-sensível; Secret para dados sensíveis. Ambos podem ser injetados como variáveis de ambiente ou montados como volumes.

Critério ConfigMap Secret
Dados típicos URLs, flags, arquivos de config, parâmetros Senhas, tokens, chaves TLS, credenciais
Encoding no etcd Texto plano Base64 (não criptografado por padrão!)
Criptografia em repouso Não (por padrão) Não (por padrão) — requer EncryptionConfiguration
Limite de tamanho 1 MiB 1 MiB
Tipo kubectl create configmap secret generic / tls / docker-registry
Referência em Pod configMapKeyRef / configMapRef secretKeyRef / secretRef
⚠ Pegadinha clássica — Base64 ≠ Criptografia

Secret NÃO é criptografado por padrão. Os valores são apenas codificados em base64, o que é reversível trivialmente (echo "dmFsb3I=" | base64 -d). Qualquer pessoa com acesso ao etcd ou permissão de kubectl get secret pode ler o valor. Para criptografia real, configure Encryption at Rest (EncryptionConfiguration) e/ou use soluções externas como Vault. A prova adora essa pegadinha.

✗ Anti-padrão — Guardar segredo em ConfigMap

Colocar senhas, tokens ou chaves em ConfigMap (em texto plano) é um anti-padrão de segurança. Use Secret mesmo que ele não seja "verdadeiramente" seguro por padrão — é o objeto semântico correto e possibilita aplicar políticas RBAC e EncryptionConfiguration por tipo de recurso.

✓ Volume vs Env Var — quando usar cada um
  • Env var: valores simples (string). Atenção: não reflete atualizações do ConfigMap/Secret em tempo real após o Pod iniciar.
  • Volume: arquivos de configuração completos. Reflete atualizações do ConfigMap/Secret automaticamente (com pequeno delay do kubelet), sem reiniciar o Pod.

Questão 1

Um desenvolvedor criou um Service do tipo ClusterIP para expor sua API ao time de QA, que acessa o cluster externamente. O QA reporta que não consegue acessar a API pelo IP do Service. Qual é a causa raiz?

  • AO selector do Service não corresponde aos labels dos Pods — os Endpoints estão vazios.
  • BClusterIP é acessível apenas dentro do cluster; acesso externo requer NodePort, LoadBalancer ou Ingress.
  • CO Service precisa de clusterIP: None para aceitar tráfego externo.
  • DO CoreDNS não resolve nomes de Services do tipo ClusterIP externamente.
B está correta: ClusterIP é um IP virtual roteável somente dentro da rede do cluster (via kube-proxy). Nenhum pacote externo chega a ele diretamente.

A (errada): Selector errado causaria Endpoints vazios e erro 503, não um problema de alcançabilidade de rede — o QA nem conseguiria fazer a conexão TCP.
C (errada): clusterIP: None cria um Headless Service (sem IP virtual), o que torna o acesso externo ainda mais difícil, não possível.
D (errada): O CoreDNS resolve nomes de Services, mas o problema é roteamento de rede, não resolução DNS. Além disso, o QA está fora do cluster, então o DNS do cluster nem seria consultado.
Questão 2

Sobre Secrets no Kubernetes, qual afirmação está correta?

  • ASecrets são criptografados por padrão no etcd usando AES-256.
  • BSecrets e ConfigMaps são equivalentes em segurança; a diferença é apenas semântica.
  • CPor padrão, os valores de um Secret são apenas codificados em base64, sem criptografia; criptografia em repouso requer configuração adicional (EncryptionConfiguration).
  • DUm Secret montado como variável de ambiente atualiza automaticamente o processo em execução quando o valor é alterado no cluster.
C está correta: Base64 é encoding reversível, não criptografia. Para habilitar criptografia em repouso é necessário configurar o EncryptionConfiguration no API Server.

A (errada): Kubernetes não criptografa Secrets por padrão. A criptografia requer configuração explícita.
B (errada): Não são equivalentes: Secrets permitem políticas RBAC granulares por tipo de recurso e podem receber EncryptionConfiguration distinta. ConfigMaps nunca deveriam armazenar dados sensíveis.
D (errada): Variáveis de ambiente são fixadas no momento da inicialização do container — não refletem alterações posteriores no Secret. Apenas Secrets montados como volumes são atualizados automaticamente pelo kubelet.
Questão 3

Qual a diferença funcional entre labels e annotations em recursos Kubernetes?

  • ALabels são usados em selectors para agrupar e selecionar recursos; annotations carregam metadados descritivos e não podem ser usadas em selectors.
  • BLabels suportam valores longos (URLs, JSON); annotations são limitadas a 63 caracteres.
  • CAnnotations são indexadas pelo etcd para consultas rápidas; labels não são indexados.
  • DLabels e annotations têm a mesma função; a distinção é apenas uma convenção de nomenclatura da comunidade.
A está correta: Esta é a distinção fundamental. Labels habilitam seleção e agrupamento (Services, Deployments, HPA todos dependem de labels). Annotations não são selecionáveis.

B (errada): É o contrário — labels têm limite de 63 caracteres no valor; annotations não têm limite prático e são usadas justamente para valores longos.
C (errada): É o inverso do que ocorre: labels são indexados pelo kube-apiserver (watch cache), o que permite buscas eficientes via selector. Annotations não são indexadas — não há indexação invertida por valor de annotation. Além disso, etcd armazena objetos como blobs serializados; a indexação por labels é feita na camada do kube-apiserver, não pelo etcd.
D (errada): A distinção é funcional e técnica, não apenas convencional. O API Server e os controladores internos usam labels; ferramentas externas como Helm e Argo CD usam annotations.
TL;DR
  • Pod = menor unidade deployável; containers compartilham IP (localhost) e volumes. Init containers terminam antes; sidecars rodam em paralelo.
  • Labels = identificadores selecionáveis (selectors). Annotations = metadados descritivos, não selecionáveis.
  • Service ClusterIP = interno apenas. NodePort = externo via porta 30000–32767. LoadBalancer = cloud. ExternalName = CNAME externo. Headless (clusterIP: None) = DNS retorna IPs dos Pods diretamente.
  • ConfigMap = config não-sensível (texto plano). Secret = dados sensíveis (base64, não criptografado por padrão).
  • Volumes refletem atualizações de ConfigMap/Secret; env vars não.
  • kube-proxy mantém as regras de roteamento; CoreDNS resolve nomes de Services.

Aulas 5 e 6 — Parte IControllers de Workload e Armazenamento

Kubernetes não gerencia Pods diretamente na produção — ele usa controllers que observam o estado atual do cluster e o reconciliam com o estado desejado. Esta seção cobre os principais controllers de workload e o modelo de armazenamento persistente: os temas com maior peso em provas de múltipla escolha.

ReplicaSet — o guardião das réplicas

O ReplicaSet garante que exatamente N réplicas de um Pod estejam rodando a qualquer momento. Quando um Pod falha ou é deletado, o controller detecta a divergência e cria um substituto. Quando há Pods a mais, ele remove o excedente. Esse ciclo é chamado de loop de reconciliação.

⚠ Pegadinha

Para escalar uma aplicação você muda o campo replicas no manifesto (ou via kubectl scale) — nunca cria Pods adicionais manualmente. Pods criados à mão não são gerenciados pelo ReplicaSet e não serão substituídos se falharem.

⚠ Pegadinha

Na prática, não se cria ReplicaSet diretamente. O Deployment gerencia ReplicaSets por você e adiciona rollout e rollback. Criar um ReplicaSet nu significa abrir mão de todo o histórico de versões — a questão de prova vai explorar exatamente esse ponto.

Deployment — rollout declarativo e rollback

O Deployment é o controller padrão para aplicações stateless. Ele gerencia um ou mais ReplicaSets: quando você atualiza a imagem ou qualquer campo do template, o Deployment cria um novo ReplicaSet e migra o tráfego de forma controlada. O ReplicaSet antigo é mantido (com replicas: 0) para permitir rollback.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-pagamentos
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api-pagamentos
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # até 1 Pod extra durante o rollout
      maxUnavailable: 0  # nenhum Pod indisponível ao mesmo tempo
  template:
    metadata:
      labels:
        app: api-pagamentos
    spec:
      containers:
      - name: api
        image: minha-org/api-pagamentos:v2.1
        ports:
        - containerPort: 8080

Comandos essenciais de rollout

  • kubectl rollout status deployment/api-pagamentos — acompanha o progresso em tempo real
  • kubectl rollout history deployment/api-pagamentos — lista revisões anteriores
  • kubectl rollout undo deployment/api-pagamentos — volta para a revisão anterior
  • kubectl rollout undo deployment/api-pagamentos --to-revision=3 — volta para revisão específica
  • kubectl scale deployment/api-pagamentos --replicas=5 — escala sem alterar imagem

Questão 1 — Controllers de Workload

Uma equipe precisa implantar um cluster Kafka de 3 nós onde cada nó precisa de armazenamento persistente exclusivo e deve ser endereçável individualmente por DNS. Qual controller Kubernetes é mais adequado?

  • ADeployment com 3 réplicas e um PVC compartilhado do tipo RWX
  • BStatefulSet com volumeClaimTemplates e um Headless Service
  • CDaemonSet com hostPath para garantir 1 instância por node
  • DReplicaSet com 3 réplicas e PersistentVolumeClaim manual
B é correto: StatefulSet fornece identidade estável (kafka-0, kafka-1, kafka-2), PVC individual por réplica e DNS por Pod via Headless Service — exatamente o que Kafka exige.
A erra: Deployment tem Pods intercambiáveis sem identidade; um PVC RWX compartilhado entre os nós Kafka causaria corrupção de dados. C erra: DaemonSet garante 1 Pod por node do cluster, não 3 réplicas independentes; e hostPath não cria PVCs individuais gerenciados. D erra: ReplicaSet nu não possui volumeClaimTemplates e não gerencia rollout — seria necessário criar PVCs manualmente para cada Pod sem garantia de binding correto.

Armazenamento: Volumes, PV, PVC e StorageClass

Kubernetes separa o consumo de armazenamento (quem precisa) da provisão (como é criado). Entender os três objetos — PV, PVC e StorageClass — é fundamental para qualquer questão sobre persistência.

Volume efêmero vs. persistente

  • emptyDir: criado quando o Pod é agendado; destruído quando o Pod é removido do node. Sobrevive a reinicializações de container dentro do mesmo Pod. Uso típico: cache temporário, compartilhamento entre containers do mesmo Pod.
  • hostPath: monta diretório do node no Pod. Dados sobrevivem ao Pod, mas são específicos do node — se o Pod for reagendado em outro node, os dados desaparecem. Use com cuidado; é um vetor de escalada de privilégio.
  • PersistentVolume (PV): recurso de armazenamento provisionado no cluster, independente de qualquer Pod. Sobrevive à remoção do Pod e do PVC (dependendo da reclaimPolicy).
⚠ Pegadinha

emptyDir não persiste a recriação do Pod. Se o Pod for deletado e recriado (por falha, rollout ou scale-down/up), um novo emptyDir vazio é montado. Dados anteriores são perdidos. Para persistência real use PVC.

✓ Ponto-chave sobre binding

O Kubernetes realiza o binding entre PVC e PV verificando: (1) capacidade suficiente, (2) accessMode compatível, (3) storageClassName coincidente. Se nenhum PV estático satisfaz, e existe uma StorageClass com provisionador, um PV é criado dinamicamente.

✗ Anti-padrão

Usar hostPath em produção para persistência. O volume é específico do node — se o Pod for reagendado em outro node os dados desaparecem. Além disso, hostPath permite que um container acesse arquivos sensíveis do sistema operacional do host, representando risco de segurança grave.

Questão 2 — PV, PVC e StorageClass

Um PVC foi criado com storageClassName: fast-ssd e accessModes: [ReadWriteOnce]. Existe um PV disponível com a mesma StorageClass e capacidade suficiente, mas com accessModes: [ReadWriteMany]. O que acontece?

  • AO PVC faz binding com o PV existente, pois RWX é um superset de RWO.
  • BO PVC falha imediatamente com erro de configuração inválida.
  • CO PVC fica em estado Pending; se a StorageClass tiver um provisionador, um novo PV RWO é criado dinamicamente.
  • DO Kubernetes converte automaticamente o accessMode do PV para RWO e realiza o binding.
C é correto: o binding exige que os accessModes solicitados pelo PVC estejam presentes no PV — o PVC com RWO não faz binding com um PV que declara apenas RWX, pois ReadWriteOnce não está na lista de modos do PV. O PVC entra em Pending e, se a StorageClass tiver um provisionador dinâmico configurado, um novo PV com RWO é criado para satisfazer a requisição.
A erra: Kubernetes não trata RWX como superset de RWO para fins de binding — os modos solicitados pelo PVC precisam estar presentes no PV (RWO ∉ {RWX}). B erra: o PVC não falha com erro; ele entra em Pending aguardando um PV compatível. D erra: Kubernetes jamais converte ou altera o accessMode de um PV existente — essa é uma propriedade imutável após a criação.
🎯 Prova
  • ReplicaSet: escalar = mudar replicas, não criar Pods manualmente.
  • Deployment: cria novo ReplicaSet a cada atualização; antigo ReplicaSet fica com replicas: 0 (base para rollback).
  • StatefulSet obrigatoriamente precisa de Headless Service (clusterIP: None) para DNS estável por Pod.
  • DaemonSet: 1 Pod por node — se um novo node entra no cluster, o DaemonSet provisiona automaticamente.
  • emptyDir: morre com o Pod. PV: independe do Pod.
  • PV é cluster-wide; PVC é namespaced.
  • reclaimPolicy: Retain preserva dados; Delete remove o disco subjacente.
TL;DR
  • ReplicaSet mantém N réplicas via reconciliação — nunca use diretamente; o Deployment já inclui tudo isso mais rollout e rollback.
  • Deployment gerencia ReplicaSets: cada deploy cria um novo RS, mantendo o antigo com replicas=0 para rollback com kubectl rollout undo.
  • StatefulSet = identidade estável + PVC por réplica + Headless Service. Use para bancos e sistemas com estado.
  • DaemonSet = exatamente 1 Pod por node. Use para agentes de infraestrutura (log, monitor, rede).
  • emptyDir morre com o Pod. PV existe independente do Pod. PVC é a requisição namespaced que faz binding ao PV.
  • StorageClass habilita provisionamento dinâmico de PVs — elimina a gestão manual de discos.
  • accessModes do PVC devem estar presentes no PV para binding: RWO ≠ RWX.

  • DaemonSet → 1 por node, agente de infra

Aulas 7, 8 (Parte I) e Aula 1 (Parte II)Probes, Autoscaling (HPA) e Jobs

Kubernetes oferece mecanismos distintos para garantir disponibilidade em tempo de execução (Probes), escalar carga de trabalho de forma automática (HPA/VPA/Cluster Autoscaler) e executar tarefas batch com garantia de conclusão (Jobs/CronJobs). As distinções entre eles são tema recorrente de prova.

TL;DR
  • livenessProbe → falhou: reinicia o container. readinessProbe → falhou: remove o Pod do Endpoint/Service (não reinicia). startupProbe → guarda as outras até o app subir.
  • HPA escala réplicas; precisa de resources.requests + metrics-server. VPA ajusta recursos por Pod. Cluster Autoscaler adiciona nodes.
  • Job roda até completar. CronJob agenda Jobs. Ambos proíbem restartPolicy: Always.

⚠ Pegadinha Clássica — Liveness × Readiness

⚠ startupProbe × initialDelaySeconds

Antes da startupProbe existir, usava-se initialDelaySeconds alto na livenessProbe para apps lentos. Com startupProbe, o kubelet aguarda ela passar antes de ativar liveness e readiness — é a abordagem correta para apps de boot imprevisível.

  • initialDelaySeconds: segundos de espera após o container iniciar antes da primeira verificação.

spec:

    ports:

    startupProbe:
      httpGet:
        path: /healthz/startup
        port: 8080
      failureThreshold: 30      # 30 x 10s = até 5 min para o app subir
      periodSeconds: 10
    livenessProbe:
      httpGet:
        path: /healthz/live
        port: 8080
      initialDelaySeconds: 0    # startupProbe já garantiu o boot
      periodSeconds: 15
      failureThreshold: 3
    readinessProbe:
      httpGet:
        path: /healthz/ready
        port: 8080
      periodSeconds: 10
      failureThreshold: 3
      successThreshold: 1
🎯 Prova — O que acontece se readinessProbe falhar continuamente?

O Pod permanece em estado Running, mas com Ready: False. Ele é removido dos Endpoints do Service e não recebe tráfego. O container não é reiniciado. Se o problema se resolver, a probe volta a passar e o Pod é readicionado automaticamente.

Questão

Um container apresenta deadlock após horas em produção: responde ao TCP mas não processa requisições. Qual probe, ao falhar, resolve o problema automaticamente?

  • AreadinessProbe com tcpSocket — remove o Pod do Service.
  • BlivenessProbe com httpGet no endpoint de negócio — reinicia o container.
  • CstartupProbe com exec — reinicia durante o boot.
  • DreadinessProbe com httpGet — reinicia o container após falha.
B é correta: deadlock exige reinício, que é efeito da livenessProbe. — A erra: tcpSocket passaria porque a porta TCP está aberta; além disso, readiness não reinicia. — C erra: startupProbe atua apenas durante o boot; após passar, é desativada. — D erra: readinessProbe nunca reinicia o container; apenas retira do balanceamento.

✗ Anti-padrão — restartPolicy: Always em Job

Jobs e CronJobs proíbem restartPolicy: Always. O Kubernetes rejeitará a criação do recurso com erro de validação. Use Never (Pod fica com status Failed para diagnóstico) ou OnFailure (kubelet reinicia o container dentro do mesmo Pod). Nunca coloque Always em um Job.

Parâmetros-chave de Job

  • completions: quantas execuções bem-sucedidas são necessárias para o Job ser concluído (padrão: 1).
  • parallelism: quantos Pods podem rodar em paralelo ao mesmo tempo (padrão: 1).
  • backoffLimit: número máximo de tentativas antes de marcar o Job como Failed (padrão: 6).
  • activeDeadlineSeconds: tempo máximo de vida do Job; Pods são encerrados e o Job é marcado como falho ao expirar.
  • ttlSecondsAfterFinished: limpa automaticamente o Job (e seus Pods) após N segundos da conclusão.

Observabilidade — Parte II · Aulas 2 e 3Logs, Monitoramento EFK e Helm

Em Kubernetes, todo container escreve para stdout/stderr; o container runtime captura essas streams e as grava em arquivos no nó. Quando o Pod é deletado ou reiniciado, esses arquivos somem — os logs são efêmeros por natureza. Para qualquer análise retrospectiva é preciso uma camada de agregação centralizada que colete os logs antes que o Pod desapareça.

Por que logs somem — e o que fazer

  • O kubelet gerencia arquivos de log por container em /var/log/pods/ no nó, mas sem retenção longa.
  • Um Pod pode ser reprogramado para outro nó; o histórico no nó antigo se perde.
  • Solução: agente de coleta rodando em cada nó como DaemonSet, que lê os arquivos de log e os encaminha para um backend centralizado antes que expirem.
  • O comando kubectl logs só funciona enquanto o container (ou ao menos o Pod) existe — nunca em logs históricos de Pods já deletados.
⚠ Pegadinha

Logs ≠ Métricas. Logs são eventos textuais (linhas de stdout/stderr). Métricas são séries temporais numéricas (CPU, memória, latência). A stack EFK/ELK trata logs; Prometheus + Grafana trata métricas. Confundir as duas stacks é erro clássico de múltipla escolha.

⚠ Pegadinha — Helm 2 × Helm 3

Helm 2 exigia um componente server-side chamado Tiller instalado no cluster, o que gerava problemas sérios de segurança (permissões de cluster admin). Se a questão perguntar o que mudou entre Helm 2 e Helm 3, a resposta central é: remoção do Tiller.

✓ helm upgrade --install

O flag --install no helm upgrade torna o comando idempotente: instala se a Release não existir, atualiza se já existir. Padrão de uso em pipelines CI/CD.

💡 helm rollback e revisões

Cada helm install ou helm upgrade cria uma nova revisão (revision) da Release, armazenada como Secret no namespace. O helm rollback <release> <número> restaura exatamente o estado daquela revisão — incluindo os values usados naquela versão.

C erra porque conceder permissão S3 à Role do nó dá acesso a todos os Pods daquele nó, violando o princípio do menor privilégio.
D erra porque iamidentitymapping mapeia usuários/roles IAM a grupos RBAC do Kubernetes — serve para autenticação no cluster, não para permissões de recursos AWS dentro dos Pods.
Questão 2

Um desenvolvedor quer executar Pods no EKS usando o modo Fargate. Qual afirmação sobre esse modo é verdadeira?

  • ANo Fargate, a AWS gerencia o Control Plane e o desenvolvedor gerencia os nós EC2 subjacentes aos Pods.
  • BDaemonSets são suportados no Fargate para injetar sidecars de observabilidade em todos os Pods.
  • CNo Fargate não há nós EC2 visíveis; o faturamento é por vCPU e memória consumidos pelo Pod, e volumes EBS não são suportados.

C é correto — Fargate abstrai completamente o EC2: cada Pod roda em microVM isolada, cobrado por segundo de vCPU/memória, sem EC2 para gerenciar, sem suporte a EBS (use EFS).

A erra porque no Fargate não há nós EC2 para o desenvolvedor gerenciar — a abstração é total no lado de infraestrutura de nó.
B erra porque DaemonSets exigem um nó real para implantar uma réplica por nó — no Fargate não existe o conceito de nó gerenciável, portanto DaemonSets não são suportados.
D erra porque Fargate e Managed Node Groups coexistem no mesmo cluster EKS; você usa Fargate Profiles para direcionar apenas determinados namespaces/labels ao Fargate.
Questão 3

Após criar um cluster EKS, um engenheiro executa kubectl get nodes e recebe o erro "The connection to the server was refused". Qual é o próximo passo correto?

B erra porque o EKS é um Control Plane gerenciado — não há acesso SSH aos nós do control plane, e o kube-apiserver não é acessível diretamente pelo operador.
C erra porque copiar o endpoint manualmente é incompleto e sujeito a erros; o update-kubeconfig configura tudo automaticamente incluindo o token de autenticação.
D erra porque o problema é de configuração de kubeconfig local, não de permissões IAM no cluster — iamidentitymapping gerencia quem tem acesso RBAC, não onde o kubectl aponta.

Segurança — RBACRole, ClusterRole, RoleBinding e ClusterRoleBinding

RBAC (Role-Based Access Control) é o mecanismo de autorização do Kubernetes. Ele responde: "o sujeito X pode executar a ação Y no recurso Z?"

Recurso Escopo Vinculado por Caso de uso típico

RoleBinding Namespace específico — Vincula Role ou ClusterRole a sujeitos em um namespace

⚠ Pegadinha — ClusterRole + RoleBinding

Um ClusterRole pode ser vinculado por um RoleBinding — nesse caso o acesso fica restrito ao namespace do RoleBinding. Isso permite reusar definições de permissão cluster-wide em escopos menores. A prova costuma afirmar que "ClusterRole só pode ser vinculado por ClusterRoleBinding" — isso é falso.

Segurança — NetworkPolicyFirewall L3/L4 entre Pods

NetworkPolicy restringe o tráfego de rede entre Pods com base em seletores de label, namespace e blocos CIDR. Requer um CNI compatível (Calico, Cilium, AWS VPC CNI com Network Policy habilitado).

✗ Anti-padrão crítico

Por padrão, todo tráfego entre Pods é permitido — qualquer Pod pode se comunicar com qualquer outro Pod no cluster. Sem NetworkPolicy, não há isolamento. Isso é um anti-padrão em produção. A primeira política a criar é uma default-deny-all por namespace, depois liberar explicitamente.

⚠ Pegadinha — NetworkPolicy e CNI

NetworkPolicy é um objeto K8s, mas não tem efeito sem um CNI que a implemente. O CNI padrão do EKS (AWS VPC CNI puro, sem o add-on de Network Policy) ignora os objetos NetworkPolicy. A prova pode afirmar que "criar um NetworkPolicy já restringe o tráfego" — isso é falso se o CNI não suportar.

Exemplo — NetworkPolicy: isola namespace, permite apenas porta 8080 da camada frontend

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-api
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: api          # aplica-se aos Pods com label app=api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend  # somente Pods frontend podem conectar
    ports:
    - protocol: TCP
      port: 8080

Segurança — Secrets & Pod SecurityDados Sensíveis, Criptografia e Postura dos Contêineres

Secrets — armazenamento e criptografia

  • Secrets armazenam dados sensíveis (senhas, tokens, certificados) em Base64 — não é criptografia! Base64 é apenas codificação.
  • Criptografia real em repouso: habilitar envelope encryption com AWS KMS no EKS (encryptionConfig no plano de controle) — o etcd guarda os dados cifrados.
  • Alternativa gerenciada: AWS Secrets Manager + CSI Secrets Store Driver (monta Secrets como volumes sem persisti-los no etcd).
Pod Security Standard Nível de restrição O que permite
privileged Sem restrição Tudo — equivale a sem política
baseline Restrição mínima Bloqueia privilégios mais perigosos (hostPID, hostNetwork, privileged containers)
restricted Restrição máxima Exige runAsNonRoot, allowPrivilegeEscalation: false, drop de todas as capabilities e seccomp profile
✗ PodSecurityPolicy foi removida

PodSecurityPolicy (PSP) foi removida no Kubernetes 1.25. A substituta oficial é o Pod Security Admission (PSA), implementado como um admission controller nativo. PSA aplica os Pod Security Standards (privileged / baseline / restricted) via labels no namespace. Nunca mencione PSP como solução atual em prova — é resposta errada.

Exemplo — securityContext aplicando princípio do menor privilégio

  name: api-seguro
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    fsGroup: 2000
  containers:
  - name: api
    image: 123456789.dkr.ecr.us-east-1.amazonaws.com/api:v2
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]

Questão 1 — RBAC e IAM no EKS

Uma equipe de desenvolvedores tem uma IAM Role configurada no aws-auth ConfigMap do EKS, mapeada para o grupo K8s dev-team. Ao tentar listar Pods no namespace production, recebem "Forbidden". Qual é a causa mais provável?

  • AA IAM Role não tem permissão eks:DescribeCluster na AWS.
  • BNão existe um RoleBinding ou ClusterRoleBinding que conceda ao grupo dev-team o verbo list em pods no namespace production.
  • CO mapeamento no aws-auth só funciona com usuários IAM, não com roles IAM.
  • DÉ necessário criar um ClusterRoleBinding — RoleBinding não funciona para grupos.
B é correto: a autenticação IAM funcionou (o usuário chegou ao cluster), mas o RBAC não tem regra que autorize o grupo dev-team a listar Pods no namespace production. A erra: eks:DescribeCluster é necessária para baixar o kubeconfig, não para operações dentro do cluster — se conseguiu conectar, esse passo já passou. C erra: aws-auth suporta tanto IAM Users (mapUsers) quanto IAM Roles (mapRoles). D erra: RoleBinding funciona com grupos, e para acesso namespaced é justamente o objeto correto; ClusterRoleBinding daria acesso em todo o cluster, o que viola o princípio do menor privilégio.
Questão 2 — NetworkPolicy

Em um cluster EKS com o add-on de Network Policy do VPC CNI habilitado, um time aplicou a seguinte NetworkPolicy no namespace payments: podSelector: {} com policyTypes: [Ingress] e sem regras ingress. Qual o efeito?

  • ANenhum efeito, pois a política está vazia.
  • BTodo tráfego Ingress e Egress é bloqueado para todos os Pods do namespace.
  • CTodo tráfego Ingress é bloqueado para todos os Pods do namespace; Egress permanece irrestrito.
  • DApenas o tráfego entre namespaces é bloqueado; tráfego intra-namespace permanece livre.
C é correto: podSelector: {} seleciona todos os Pods do namespace; policyTypes: [Ingress] sem regras ingress significa "nega todo Ingress". Egress não foi declarado, portanto permanece permitido. A erra: uma política com policyTypes declarado e sem regras correspondentes é uma default deny para aquele tipo — tem efeito sim. B erra: Egress não foi incluído no policyTypes, então não é afetado. D erra: NetworkPolicy não distingue intra/inter-namespace sozinha — o podSelector: {} aplica-se a todos os Pods independente da origem do tráfego.

Aula 9 — ObservabilidadeMonitoramento e Logging no EKS

Observabilidade em Kubernetes se apoia em três pilares complementares. Cada pilar responde a uma pergunta diferente e usa ferramentas específicas no ecossistema EKS.

CloudWatch Container Insights

  • Solução gerenciada AWS: coleta métricas de CPU, memória, rede e disco por Pod, Node e cluster.
  • Requer o add-on Amazon CloudWatch Observability (ou instalação manual do agente CloudWatch + Fluent Bit).
  • Integra com CloudWatch Dashboards e alarmes nativos — sem infraestrutura adicional para gerenciar.
  • Desvantagem: custo por métrica/log ingerido; menos flexibilidade que Prometheus para queries ad-hoc (PromQL).

Prometheus + Grafana — stack open source

  • Prometheus: coleta métricas via scrape HTTP (/metrics) dos Pods e componentes K8s. Armazena localmente como série temporal. Linguagem de query: PromQL.
  • Grafana: consome Prometheus como datasource e renderiza dashboards interativos.
  • Deploy típico: kube-prometheus-stack (Helm chart que instala Prometheus, Grafana, Alertmanager e exporters em um comando).
  • ServiceMonitor (CRD do Prometheus Operator) define quais Services raspar — padrão GitOps-friendly.

  • DaemonSet: um Pod por Node, lê os logs de todos os contêineres em /var/log/containers/.
  • Roteia para CloudWatch Logs, Amazon OpenSearch Service (Elasticsearch), S3 ou Kinesis Data Firehose.
  • Mais leve que Fluentd — preferido em EKS; Fluentd é usado quando transformações complexas são necessárias.
  • Configuração por ConfigMap — define inputs, filters e outputs declarativamente.

Uma empresa quer garantir que o estado real do cluster EKS nunca divirja do estado declarado no repositório Git, com detecção e reconciliação automáticas. Qual abordagem atende melhor esse requisito?

Questão 4 — Pod Security e Secrets

Qual afirmação sobre segurança de Pods e Secrets no Kubernetes está correta?

  • ASecrets são armazenados em Base64 no etcd por padrão; para criptografia real em repouso no EKS, é necessário habilitar envelope encryption com AWS KMS.

  • CO campo readOnlyRootFilesystem: true impede que processos dentro do contêiner façam chamadas de rede.
  • DBase64 é uma forma segura de armazenar senhas em Secrets, pois não é texto puro.
A é correto: Base64 é codificação, não criptografia — qualquer pessoa com acesso ao etcd decodifica em segundos. A criptografia real requer KMS. B erra: PSP foi removida no K8s 1.25; o substituto é Pod Security Admission (PSA). C erra: readOnlyRootFilesystem impede escrita no filesystem do contêiner, não conexões de rede — isso é papel de NetworkPolicy. D erra: Base64 não é segurança — é reversível sem chave; é usado apenas por conveniência de transporte de dados binários.

Controller que mantém N réplicas de um Pod. Gerenciado pelo Deployment.
Deployment
Controller de apps stateless; faz rollout/rollback criando novos ReplicaSets.
StatefulSet
Workload com identidade estável, ordem e PVC por réplica (bancos). Exige Headless Service.
DaemonSet
Garante 1 Pod por node — agentes de log/monitor/rede.
Service
Abstração estável (IP/DNS) que balanceia tráfego para Pods via selector de labels.
ConfigMap / Secret
Injetam configuração. Secret é base64 (não criptografado por padrão) para dados sensíveis.
PV / PVC / StorageClass
PV = armazenamento real (cluster-wide); PVC = requisição namespaced; StorageClass = provisionamento dinâmico.
Probe
Verificação de saúde: liveness (reinicia), readiness (tira do tráfego), startup (boot lento).
HPA
HorizontalPodAutoscaler: escala réplicas por métricas. Requer metrics-server e requests.
Helm
Gerenciador de pacotes do K8s. Chart (templates) → Release (instância). Helm 3 sem Tiller.
EKS
Kubernetes gerenciado da AWS: control plane gerenciado; nodes via Managed/Self/Fargate.
IRSA
IAM Roles for Service Accounts: dá permissão AWS a Pods via OIDC, sem chaves estáticas.
RBAC
Autorização no cluster: Role/ClusterRole + (Cluster)RoleBinding.
NetworkPolicy
Firewall L3/L4 entre Pods. Sem ela, todo tráfego é permitido.
GitOps
Modelo pull (ArgoCD/Flux): Git é a fonte da verdade e o agente sincroniza o cluster a ele.

Véspera da provaPegadinhas & checklist final

🎯 Releia antes de entregar a prova
  • etcd é o banco (não o scheduler); scheduler escolhe o node; kubelet roda no node e inicia o container.
  • kubelet e kube-proxy são do Worker Node — não do Control Plane.
  • Label seleciona; Annotation não é selecionável.
  • ClusterIP só é acessível dentro do cluster; para expor externamente use NodePort/LoadBalancer/Ingress.
  • Secret = base64, não criptografia. Criptografia em repouso precisa ser habilitada (KMS).
  • liveness reinicia; readiness tira do balanceamento (não reinicia); startup protege boot lento.
  • Escalar = mudar replicas (ou kubectl scale) — nunca criar Pods à mão.
  • emptyDir morre com o Pod; PV é independente. PV é cluster-wide; PVC é namespaced.
  • StatefulSet exige Headless Service e dá PVC por réplica; ≠ Deployment com PVC compartilhado.
  • HPA precisa de metrics-server e resources.requests; HPA = réplicas, VPA = recursos, Cluster Autoscaler = nodes.
  • Job usa restartPolicy Never/OnFailure (nunca Always); Job termina, Deployment roda sempre.
  • Helm 3 removeu o Tiller; Fluentd/Fluent Bit rodam como DaemonSet; logs ≠ métricas (Prometheus = métricas).
  • No EKS a AWS gerencia o control plane; Fargate não tem EC2 para gerenciar; use IRSA (não chave estática) para dar permissão AWS a Pods.
  • IAM autentica × RBAC autoriza no EKS; Role é namespaced, ClusterRole é cluster-wide.
  • NetworkPolicy: sem ela, tudo é permitido. PodSecurityPolicy foi removida → use Pod Security Admission.
