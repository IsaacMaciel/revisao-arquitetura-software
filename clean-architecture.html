Tópico 02 · Clean Architecture

Clean Architecture

Proposta por Robert C. Martin (Uncle Bob), a Clean Architecture organiza o sistema em círculos concêntricos governados por uma única regra inviolável: a Regra da Dependência. O objetivo não é "código bonito" — é manter o custo de mudança baixo ao longo da vida do software, isolando as regras de negócio dos detalhes (banco, UI, frameworks).

🎯 Como Clean Architecture cai na prova

Esperе: (1) a Regra da Dependência e seu sentido (de fora para dentro) — quase certo; (2) o que vive em cada círculo (Entities × Use Cases × Adapters × Frameworks) e o que NÃO pode atravessar a fronteira; (3) SOLID — significado de cada letra e exemplos; (4) paradigmas (o que cada um remove); (5) coesão/acoplamento de componentes (REP/CCP/CRP, ADP/SDP/SAP).

FundamentosO que é Clean Architecture

Clean Architecture é a síntese de várias arquiteturas anteriores — Hexagonal (Ports & Adapters), Onion, DCI, BCE — que compartilham o mesmo objetivo: separação de interesses por camadas, com as regras de negócio no centro e os detalhes na borda.

As propriedades de um sistema "clean"

  • Independente de frameworks: o framework é uma ferramenta, não uma camada que dita a arquitetura.
  • Testável: as regras de negócio podem ser testadas sem UI, banco, servidor ou qualquer elemento externo.
  • Independente da UI: a UI pode mudar (web → CLI → desktop) sem tocar nas regras.
  • Independente do banco de dados: trocar Oracle por Mongo não afeta as regras de negócio.
  • Independente de qualquer agente externo: as regras não sabem nada do mundo de fora.

FundamentosO objetivo: dois valores do software

Uncle Bob distingue dois valores de qualquer software. A prova adora essa distinção:

ValorO que éQuem o vê
Comportamento (behavior)Fazer o software funcionar conforme os requisitos — o urgente.Stakeholders imediatos.
Estrutura / ArquiteturaManter o software soft: fácil de mudar — o importante.Visível a longo prazo; o valor da arquitetura.
⚠ A matriz de Eisenhower do Uncle Bob

O comportamento é urgente mas nem sempre importante; a arquitetura é importante mas raramente urgente. O erro clássico é deixar o urgente engolir o importante — e a arquitetura apodrece. "Software" vem de soft = a razão de existir é ser fácil de mudar.

Conceito centralA Regra da Dependência

É o conceito mais cobrado. A Regra da Dependência diz:

📐 Regra da Dependência

As dependências do código-fonte só podem apontar para dentro, em direção às políticas de mais alto nível. Nada num círculo interno pode saber absolutamente nada sobre algo num círculo externo — incluindo nomes de funções, classes, variáveis ou qualquer entidade de software declarada fora.

Consequência prática: o fluxo de controle pode ir de fora para dentro e voltar, mas a dependência de código aponta sempre para dentro. Quando o fluxo precisa ir de dentro para fora (ex.: um use case precisa gravar no banco), usa-se Inversão de Dependência (DIP): o círculo interno define uma interface e o externo a implementa.

✗ Violações típicas

Uma Entity importar uma classe do ORM; um Use Case referenciar um objeto HttpRequest do framework web; o domínio "conhecer" a estrutura da tabela. Tudo isso aponta a dependência para fora → viola a regra.

As camadasOs círculos concêntricos

Quanto mais interno o círculo, mais alto o nível e mais geral/estável a política. Quanto mais externo, mais detalhe e mais volátil. As quatro camadas clássicas (podem ser mais):

Frameworks & DriversDetalhes plugáveis (mais volátil)
Interface AdaptersConverte dados entre dentro e fora
Use CasesRegras específicas da aplicação
EntitiesRegras de negócio mais gerais (mais estável)
Regra da Dependência: o código aponta sempre para o centro. Fora = detalhe/volátil; dentro = política/estável.
💡 As cores não são lei

O número de círculos é só uma ideia — o que é inviolável é a Regra da Dependência. Você pode ter mais de quatro camadas, mas elas sempre obedecem ao sentido de fora→dentro.

Camada · centroEntities (Enterprise Business Rules)

As Entities encapsulam as regras de negócio mais gerais e de mais alto nível — aquelas que existiriam mesmo sem o sistema automatizado. Numa empresa grande, uma entity pode ser um objeto com métodos, ou um conjunto de estruturas e funções. São as menos prováveis de mudar quando algo externo muda.

⚠ Não confunda com a Entity do DDD

A "Entity" da Clean Architecture ≈ regras de negócio corporativas (Enterprise Business Rules). É um conceito de camada, mais amplo que a "Entidade" tática do DDD (que se opõe a Value Object pela identidade). Em prova de Clean Architecture, pense em "regra de negócio crítica e duradoura".

CamadaUse Cases (Application Business Rules)

Os Use Cases contêm as regras de negócio específicas da aplicação — orquestram o fluxo de dados de e para as Entities para realizar uma operação do sistema (ex.: "Realizar Saque"). Eles não sabem como a informação chega (HTTP? CLI?) nem para onde vai (Postgres? arquivo?) — isso é detalhe das camadas externas.

Padrão de comunicação dos use cases

  • Input/Output Boundaries: interfaces que delimitam a entrada e a saída do use case.
  • Request/Response Models (DTOs): estruturas simples de dados que cruzam a fronteira — sem objetos do framework.
  • Interactor: a implementação do use case que executa a regra.

CamadaInterface Adapters

Convertem os dados do formato conveniente para use cases/entities para o formato conveniente para agentes externos (e vice-versa). Aqui vivem:

  • Controllers — recebem a entrada externa e a traduzem para o use case.
  • Presenters — formatam a saída do use case para a view (ex.: ViewModel).
  • Gateways / Repositories (impl.) — adaptam o acesso a dados.

É a camada que implementa o padrão MVC/MVP/MVVM e onde mora o SQL — nenhum SQL deve "vazar" para dentro.

Camada · bordaFrameworks & Drivers

O círculo mais externo: o banco de dados, o framework web, a UI, dispositivos. Uncle Bob: "the web is a detail", "the database is a detail". São plugáveis e devem conter o mínimo de código — só a "cola" que liga ao círculo de dentro.

MecanismoCruzando fronteiras (DIP na prática)

O ponto delicado: o fluxo de controle às vezes vai de dentro (use case) para fora (banco), mas a dependência tem de continuar apontando para dentro. A solução é a Inversão de Dependência:

Fluxo de controle vai para fora; a dependência de código aponta para dentro (interface no centro).
Questão

Um Use Case precisa persistir dados no banco, mas não pode depender da camada de infraestrutura. Como a Clean Architecture resolve isso?

  • AO Use Case importa diretamente a classe do ORM para gravar os dados.
  • BO Use Case define uma interface (porta) no círculo interno; a infraestrutura a implementa no círculo externo (Inversão de Dependência).
  • CA Entity acessa o banco para o Use Case não precisar.
  • DO fluxo de controle não pode sair do círculo interno em hipótese alguma.
O DIP inverte a seta: a interface fica no centro e a implementação na borda. (A) e (C) violam a Regra da Dependência; (D) confunde fluxo de controle (que pode sair) com dependência de código (que aponta para dentro).

Aula 5 · paradigmasParadigmas de programação

Uncle Bob tem uma tese provocadora: cada paradigma retira algo do programador (impõe disciplina), não adiciona poder. Cada um remove um uso de uma "palavra" perigosa:

ParadigmaO que REMOVEDisciplina que impõeServe à arquitetura porque…
EstruturadaO goto (saltos irrestritos)Controle de fluxo via if/while/sequência.Permite decompor em módulos testáveis/prováveis.
Orientada a ObjetosPonteiros de função (transferência indireta de controle)Polimorfismo seguro.Dá controle sobre a direção das dependências (base do DIP e dos plugins).
FuncionalA atribuição (mutação de variável)Imutabilidade.Elimina condições de corrida e facilita concorrência.
💡 O que importa para a arquitetura

Para o Uncle Bob, o grande presente do OO à arquitetura é o polimorfismo, que permite inverter a direção da dependência através de uma fronteira — exatamente o que torna possível plugar banco/UI sem o domínio saber. É daí que sai a Regra da Dependência.

Questão

Segundo Robert C. Martin, qual recurso a Programação Orientada a Objetos efetivamente "remove" e qual é seu maior valor arquitetural?

  • ARemove a atribuição; valor: imutabilidade.
  • BRemove o goto; valor: fluxo estruturado.
  • CNão remove nada; apenas adiciona herança e encapsulamento.
  • DRemove os ponteiros de função; valor: polimorfismo que permite inverter a direção das dependências.
Para o Uncle Bob, OO disciplina a transferência indireta de controle (ponteiros de função) e oferece polimorfismo — o mecanismo que inverte dependências através de fronteiras. (A) descreve a Funcional; (B) descreve a Estruturada.

Aula 5 · componentesComponentes & princípios de coesão

Um componente é a menor unidade que pode ser deployada (jar, dll, gem). Como agrupar classes em componentes? Três princípios de coesão — que estão em tensão entre si:

SiglaPrincípioDiz que…
REPReuse/Release EquivalenceA granularidade de reúso é a granularidade de release. O que é reusado junto, versiona junto.
CCPCommon Closure PrincipleAgrupe classes que mudam pelas mesmas razões e nos mesmos momentos (é o SRP no nível de componente).
CRPCommon Reuse PrincipleNão force os usuários a depender do que não usam; classes reusadas juntas ficam juntas (é o ISP no nível de componente).
Mnemônico — coesão de componentes
"REP, CCP, CRP — o triângulo da tensão"
  • CCP e CRP puxam para lados opostos (juntar p/ manutenção × separar p/ reúso); REP equilibra. Não dá para maximizar os três ao mesmo tempo.

ComponentesAcoplamento de componentes

Três princípios para as relações entre componentes:

SiglaPrincípioDiz que…
ADPAcyclic DependenciesO grafo de dependências entre componentes não pode ter ciclos. (Quebre ciclos com DIP ou um novo componente.)
SDPStable DependenciesDependa na direção da estabilidade: componentes instáveis dependem de estáveis, nunca o contrário.
SAPStable AbstractionsUm componente deve ser tão abstrato quanto estável. Estável → abstrato (interfaces); instável → concreto.
⚠ Estável ≠ "muda pouco por sorte"

Estabilidade aqui = "difícil de mudar", e isso decorre de quantos dependem de você (muitos dependentes = estável, pois mudar quebra todos). SDP + SAP juntos evitam a "zona da dor" (estável e concreto) e a "zona da inutilidade" (abstrato e instável).

Aula 6 · Design PrinciplesSOLID

Os cinco princípios de design de classes (Uncle Bob / Michael Feathers). Quase garantido em prova — saiba a letra, o nome e uma frase de cada:

LetraPrincípioEm uma frase
SSingle Responsibility (SRP)Uma classe deve ter um único motivo para mudar — responder a um único ator/stakeholder.
OOpen/Closed (OCP)Aberto para extensão, fechado para modificação: estenda comportamento sem alterar código existente.
LLiskov Substitution (LSP)Subtipos devem ser substituíveis por seus tipos base sem quebrar o programa.
IInterface Segregation (ISP)Não force um cliente a depender de métodos que não usa; prefira interfaces pequenas.
DDependency Inversion (DIP)Dependa de abstrações, não de implementações concretas. Detalhes dependem de políticas, não o contrário.
⚠ Pegadinha do SRP

SRP não é "uma classe faz só uma coisa". É "uma classe tem um único motivo para mudar", ou seja, responde a um único ator. Alternativa que define SRP como "função pequena" geralmente está incompleta/errada.

Questão

"Uma classe deve estar aberta para extensão, mas fechada para modificação." Qual princípio SOLID é esse e o que ele evita?

  • ASRP — evita classes com muitas responsabilidades.
  • BLSP — evita que subtipos quebrem o contrato da base.
  • COCP — evita modificar código existente e testado ao adicionar novo comportamento.
  • DDIP — evita depender de implementações concretas.
É o Open/Closed Principle: novo comportamento entra por extensão (herança, composição, plugins), sem alterar o que já funciona — reduzindo o risco de regressões.
Questão

Uma interface Trabalhador obriga toda implementação a ter comer() e trabalhar(). Um Robo implementa trabalhar() mas é forçado a implementar comer() sem sentido. Qual princípio foi violado?

  • AISP — Interface Segregation: o cliente foi forçado a depender de um método que não usa.
  • BOCP — Open/Closed.
  • CSRP — Single Responsibility.
  • DLSP — Liskov Substitution.
Interface "gorda" que força implementações a métodos inúteis viola o ISP. A solução é segregar em interfaces menores (ex.: Trabalhavel e Alimentavel).

Aula 3-4 · Clean Code em testesClean Code aplicado a testes

Testes são cidadãos de primeira classe — código de teste sujo apodrece tão rápido quanto código de produção sujo. Uncle Bob chama testes da regra F.I.R.S.T.:

LetraSignificaBom teste é…
FFastRápido — você roda o tempo todo.
IIndependentIndependente — um teste não depende de outro nem da ordem.
RRepeatableRepetível em qualquer ambiente (sem depender de rede/data/máquina).
SSelf-validatingAutoverificável — passa ou falha, sem inspeção manual.
TTimelyEscrito no momento certo — idealmente antes do código (TDD).

Estrutura e leis de teste

  • AAA / Given-When-Then: Arrange (prepara) → Act (executa) → Assert (verifica). Um conceito por teste.
  • As 3 Leis do TDD: (1) não escreva código de produção sem um teste que falhe; (2) não escreva mais teste do que o suficiente para falhar; (3) não escreva mais produção do que o suficiente para passar.
  • Ciclo Red → Green → Refactor: falha → faz passar → melhora sem quebrar.
💡 Por que isso é arquitetura

A testabilidade não é acidente: uma Clean Architecture é testável porque as regras de negócio não dependem de UI/DB/framework. Se um use case só pode ser testado subindo o banco e o servidor, a arquitetura falhou na Regra da Dependência.

Aula 7-8 · práticaImplementando a arquitetura

Na prática, a organização do código costuma ser por camada/feature respeitando as fronteiras. Um fluxo de request típico atravessa os círculos assim:

Web/UI
→
Controller
→
Use Case
Interactor
→
Entities
→
Presenter
→
ViewModel/UI
Controle entra, mergulha até as Entities e volta via Presenter — a dependência de código nunca aponta para fora.

Decisões de implementação que a aula enfatiza

  • Screaming Architecture: a estrutura de pastas deve "gritar" o domínio (ex.: emprestimo/, cobranca/), não o framework (controllers/, models/).
  • Detalhes adiados: escolher banco/framework é uma decisão que pode (e deve) ser postergada — a arquitetura permite começar sem decidir.
  • Humble Object: separe o que é difícil de testar (view, infra) do que é fácil (lógica), empurrando a lógica para dentro.
  • Cruzar fronteira só com DTOs simples, nunca com Entities ou objetos do framework.

ComparaçãoClean × Hexagonal × Onion

São "primas" — mesma ideia (domínio no centro, dependência para dentro), ênfases diferentes. Distinguir cai em prova:

ArquiteturaAutorÊnfase distintiva
Hexagonal (Ports & Adapters)Alistair CockburnSimetria entre entradas e saídas via portas (interfaces) e adaptadores. Sem nº fixo de camadas.
OnionJeffrey PalermoCamadas concêntricas explícitas com o modelo de domínio no núcleo; foco em DIP entre camadas.
CleanRobert C. MartinUnifica as anteriores; nomeia as camadas (Entities/Use Cases/Adapters/Frameworks) e formaliza a Regra da Dependência + componentes/SOLID.
💡 Frase para guardar

Hexagonal, Onion e Clean são variações do mesmo tema: isolar a regra de negócio dos detalhes e fazer a dependência apontar para o domínio. A Clean é a mais prescritiva sobre os nomes das camadas.

Véspera da provaPegadinhas & checklist final

🎯 Releia antes de entregar a prova
  • Regra da Dependência: código aponta para dentro; círculo interno não conhece o externo.
  • Fluxo de controle pode sair; dependência de código não. Use DIP para inverter.
  • Camadas (dentro→fora): Entities → Use Cases → Adapters → Frameworks.
  • Banco, web e UI são detalhes no círculo externo.
  • SRP = um motivo para mudar / um ator (não "faz uma coisa só").
  • OCP = aberto p/ extensão, fechado p/ modificação.
  • OO remove ponteiros de função → polimorfismo → inverte dependências (o valor arquitetural).
  • Funcional remove atribuição (imutabilidade); Estruturada remove goto.
  • Coesão de componentes = REP/CCP/CRP; acoplamento = ADP/SDP/SAP.
  • ADP = grafo de dependências sem ciclos.
  • Testes seguem F.I.R.S.T.; arquitetura limpa é testável por construção.
  • Clean, Hexagonal e Onion = mesma ideia, ênfases diferentes (não são opostas).
