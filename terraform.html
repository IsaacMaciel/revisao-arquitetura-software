Tópico 03 · Terraform

Terraform

Criado pela HashiCorp, o Terraform é a ferramenta de Infrastructure as Code (IaC) que provisiona e gerencia infraestrutura de forma declarativa: você descreve o estado desejado em HCL e o Terraform calcula e executa as mudanças necessárias para chegar lá. O coração de tudo é o state — o mapa entre a sua configuração e os recursos reais no provedor.

🎯 Como Terraform cai na prova

Espere: (1) declarativo × imperativo e o que é IaC — quase certo; (2) o que é o tfstate, por que existe e por que precisa de remote backend + lock; (3) o fluxo de comandos (init → plan → apply → destroy) e o papel de cada um; (4) precedência de variáveis (quem vence quem); (5) count × for_each (a pegadinha clássica); (6) data × resource × variable × local; (7) módulos (source, version, inputs/outputs); (8) Terraform Cloud (remote runs, VCS-driven, Sentinel).

Aula 1 · FundamentosIntrodução ao Terraform

Infrastructure as Code (IaC) é a prática de definir e provisionar infraestrutura (servidores, redes, bancos, DNS) por meio de arquivos de configuração versionáveis, em vez de cliques no console. Isso traz versionamento (Git), revisão por pares, reprodutibilidade e auditoria.

Características que definem o Terraform

  • Declarativo: você descreve o quê (estado final), não o como (passos).
  • Cloud-agnostic / multi-provider: AWS, Azure, GCP, Kubernetes, etc., via providers plugáveis.
  • HCL (HashiCorp Configuration Language): linguagem própria, legível, declarativa (também aceita JSON).
  • Idempotente: rodar apply de novo sem mudanças na config não recria nada — ele converge para o estado desejado.
  • Plano explícito: mostra o diff antes de aplicar (execution plan).
  • State: mantém um arquivo de estado que mapeia config ↔ recursos reais.
💡 Idempotência em uma frase

Idempotência = aplicar a mesma configuração N vezes produz o mesmo resultado. O Terraform compara o estado desejado (config) com o estado atual (state + realidade) e só faz a diferença — não executa comandos cegamente como um script imperativo.

Conceito centralDeclarativo × Imperativo

É a distinção que mais cai. Um script imperativo (Bash, parte do Ansible) lista os passos; uma config declarativa (Terraform, CloudFormation) descreve o resultado e deixa a ferramenta descobrir os passos.

CritérioDeclarativo (Terraform)Imperativo (script)
O que você escreveO estado final desejado.A sequência de comandos para chegar lá.
Quem calcula os passosA ferramenta (via plan).Você (no código).
ReexecuçãoIdempotente — converge para o desejado.Pode duplicar/quebrar se não tratar estado manualmente.
Conhecimento do existenteMantém state para saber o que já existe.Normalmente não sabe — você verifica na mão.
⚠ Pegadinha: declarativo ≠ "sem ordem"

Ser declarativo não significa que a ordem não importe. O Terraform monta um grafo de dependências (DAG) a partir das referências entre recursos e executa na ordem correta, em paralelo quando possível. A ordem é inferida, não escrita à mão.

ComparaçãoTerraform × CloudFormation × Ansible × Pulumi

Distinguir as ferramentas de provisionamento/configuração cai em prova. O critério-chave: declarativo × imperativo, provisioning × configuration management e cloud-agnostic × cloud-específico.

FerramentaFocoParadigmaEscopo
Terraform (HashiCorp)Provisionamento de infraDeclarativo (HCL)Multi-cloud / agnóstico
CloudFormation (AWS)Provisionamento de infraDeclarativo (JSON/YAML)Só AWS
Ansible (Red Hat)Configuration management (e algum provisioning)Procedural/imperativo (playbooks)Multi-plataforma; agentless (SSH)
PulumiProvisionamento de infraDeclarativo via linguagens gerais (TS, Python, Go)Multi-cloud
💡 Resumo das distinções

Terraform vs CloudFormation: mesma ideia declarativa, mas Terraform é multi-cloud e CFN é só AWS. Terraform vs Ansible: Terraform provisiona infra (declarativo + state); Ansible é mais configuration management (procedural, sem state próprio). Terraform vs Pulumi: ambos declarativos, mas Pulumi usa linguagens de programação reais em vez de HCL.

Questão

Qual afirmação distingue corretamente Terraform de Ansible?

  • AAmbos são imperativos e mantêm um arquivo de state idêntico.
  • BTerraform é exclusivo da AWS; Ansible é multi-cloud.
  • CTerraform é declarativo e focado em provisionamento de infra com state; Ansible é mais procedural e focado em configuration management.
  • DTerraform usa playbooks YAML executados em ordem; Ansible usa HCL declarativo.
Terraform = declarativo, provisiona infra e mantém state; Ansible = procedural/imperativo, foco em configuration management (instalar pacotes, configurar SO), agentless via SSH. (B) inverte: CloudFormation é que é só AWS, não o Terraform. (D) troca as linguagens.

Aula 2 · NúcleoProviders & Backend

Um provider é um plugin que ensina o Terraform a falar com uma API específica (AWS, Azure, GCP, GitHub, Kubernetes…). Ele expõe os resource types (aws_instance) e data sources (aws_ami). Providers são baixados no terraform init e fixados no lock file (.terraform.lock.hcl).

hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}

O backend define onde o state é armazenado e como as operações rodam. O default é o local backend (arquivo terraform.tfstate no diretório). Em equipe, usa-se um remote backend.

O Core lê config + state e fala com a nuvem somente através do provider.

Conceito críticoO tfstate (state)

O state (arquivo terraform.tfstate, em JSON) é o mapa entre a sua configuração e os recursos reais no provedor. Sem ele o Terraform não saberia qual recurso real corresponde a qual bloco da config.

Por que o state existe

  • Mapeamento (binding): liga cada recurso da config a um ID real (ex.: i-0abc123).
  • Metadados & dependências: guarda a ordem e relações para destruir/atualizar corretamente.
  • Performance / cache: evita consultar toda a nuvem a cada plan.
  • Detecção de drift: compara state × realidade × config para calcular o diff.
CritérioLocal backendRemote backend
Onde fica o stateArquivo local terraform.tfstate.Remoto (S3, Terraform Cloud, GCS, Azure Blob…).
Trabalho em equipeRuim — state não compartilhado, conflitos.Compartilhado e centralizado.
State lockingNão há (ou só local).Sim (ex.: S3 + DynamoDB; ou nativo no TF Cloud).
Segurança de segredosFica em texto no disco do dev.Cifrado em repouso, acesso controlado.
✗ O state é SENSÍVEL

O state pode conter segredos em texto puro (senhas de RDS, chaves, tokens) que recursos retornam. Por isso: nunca commitar terraform.tfstate no Git; usar remote backend cifrado; restringir acesso. Tratar o state como dado confidencial.

⚠ Pegadinha: state locking

O state lock impede que dois apply simultâneos corrompam o state. No backend S3 clássico, o lock é feito por uma tabela DynamoDB (o S3 guarda o state; o DynamoDB guarda o lock). Não confunda: o S3 não faz lock sozinho na configuração tradicional.

hcl
terraform {
  backend "s3" {
    bucket         = "minha-empresa-tfstate"
    key            = "prod/network/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "tf-locks"   # state locking
    encrypt        = true
  }
}
Questão

Uma equipe usa o backend S3 para o state do Terraform. Qual é o papel da tabela DynamoDB associada?

  • AArmazenar o conteúdo do arquivo de state em vez do S3.
  • BFornecer state locking, impedindo dois apply simultâneos de corromperem o state.
  • CCifrar automaticamente o state em repouso.
  • DSubstituir o comando terraform plan por uma versão remota.
O S3 guarda o state; a tabela DynamoDB guarda o lock (state locking), serializando operações concorrentes. (A) inverte os papéis; (C) a cifragem vem de encrypt = true/SSE do S3, não do DynamoDB; (D) o plan não depende disso.

Aula 3 · CLIPrincipais comandos

O ciclo de vida básico é init → plan → apply (e destroy para remover). Saber o que cada comando faz — e o que NÃO faz — é prato cheio de prova.

ComandoO que faz
terraform initInicializa o diretório: baixa providers e módulos, configura o backend. Sempre o primeiro.
terraform planCalcula e mostra o diff (o que será criado/alterado/destruído). Não muda nada.
terraform applyAplica as mudanças para chegar ao estado desejado (pede confirmação ou usa um plano salvo).
terraform destroyDestrói toda a infra gerenciada por aquele state.
terraform fmtFormata os arquivos .tf no estilo canônico.
terraform validateValida a sintaxe e consistência interna da config (não acessa a nuvem).
terraform refreshAtualiza o state com a realidade do provedor (hoje embutido no plan/apply via -refresh-only).
terraform importTraz um recurso existente (criado fora) para o state, sem recriá-lo.
terraform taint / untaintMarca/desmarca um recurso para ser recriado no próximo apply (preferir -replace hoje).
terraform workspaceGerencia múltiplos states isolados (ex.: dev/stage/prod) com a mesma config.
terraform outputMostra os valores de output definidos.
terraform showExibe o state ou um plano salvo em formato legível.
terraform state list / mv / rmInspeciona e manipula o state: listar, mover (renomear/refatorar), remover (sem destruir o recurso real).
Mnemônico — o fluxo de vida
"Init · Plan · Apply · Destroy"
  • Init prepara (providers/backend) → Plan mostra o diff (não muda nada) → Apply executa → Destroy desfaz. Decore essa ordem: o plan nunca altera infra; o apply é quem altera.
⚠ Pegadinha: state rm não destrói

terraform state rm remove o recurso do state (o Terraform "esquece" dele), mas não destrói o recurso real na nuvem. Já terraform destroy destrói o recurso real. E terraform import faz o oposto do rm: traz um recurso existente para o state.

Questão

Qual comando mostra o conjunto de mudanças que seriam feitas, sem modificar a infraestrutura real?

  • Aterraform plan — calcula e exibe o diff; não aplica nada.
  • Bterraform apply — pois ele só simula as mudanças.
  • Cterraform init — porque baixa os providers para validar.
  • Dterraform destroy — pois mostra o que seria removido.
O plan produz o execution plan (diff) sem tocar na infra. (B) o apply efetivamente aplica; (C) o init só prepara o diretório; (D) o destroy remove de fato (e seu próprio plan mostra remoções, mas o comando do enunciado é o plan).

Aula 4 · ConfiguraçãoVariáveis & Output

As input variables parametrizam a config (tornam-na reutilizável). Os output values expõem valores para o usuário ou para outros módulos.

hcl
variable "instance_type" {
  type        = string
  default     = "t3.micro"
  description = "Tipo da instância EC2"
}

variable "db_password" {
  type      = string
  sensitive = true   # não aparece em logs/plan
}

output "instance_ip" {
  value = aws_instance.web.public_ip
}

Tipos suportados: primitivos (string, number, bool), coleções (list, set, map) e estruturais (object, tuple). sensitive = true oculta o valor da saída; sensitive em output também esconde nos logs.

Pegadinha clássicaPrecedência de variáveis (ordem de carregamento)

Quando a mesma variável é definida em vários lugares, o Terraform aplica uma ordem de precedência. Quem é carregado por último vence. Cai muito em prova:

Ordem (do menor → maior peso)FonteObservação
1 (mais fraco)default no bloco variableValor de fallback.
2Variável de ambiente TF_VAR_nomeEx.: TF_VAR_region=us-east-1.
3terraform.tfvarsCarregado automaticamente.
4*.auto.tfvars (ordem alfabética)Carregados automaticamente.
5 (mais forte)-var e -var-file na linha de comandoSempre vencem (a última flag na linha prevalece).
⚠ Pegadinha: a CLI vence o tfvars

Se a variável estiver no terraform.tfvars e for passada com -var na linha de comando, a CLI vence. O default é o mais fraco de todos; TF_VAR_ perde para os arquivos .tfvars; e a linha de comando bate todos.

Questão

A variável region tem default = "us-west-2", está como region = "us-east-1" no terraform.tfvars, e você roda terraform apply -var="region=eu-west-1". Qual valor é usado?

  • Aus-west-2 — o default sempre prevalece.
  • Bus-east-1 — o tfvars tem prioridade máxima.
  • CErro — não se pode definir a variável em mais de um lugar.
  • Deu-west-1 — a flag -var da linha de comando vence todas as demais fontes.
A ordem é: default < TF_VAR_ < terraform.tfvars < *.auto.tfvars < -var/-var-file (CLI). A CLI é o mais forte → eu-west-1. (A) e (B) erram a precedência; (C) é falso — definir em vários lugares é permitido e resolvido pela precedência.

Aula 5 · ConfiguraçãoData Sources & Locals

Três coisas que a prova adora confundir: variable (entrada externa), local (valor calculado interno) e data source (consulta read-only à infra existente).

BlocoO que éDireção / efeito
variableEntrada parametrizável da config.Vem de fora (CLI, tfvars, env). Não cria infra.
localValor nomeado interno (expressão calculada).Reutilização/DRY dentro do módulo. Não cria infra.
data (data source)Consulta read-only a recursos que já existem.Lê, não cria/altera (ex.: buscar a AMI mais recente).
resourceObjeto de infra gerenciado.Cria/atualiza/destrói o recurso real.
 
hcl
# data: LÊ a AMI mais recente (não cria nada)
data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"]
  filter {
    name   = "name"
    values = ["ubuntu/images/*-22.04-amd64-server-*"]
  }
}

locals {
  name_prefix = "prod-web"
  common_tags = { Env = "prod", Team = "infra" }
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id   # usa o data source
  instance_type = var.instance_type
  tags          = local.common_tags
}
⚠ Pegadinha: data ≠ resource

Um data source (data "aws_ami") consulta algo que já existe — ele NÃO cria nem destrói nada. Um resource (resource "aws_instance") é gerenciado pelo Terraform e entra no destroy. Alternativa que diz "data source cria o recurso" está errada.

Questão

Você precisa referenciar uma AMI da AWS que já existe na conta, sem gerenciá-la pelo Terraform. Qual bloco usar?

  • AUm resource "aws_ami", pois todo objeto da AWS é um resource.
  • BUm data "aws_ami" — data source faz consulta read-only sem criar/gerenciar o objeto.
  • CUma variable do tipo string com o ID hardcoded é a única forma.
  • DUm local, pois locals consultam a API do provider.
Data source é exatamente para ler recursos existentes sem gerenciá-los. (A) usaria um resource e tentaria gerenciar/criar; (C) é possível mas frágil (e não é "a única forma"); (D) local só calcula expressões, não consulta APIs.

Aula 6 · ReúsoMódulos

Um módulo é um conjunto de arquivos .tf em um diretório — a unidade de reúso e empacotamento de infra. Todo diretório de trabalho é o root module; ele pode chamar child modules.

Anatomia de uma chamada de módulo

  • source: de onde vem o módulo — caminho local (./modules/vpc), Git, ou o Terraform Registry (terraform-aws-modules/vpc/aws).
  • version: restrição de versão (só para registry/sources versionados). Fixar versão evita quebras.
  • inputs: as variáveis que você passa ao módulo.
  • outputs: os valores que o módulo expõe de volta (module.vpc.vpc_id).
hcl
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.8.1"          # fixa a versão

  name = "prod-vpc"
  cidr = "10.0.0.0/16"
}

# consumindo um output do módulo
resource "aws_instance" "web" {
  subnet_id = module.vpc.public_subnets[0]
}
💡 Módulos = DRY de infra

Módulos permitem encapsular um padrão (VPC, cluster, bucket com políticas) e reutilizá-lo em dev/stage/prod com inputs diferentes — o "Don't Repeat Yourself" aplicado à infraestrutura. O Terraform Registry publica módulos públicos e privados versionados.

Questão

Ao consumir um módulo do Terraform Registry, qual a importância de fixar o argumento version?

  • AÉ obrigatório para qualquer source, inclusive caminhos locais.
  • BDefine a versão do provider AWS automaticamente.
  • CGarante reprodutibilidade: evita que uma atualização do módulo quebre sua infra de forma inesperada.
  • DNão tem efeito — o Terraform sempre usa a última versão.
Fixar version trava o módulo numa versão conhecida, garantindo reprodutibilidade. (A) é falso: version só vale para sources versionados (registry/git tag), não para caminhos locais; (B) confunde com required_providers; (D) é o oposto do correto.

Aula 7 · LógicaLoops & expressões

O par mais cobrado: count × for_each. Ambos criam múltiplas instâncias de um recurso, mas a forma como o Terraform indexa no state muda tudo.

Critériocountfor_each
EntradaUm número.Um map ou set de strings.
Índice no statePosicional: [0], [1]…Por chave: ["web"], ["db"].
Remover um item do meio⚠ Reindexação: tudo após o removido é recriado/deslocado.Estável: só o item da chave removida é afetado.
Quando usarN cópias idênticas/condicional (0 ou 1).Coleção de itens distintos identificados por chave.
 
hcl
# count — N cópias indexadas por posição
resource "aws_instance" "app" {
  count         = 3
  instance_type = "t3.micro"
}

# for_each — uma por chave do map (índice estável)
resource "aws_instance" "named" {
  for_each      = { web = "t3.small", db = "t3.medium" }
  instance_type = each.value
  tags          = { Name = each.key }
}
⚠ Pegadinha: por que preferir for_each

Com count, remover um item no meio da lista faz o Terraform reindexar — os recursos seguintes "deslizam" de índice e são destruídos/recriados (efeito colateral perigoso). Com for_each a chave é estável, então só o item removido é afetado. Por isso a recomendação: count para 0/1 ou cópias idênticas; for_each para coleções nomeadas.

Questão

Você gerencia 5 buckets distintos. Removendo um do meio da lista, por que for_each é preferível a count?

  • APorque count não permite mais de 3 recursos.
  • BPorque for_each é imperativo e count é declarativo.
  • CNão há diferença prática; ambos indexam por chave de string.
  • DPorque count indexa por posição: remover do meio reindexa e recria recursos seguintes; for_each usa chaves estáveis, afetando só o item removido.
O ponto é a indexação no state: count usa índice posicional (reindexa ao remover do meio); for_each usa chave estável. (A) count aceita qualquer número; (B) ambos são declarativos; (C) só o for_each indexa por chave — count indexa por posição.

Além dos loops de recurso, o HCL tem for expressions (transformar listas/maps), dynamic blocks (gerar blocos repetidos dentro de um recurso) e conditionals (cond ? a : b):

hcl
# for expression: maiúsculas de cada nome
upper_names = [for n in var.names : upper(n)]

# conditional
instance_type = var.is_prod ? "t3.large" : "t3.micro"

# dynamic block: gera N ingress rules
dynamic "ingress" {
  for_each = var.ports
  content {
    from_port = ingress.value
    to_port   = ingress.value
    protocol  = "tcp"
  }
}

LógicaMeta-arguments: depends_on & lifecycle

Os meta-arguments são argumentos que qualquer bloco resource aceita, independentemente do provider: count, for_each, provider, depends_on e lifecycle.

Os dois que mais caem

  • depends_on: declara dependência explícita quando o Terraform não consegue inferi-la por referência. Use só quando necessário — prefira dependências implícitas.
  • lifecycle: controla o ciclo de vida: create_before_destroy (cria o novo antes de destruir o velho), prevent_destroy (bloqueia destruição acidental) e ignore_changes (ignora mudanças externas em certos atributos).

Aula 8 · PráticaCriando infra com AWS

O fluxo prático junta tudo: declarar o provider, descrever os recursos e rodar init → plan → apply. As dependências entre recursos são, na maioria, implícitas — surgem das referências de um recurso a outro.

hcl
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

resource "aws_subnet" "public" {
  vpc_id     = aws_vpc.main.id   # dependência IMPLÍCITA
  cidr_block = "10.0.1.0/24"
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"
  subnet_id     = aws_subnet.public.id
}

resource "aws_s3_bucket" "assets" {
  bucket = "prod-assets-bucket"
}
💡 Dependência implícita × explícita

Quando o aws_subnet referencia aws_vpc.main.id, o Terraform infere que a VPC deve existir primeiro — é uma dependência implícita (o caso normal). Só use depends_on (explícita) quando há uma dependência real que não aparece como referência no código.

→

cria infra

O apply só executa após o plan ser revisado/confirmado; o grafo de dependências define a ordem real.

Aula 9 · PlataformaTerraform Cloud

O Terraform Cloud (HCP Terraform) é a plataforma gerenciada da HashiCorp que executa o Terraform de forma remota, centralizando state, runs e políticas para equipes.

O que o Terraform Cloud entrega

  • Remote runs: plan/apply rodam em runners gerenciados, não na máquina do dev.
  • Remote state: state armazenado, cifrado, versionado e com locking nativo.
  • VCS-driven workflow: conecta a um repositório (GitHub/GitLab); um push dispara o plan automaticamente.
  • Workspaces: no TF Cloud, cada workspace é um ambiente isolado com seu próprio state e variáveis (mais amplo que o workspace da CLI).
  • Sentinel: policy as code — regras que validam o plan antes do apply (ex.: "proibir instância sem tag", "negar bucket público").
⚠ Pegadinha: workspace CLI ≠ workspace TF Cloud

O workspace da CLI (terraform workspace) só separa states dentro do mesmo backend. O workspace do Terraform Cloud é um conceito mais rico: ambiente completo com state, variáveis, runs e VCS próprios. A prova pode tentar tratá-los como idênticos.

Questão

No Terraform Cloud, qual recurso permite aplicar regras de governança (policy as code) que validam um plan antes do apply?

  • ASentinel — framework de policy as code que avalia o plan e pode barrar o apply.
  • Bterraform validate — pois valida regras de negócio da empresa.
  • CO backend S3, que aplica políticas de bucket ao state.
  • DO lock file .terraform.lock.hcl.
Sentinel é o policy-as-code do TF Cloud/Enterprise, avaliado entre o plan e o apply. (B) validate só checa sintaxe/consistência da config, não políticas de governança; (C) o S3 guarda state, não aplica policy; (D) o lock file só fixa versões de provider.

clique
variable = entrada externa; local = valor calculado interno; data = consulta read-only à infra existente. Nenhum cria infra.
count × for_each — quando usar cada um?
clique
count (índice posicional) para 0/1 ou cópias idênticas; for_each (chave estável) para coleções nomeadas — evita reindexação ao remover do meio.
O que é um data source?
clique
Bloco read-only que consulta recursos existentes (ex.: AMI mais recente). NÃO cria nem destrói nada.
O que faz terraform import?
clique
Traz um recurso existente (criado fora) para o state, sem recriá-lo. Oposto de state rm.
state rm destrói o recurso real?
clique
Não. Remove apenas do state (Terraform "esquece"); o recurso na nuvem continua. Quem destrói é o destroy.
Para que servem os módulos?
clique
Empacotar e reutilizar infra (DRY). Têm source, version, inputs e outputs; root module chama child modules.
Sentinel no Terraform Cloud — o que é?
clique
Policy as code: regras avaliadas entre o plan e o apply para impor governança (ex.: barrar bucket público).

Véspera da provaPegadinhas & checklist final

🎯 Releia antes de entregar a prova
  • Terraform é declarativo (estado desejado) e idempotente; ele monta um DAG e infere a ordem.
  • Terraform × CloudFormation: ambos declarativos, mas Terraform é multi-cloud e CFN é só AWS.
  • Terraform × Ansible: Terraform provisiona infra com state; Ansible é configuration management procedural.
  • O tfstate mapeia config ↔ recursos reais e pode conter segredos — nunca commitar.
  • Remote backend habilita compartilhamento + state locking (S3 guarda; DynamoDB faz o lock).
  • Fluxo: init → plan → apply → destroy. O plan NÃO altera infra; o apply altera.
  • state rm remove do state (não destrói o recurso real); import faz o oposto.
  • Precedência: default < TF_VAR_ < tfvars < *.auto.tfvars < CLI (-var) — a CLI vence.
  • variable = entrada; local = calculado interno; data = consulta read-only; resource = gerenciado.
  • count = índice posicional (reindexa ao remover do meio); for_each = chave estável.
  • Módulos: source + version (fixar = reprodutibilidade) + inputs/outputs.
  • Dependência implícita (referência) é o normal; depends_on só quando não há referência.
  • Terraform Cloud: remote runs, VCS-driven, remote state e Sentinel (policy as code).
