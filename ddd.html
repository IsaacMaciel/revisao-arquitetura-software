Tópico 01 · Domain-Driven Design

Domain-Driven Design

DDD é uma abordagem para desenvolver software complexo que coloca o domínio do negócio no centro. Une um lado estratégico (como dividir o sistema e alinhar com o negócio) e um lado tático (como modelar o código). Esta página cobre o cânone (Evans/Vernon) e os tópicos de descoberta da sua ementa.

🎯 Como DDD costuma cair na prova

Em múltipla escolha, DDD aparece como: (1) definições trocadas entre conceitos próximos — Entidade × Value Object, Domain × Application Service; (2) classificação — "qual destes é um padrão de Context Mapping?"; (3) identificar o conceito a partir de um exemplo; (4) verdadeiro/falso sobre regras (ex.: "agregados podem referenciar outros agregados por ID — V ou F").

FundamentosO que é DDD

Formalizado por Eric Evans (2003, livro "azul") e expandido por Vaughn Vernon ("Implementing DDD", livro "vermelho"). A ideia central: o maior obstáculo em software complexo não é a tecnologia, é a complexidade do domínio. DDD ataca isso construindo um modelo compartilhado entre quem entende do negócio (domain experts) e quem programa.

Os dois lados do DDD

LadoPergunta que respondeFerramentas principais
EstratégicoComo dividir o sistema grande em partes e alinhá-las ao negócio?Domínio/subdomínios, Linguagem Ubíqua, Bounded Contexts, Context Mapping
TáticoComo modelar e implementar cada parte em código?Entidades, Value Objects, Aggregates, Domain Events, Repositories, Factories, Services
TL;DR
  • DDD = colocar o domínio no centro do design para domar a complexidade.
  • Estratégico = onde traçar fronteiras (bounded contexts). Tático = como modelar dentro de cada fronteira.
  • O coração de tudo é a colaboração com domain experts e uma linguagem comum.

EstratégicoDomínio & subdomínios

Domínio é a esfera de conhecimento e atividade do negócio (ex.: "comércio eletrônico", "gestão de patrimônio"). Como é grande demais para modelar de uma vez, divide-se em subdomínios. Há três tipos — e distingui-los cai em prova:

SubdomínioO que éEstratégiaExemplo (e-commerce)
Core (núcleo)A vantagem competitiva, o motivo do software existir. Onde está o diferencial.Investir o melhor time; modelar com cuidado máximo.Motor de recomendação / precificação
Supporting (suporte)Necessário ao negócio, mas não é diferencial. Específico do negócio.Construir de forma mais simples; pode ser terceirizado.Catálogo de produtos
Generic (genérico)Resolvido igual em qualquer empresa; sem diferencial.Comprar/usar pronto (off-the-shelf).Autenticação, envio de e-mail, pagamento
⚠ Pegadinha

O core domain NÃO é "o maior" nem "o mais complexo tecnicamente" — é o que dá vantagem competitiva. Genérico ≠ inútil: é só algo que não vale a pena construir do zero.

Questão

Uma fintech investe pesado no algoritmo de análise de crédito (seu diferencial) e usa um serviço pronto de terceiros para envio de SMS. Como classificamos esses dois?

  • AAmbos são core domains, pois o sistema depende dos dois.
  • BAnálise de crédito é supporting e SMS é core.
  • CAnálise de crédito é core domain e o envio de SMS é generic subdomain.
  • DAnálise de crédito é generic porque já existem bibliotecas de crédito.
O diferencial competitivo (análise de crédito) é o core domain — recebe o melhor esforço de modelagem. SMS é resolvido igual por qualquer empresa, logo é generic e deve ser comprado pronto.

EstratégicoLinguagem Ubíqua

A Linguagem Ubíqua (Ubiquitous Language) é um vocabulário comum, rigoroso e compartilhado entre desenvolvedores e domain experts, usado em toda parte: conversas, documentos, nomes de classes, métodos e tabelas. Se o negócio diz "apólice", o código tem Apolice — não Contrato2.

Características essenciais

  • Ubíqua = "em todo lugar": fala, texto e código usam os mesmos termos.
  • Viva: evolui junto com o entendimento do domínio; o modelo muda quando a linguagem muda.
  • Vinculada a um Bounded Context: a mesma palavra pode ter significados diferentes em contextos diferentes (ver Bounded Context).
  • Elimina tradução entre "linguagem do negócio" e "linguagem técnica" — a tradução é onde nascem os bugs de entendimento.
⚠ Pegadinha

Linguagem Ubíqua não é global. Ela é ubíqua dentro de um Bounded Context. "Cliente" no contexto de Vendas ≠ "Cliente" no contexto de Suporte. Alternativa de prova que diz "uma única linguagem para toda a empresa" geralmente está errada.

FundamentosModel-Driven Design

O modelo de domínio é uma abstração seletiva do conhecimento do negócio — não é o mundo real inteiro, só o que importa para resolver o problema. Model-Driven Design diz que o modelo e o código devem espelhar-se mutuamente: o código é a expressão do modelo. Se o modelo evolui, o código evolui; se o código fica difícil de mudar, o modelo provavelmente está errado.

✗ Anti-padrão: Anemic Domain Model

O Modelo de Domínio Anêmico é quando as classes de domínio só têm dados (getters/setters) e toda a lógica fica em "services". Martin Fowler chama de anti-padrão porque viola o encapsulamento e joga fora o valor do OO. No DDD, comportamento e regras de negócio vivem dentro das entidades/agregados. Aparece muito em prova como "qual é o anti-padrão?".

EstratégicoBounded Contexts

Um Bounded Context (Contexto Delimitado) é uma fronteira explícita dentro da qual um modelo de domínio específico — e sua linguagem ubíqua — são válidos e consistentes. É o padrão central do DDD estratégico.

Por que existe

Tentar um único modelo unificado para um sistema grande gera ambiguidade: o mesmo termo significa coisas diferentes para áreas diferentes. O Bounded Context resolve isso dando a cada área seu próprio modelo coerente, com fronteiras claras. Dentro da fronteira, a linguagem é precisa; fora dela, pode mudar.

Relação com microsserviços: um Bounded Context é um forte candidato a virar um microsserviço (limite de autonomia e dados). Mas são conceitos distintos — BC é sobre modelo/linguagem; microsserviço é sobre deploy/processo. Um não obriga o outro.

Questão

Qual afirmação descreve corretamente a relação entre Bounded Context e Linguagem Ubíqua?

  • AA Linguagem Ubíqua é única para toda a organização e os Bounded Contexts apenas a implementam.
  • BCada Bounded Context delimita a validade de uma Linguagem Ubíqua; o mesmo termo pode significar coisas diferentes em contextos distintos.
  • CBounded Context é um conceito tático e Linguagem Ubíqua é estratégico; não se relacionam.
  • DBounded Context é sinônimo de microsserviço.
A linguagem é ubíqua dentro da fronteira do contexto. "Cliente" em Vendas e em Faturamento podem ser modelos diferentes. (A) erra ao globalizar a linguagem; (D) confunde BC com microsserviço.

EstratégicoContext Mapping

O Context Map documenta como os Bounded Contexts se relacionam — técnica e organizacionalmente. Os padrões descrevem o tipo de relação e o equilíbrio de poder entre as equipes (upstream/downstream). Saber classificar esses padrões cai em prova.

PadrãoSignificado
PartnershipDois contextos/times com sucesso interdependente; coordenam-se de igual para igual.
Shared KernelDois times compartilham um subconjunto do modelo/código. Reduz duplicação, mas cria acoplamento — mudanças exigem acordo.
Customer / SupplierUpstream (fornecedor) e downstream (cliente). O downstream tem voz; o upstream atende às necessidades dele.
ConformistO downstream se submete ao modelo do upstream sem tradução (sem poder de negociação).
Anticorruption Layer (ACL)Camada de tradução que protege o modelo do downstream de um modelo externo/legado ruim. Padrão muito cobrado.
Open Host Service (OHS)O upstream expõe um protocolo/API aberto e bem definido para vários consumidores.
Published LanguageLinguagem de intercâmbio bem documentada e compartilhada (ex.: um schema, XML/JSON padronizado). Anda junto com OHS.
Separate WaysOs contextos não se integram — custo de integração não compensa. Seguem caminhos separados.
Big Ball of MudRegião sem fronteiras claras, modelos misturados. Reconhecê-la e isolá-la (com ACL) é a estratégia.
💡 Como lembrar upstream × downstream

Upstream = "rio acima" = o fornecedor, influencia o de baixo. Downstream = "rio abaixo" = o consumidor, sofre as mudanças. Conformist e ACL são as duas posturas possíveis do downstream: conformar-se ou se proteger.

Questão

Sua aplicação nova precisa integrar com um ERP legado cujo modelo de dados é confuso e você não quer "contaminar" seu domínio limpo. Qual padrão de Context Mapping você aplica?

  • AAnticorruption Layer (ACL)
  • BConformist
  • CShared Kernel
  • DSeparate Ways
A ACL traduz o modelo externo/legado para o seu modelo, isolando-o. Conformist seria o oposto (submeter-se ao legado); Shared Kernel aumentaria o acoplamento; Separate Ways não integraria.

Tático · clássico de provaEntidade × Value Object

Esta distinção é a mais cobrada de DDD tático. O critério é identidade.

AspectoEntidade (Entity)Value Object (VO)
IdentidadeTem identidade própria e contínua (um id). É "quem é".Não tem identidade; é definido só pelos seus atributos. É "o que vale".
IgualdadePor identidade — dois objetos com mesmo id são o mesmo, ainda que atributos mudem.Por valor — dois VOs com os mesmos atributos são iguais.
MutabilidadeMutável ao longo do tempo (estado evolui).Imutável — para mudar, cria-se um novo.
Ciclo de vidaRastreado; nasce, muda e morre.Descartável; usado e substituído.
ExemplosCliente, Pedido, ContaBancáriaDinheiro (valor+moeda), Endereço, CPF, Período de datas, Cor
⚠ Pegadinha

Se a igualdade entre dois objetos importa por quem eles são → Entidade. Se importa por o que eles contêm → Value Object. "Endereço" geralmente é VO; mas se o negócio precisa rastrear cada endereço individualmente (histórico, status próprio), pode virar Entidade. Depende do contexto — não há resposta absoluta fora do domínio.

Questão

Sobre Value Objects, assinale a alternativa CORRETA:

  • ASão comparados por identidade (id) e possuem ciclo de vida rastreado.
  • BDevem ser mutáveis para refletir mudanças de estado.
  • CSempre se tornam tabelas próprias com chave primária.
  • DSão definidos por seus atributos, comparados por valor e idealmente imutáveis.
VO = sem identidade, igualdade por valor, imutável. (A) e (C) descrevem Entidade; (B) contraria a imutabilidade característica do VO.

Tático · centralAggregates & Aggregate Root

Um Aggregate (Agregado) é um conjunto de objetos (entidades + VOs) tratado como uma unidade de consistência. Tem uma raiz — a Aggregate Root — que é a única porta de entrada: o mundo externo só fala com a raiz, nunca diretamente com os objetos internos.

Regras de ouro dos agregados (caem muito)

  • A raiz é a fronteira de consistência: invariantes (regras que devem ser sempre verdadeiras) são garantidas dentro do agregado, pela raiz.
  • Acesso só pela raiz: referências externas apontam para a Aggregate Root, não para objetos internos.
  • Referencie outros agregados por identidade (ID), não por objeto direto. Isso mantém os agregados pequenos e desacoplados.
  • Uma transação = um agregado: idealmente, cada transação modifica um único agregado. Consistência entre agregados é eventual (via Domain Events).
  • O Repository opera no nível do agregado (um repositório por Aggregate Root).

✗ Erro comum

Um código que carrega pedido.getCliente().getEndereco().setCep(...) atravessando agregados e modificando dois numa só transação viola as regras de agregado. O correto: cliente é outro agregado, referenciado por ID, modificado em sua própria transação.

Questão

Qual é a função principal de uma Aggregate Root?

  • AServir como classe base de todas as entidades do sistema.
  • BMapear diretamente cada tabela do banco de dados.
  • CSer o único ponto de acesso ao agregado e garantir suas invariantes/consistência.
  • DExpor livremente os objetos internos para manipulação externa.
A raiz é a fronteira de consistência e a única porta de entrada do agregado, protegendo as invariantes. (D) é justamente o oposto do que o padrão prega.

TáticoServices, Repositories & Factories

Domain Service × Application Service

Distinção que cai em prova. Ambos são "serviços", mas com responsabilidades diferentes:

Domain ServiceApplication Service
ContémLógica de negócio que não pertence naturalmente a uma entidade/VO específico.Orquestração: coordena, controla transação, chama o domínio. Sem regra de negócio.
CamadaCamada de domínio.Camada de aplicação.
ExemploTransferenciaService.transferir(contaA, contaB, valor) (regra envolve duas contas).RealizarPedidoUseCase: abre transação, busca no repo, chama o domínio, publica evento.

Repository

Abstrai a persistência, dando a ilusão de uma coleção em memória de agregados. Você pede "salve este Pedido" / "ache o Pedido X" sem saber se é SQL, NoSQL ou arquivo. Um repositório por Aggregate Root. Não confundir com DAO genérico — o repositório fala a linguagem do domínio.

Factory

Encapsula a criação de objetos/agregados complexos, garantindo que nasçam já em estado válido e consistente. Usa-se quando a construção tem regras demais para um construtor simples.

⚠ Distinção fina

Repository = recupera/persiste objetos que já existem. Factory = cria objetos novos. São complementares, não concorrentes.

TáticoDomain Events

Um Domain Event representa algo relevante que aconteceu no domínio, no passado. Nomeado no particípio: PedidoRealizado, PagamentoConfirmado. Permite desacoplar agregados e contextos: quando algo ocorre, um evento é publicado e outros reagem — base para consistência eventual e arquiteturas event-driven.

Mnemônico — building blocks táticos
"Eu Vi Agregar Dados Rápido, Faz Sentido"

ArquiteturaArquiteturas que abrigam o DDD

DDD não exige uma arquitetura específica, mas combina com aquelas que isolam o domínio de infraestrutura e UI. O princípio comum: a dependência aponta para dentro, em direção ao domínio (Dependency Inversion).

Arquitetura em Camadas (Layered)

Clássica: Apresentação → Aplicação → Domínio → Infraestrutura. Cada camada depende da de baixo. Simples, mas a forma ingênua deixa o domínio dependendo da infra.

Hexagonal (Ports & Adapters)

Alistair Cockburn. O domínio fica no centro e se comunica com o mundo por portas (interfaces); adaptadores implementam essas portas (banco, UI, APIs). O núcleo não conhece os detalhes externos — dá testabilidade e troca de tecnologia sem tocar no domínio.

Onion & Clean Architecture

Variações da mesma ideia (Jeffrey Palermo / Robert C. Martin): camadas concêntricas com o domínio no centro e a regra de dependência apontando sempre para dentro. Frameworks/UI/DB ficam na borda e são "detalhes".

Borda UI · Controllers · DB · Frameworks (detalhes)
Adaptadores / Interface Repositórios concretos · Gateways
Aplicação Use Cases · Application Services (orquestração)
Centro Domínio: Entidades · VOs · Aggregates · Domain Services
A dependência aponta de fora para dentro — o domínio não conhece a borda.
Questão

Na Arquitetura Hexagonal, o que são "portas" e "adaptadores"?

  • APortas são bancos de dados; adaptadores são telas de UI.
  • BPortas são interfaces definidas pelo domínio; adaptadores são as implementações que conectam o domínio ao mundo externo.
  • CPortas e adaptadores são sinônimos de camadas de apresentação.
  • DAdaptadores ficam no centro e as portas na borda externa.
O domínio define portas (interfaces); os adaptadores as implementam para falar com DB, UI, APIs. Isso isola o núcleo dos detalhes de tecnologia.

Descoberta · da sua ementaDomain Storytelling

Domain Storytelling (Stefan Hofer & Henning Schwentner) é uma técnica colaborativa de descoberta: domain experts narram histórias de como o trabalho acontece, e um facilitador as desenha em tempo real com uma notação pictográfica simples — atores, objetos de trabalho e atividades numeradas em sequência.

Elementos da notação

  • Atores (pessoas/sistemas que agem) — bonecos/ícones.
  • Objetos de trabalho (documentos, itens manipulados).
  • Atividades = setas numeradas mostrando a sequência da história.

Serve para construir a linguagem ubíqua, alinhar entendimento e revelar fronteiras de bounded contexts. É concreta (conta uma história específica), não abstrata.

Descoberta · da sua ementaEvent Storming

Event Storming (Alberto Brandolini) é um workshop colaborativo com post-its coloridos numa parede, partindo dos Domain Events (laranja, no passado) para explorar o domínio rapidamente. A cor de cada post-it tem significado fixo:

Cor (convenção)ElementoSignificado
🟧 LaranjaDomain EventAlgo que aconteceu (no passado). Ponto de partida.
🟦 AzulCommandAção/decisão que dispara um evento.
🟨 AmareloAggregateOnde os comandos batem e os eventos nascem.
🟪 LilásPolicyRegra "sempre que… então…" (reação a evento).
🟩 VerdeRead ModelInformação que um ator consulta para decidir.
🩷 RosaExternal SystemSistema externo envolvido.
🟥 VermelhoHot SpotDúvida, conflito ou problema a resolver.

Os três níveis de Event Storming

  1. Big Picture: visão ampla do negócio inteiro; descobre subdomínios e fronteiras.
  2. Process Level: aprofunda um processo específico (comandos, políticas, read models).
  3. Design Level: detalhe fino até os agregados — quase pronto para virar código.
⚠ Não confunda

Domain Storytelling = narrar histórias com atores/atividades numeradas (foco em fluxo de trabalho e linguagem). Event Storming = explorar via eventos em post-its coloridos numa parede (foco em descobrir o domínio por eventos). Ambos são técnicas de descoberta colaborativa, mas com notações e pontos de partida diferentes.

Questão

No Event Storming, qual elemento é o ponto de partida do workshop e é escrito no tempo passado?

  • ADomain Event (post-it laranja), ex.: "Pedido Confirmado".
  • BCommand (post-it azul), ex.: "Confirmar Pedido".
  • CAggregate (post-it amarelo).
  • DHot Spot (post-it vermelho).
Event Storming parte dos eventos de domínio (laranja, no passado) e a partir deles descobre comandos, agregados e políticas. Por isso o nome "Event" Storming.

Descoberta · da sua ementaLevantamento de requisitos · DoR · DoD

No fluxo ágil que costuma acompanhar DDD, dois critérios formalizam quando algo está pronto para entrar e para sair do desenvolvimento:

Definition of Ready (DoR)Definition of Done (DoD)
PerguntaEsta tarefa está pronta para começar?Esta tarefa está pronta para ser considerada concluída?
MomentoAntes de puxar para a sprint/dev.Depois do desenvolvimento, antes de entregar.
Exemplos de critériosHistória clara, critérios de aceite definidos, estimada, sem bloqueios, dependências conhecidas.Código revisado, testes passando, integrado, documentado, critérios de aceite atendidos, deployável.
FocoQualidade da entrada.Qualidade da saída.
💡 Como lembrar

Ready = portão de entrada (pronto pra começar). Done = portão de saída (pronto pra entregar). Pegadinha clássica: trocar as definições entre si, ou dizer que DoD é "definido pelo cliente" — na prática, a DoD é acordada pelo time e aplica-se a todos os itens.

Auto-testeFlashcards — clique para virar

Teste-se rápido. Pense na resposta antes de clicar.

O que distingue uma Entidade de um Value Object?
clique
A identidade. Entidade tem id próprio e contínuo (igualdade por identidade, mutável). VO é definido pelos atributos (igualdade por valor, imutável).
O que é uma Aggregate Root?
clique
A entidade que é a única porta de entrada do agregado e a fronteira de consistência — protege as invariantes. Acesso externo só por ela.
Core, Supporting e Generic subdomain — diferença?
clique
Core = diferencial competitivo (melhor esforço). Supporting = necessário mas não diferencial. Generic = comum a todos, comprar pronto.
O que é um Bounded Context?
clique
Fronteira explícita onde um modelo de domínio e sua Linguagem Ubíqua são válidos e consistentes. O mesmo termo pode diferir entre contextos.
Para que serve uma Anticorruption Layer (ACL)?
clique
Traduzir e isolar o modelo do seu contexto do modelo de um sistema externo/legado ruim, evitando "contaminação". Padrão de Context Mapping.
Domain Service × Application Service?
clique
Domain = lógica de negócio sem dono natural (camada domínio). Application = orquestração/transação, sem regra de negócio (camada de aplicação).
Qual é o anti-padrão "Anemic Domain Model"?
clique
Classes de domínio só com dados (getters/setters) e toda a lógica em services. Viola encapsulamento; Fowler o critica. No DDD, comportamento vive na entidade/agregado.
Event Storming × Domain Storytelling?
clique
Ambos são descoberta colaborativa. Event Storming: post-its coloridos a partir de eventos. Domain Storytelling: desenhar histórias com atores/atividades numeradas.
DoR × DoD?
clique
Ready = portão de entrada (pronto p/ começar: claro, estimado, sem bloqueio). Done = portão de saída (pronto p/ entregar: testado, revisado, integrado).
Regra de dependência (Hexagonal/Onion/Clean)?
clique
A dependência aponta para dentro, em direção ao domínio. UI/DB/frameworks são "detalhes" na borda; o domínio não os conhece (Dependency Inversion).

Véspera da provaPegadinhas & checklist final

🎯 Releia antes de entregar a prova
  • Core domain = vantagem competitiva, não "o maior/mais complexo".
  • Linguagem Ubíqua vale dentro de um bounded context, não para a empresa toda.
  • Bounded Context ≠ microsserviço (relacionados, não sinônimos).
  • Entidade = identidade; VO = valor/imutável.
  • Agregado: acesso só pela raiz; referencie outros agregados por ID; 1 transação ≈ 1 agregado.
  • Repository recupera/persiste; Factory cria.
  • Domain Service tem regra de negócio; Application Service só orquestra.
  • ACL protege/traduz; Conformist se submete.
