Tópico 06 · Microsserviços

Fundamentos & Comunicação

Microsserviços não são uma tecnologia — são um estilo arquitetural que decompõe uma aplicação em serviços pequenos, coesos e deployáveis de forma independente, cada um responsável por uma capacidade de negócio. A vantagem vem acompanhada de um custo real: complexidade de rede, dados distribuídos e novas classes de falha. Compreender quando usar e como os serviços se comunicam é o cerne desta revisão.

🎯 Como Microsserviços (fundamentos) cai na prova

Espere: (1) distinção monólito × microsserviços × SOA — conceitos trocados é a pegadinha clássica; (2) decomposição por business capability vs. bounded context (DDD) — diferença de critério; (3) comunicação síncrona × assíncrona e o impacto no acoplamento; (4) API Gateway × BFF — responsabilidades e quando usar cada um; (5) API Composition × CQRS para queries que cruzam serviços; (6) monólito distribuído como anti-padrão — pior dos dois mundos.

Aula 1Estratégias & Padrões de Microsserviços

Um microsserviço é um serviço pequeno, autônomo, com responsabilidade única e deployável de forma independente. A aplicação como um todo é composta pela colaboração desses serviços. Cada serviço possui seu próprio processo, sua própria base de dados (Database-per-Service) e se comunica via rede.

Por que microsserviços existem?

  • Escalabilidade independente: escale só o serviço que está sobrecarregado, não a aplicação inteira.
  • Deploy independente: equipes deployam sem coordenar com outras equipes.
  • Isolamento de falhas: a falha de um serviço não derruba o sistema inteiro (se bem projetado).
  • Liberdade tecnológica: cada serviço pode usar a tecnologia mais adequada à sua necessidade.
  • Times autônomos (Lei de Conway): a estrutura do sistema reflete a estrutura da organização.

O "Microservices Tax" — o custo real

  • Latência e falhas de rede entre serviços.
  • Consistência eventual em vez de transações ACID.
  • Complexidade operacional: observabilidade, service discovery, orquestração.
  • Overhead de desenvolvimento e teste de contratos entre serviços.
  • Dados distribuídos tornam queries simples em desafios complexos.
⚠ Quando NÃO usar microsserviços

Microsserviços não são a solução padrão. Evite quando: o time é pequeno e não tem maturidade operacional; o domínio ainda não está bem compreendido (mudanças frequentes de boundary custam caro); a aplicação é simples ou de baixo tráfego; a infraestrutura (CI/CD, observabilidade, service mesh) não está pronta. Comece com um monólito modular e migre se/quando a complexidade justificar.

⚠ Pegadinha: SOA ≠ Microsserviços

SOA usa um ESB como barramento central (lógica de roteamento, transformação e orquestração fica no barramento). Microsserviços seguem o princípio oposto: "smart endpoints, dumb pipes" — os serviços contêm a lógica, o transporte é burro. SOA tipicamente tem serviços de granularidade maior e banco compartilhado.

Questão 1

Qual das seguintes afirmações distingue corretamente SOA de microsserviços?

  • ASOA usa serviços pequenos e autônomos com database-per-service, enquanto microsserviços usam banco compartilhado e ESB central.
  • BSOA centraliza a lógica de integração no ESB ("smart pipe"), enquanto microsserviços colocam a lógica nos próprios serviços ("smart endpoints, dumb pipes").
  • CSOA e microsserviços são sinônimos: ambos promovem serviços independentes sem banco compartilhado.
  • DMicrosserviços exigem ESB para comunicação, enquanto SOA usa REST direto entre serviços.
A distinção central é o papel do barramento: SOA concentra orquestração/transformação no ESB; microsserviços são "dumb pipes" (Kafka, HTTP simples) com lógica nos endpoints. (A) inverte os atributos; (C) iguala os dois; (D) inverte os protocolos.

Questão 2

Ao decompor um sistema de e-commerce em microsserviços usando a estratégia de business capability, qual critério deve guiar os limites de cada serviço?

  • AO tamanho do código: cada serviço deve ter menos de 500 linhas.
  • BA tecnologia de persistência: serviços que usam o mesmo banco ficam juntos.
  • CA capacidade organizacional estável que o serviço entrega (ex.: Pedidos, Pagamentos, Catálogo).
  • DO bounded context derivado da linguagem ubíqua do domínio.
Business capability parte do o que a empresa faz — uma capacidade estável do negócio (Pedidos, Pagamentos, Inventário). (A) usa tamanho de código, que nunca foi o critério correto. (B) é anti-padrão (banco compartilhado acopla serviços). (D) é a estratégia DDD/bounded context, que é uma estratégia diferente (correta mas não a pedida).

Aula 1 · tamanhoTamanho de Serviço & Monólito Distribuído

Não existe uma métrica de linhas de código para "micro". O que importa é que o serviço seja coeso (responsabilidade única), deployável independentemente e compreensível por um time pequeno. Sam Newman sugere pensar em termos de bounded context e capacidade de ser mantido sem coordenar com outros times.

✗ Anti-padrão: Monólito Distribuído

O monólito distribuído ocorre quando você divide fisicamente a aplicação em "serviços" mas eles continuam fortemente acoplados — compartilham banco de dados, dependem de chamadas síncronas em cadeia, ou precisam ser deployados juntos. Você pega o pior dos dois mundos: a complexidade da rede de microsserviços sem a autonomia e escalabilidade independente. É o sinal mais comum de falha na adoção de microsserviços.

Mnemônico — critério de "micro" saudável
"Coeso · Autônomo · Deployável"
  • Coeso: responsabilidade única e modelo de dados próprio.
  • Autônomo: pode ser desenvolvido e alterado sem coordenar com outros serviços.
  • Deployável: pode ser colocado em produção independentemente dos demais.

Aula 2Comunicação entre Processos

Serviços se comunicam pela rede — o que traz falhas e latências inexistentes em chamadas em-processo. Há dois estilos fundamentais de interação (one-to-one e one-to-many) e dois modos de invocação (síncrona e assíncrona):

EstiloOne-to-OneOne-to-Many (Publish-Subscribe)
SíncronoREST / gRPC (request-response direto)— (não comum: broadcast síncrono é raro)
AssíncronoMessage Queue (ponto-a-ponto)Pub/Sub: tópicos (Kafka, RabbitMQ)

Protocolos de comunicação

  • REST (HTTP/JSON): amplamente adotado, human-readable, sem schema formal (mas OpenAPI compensa). Adequado para APIs públicas e integração heterogênea.
  • gRPC (HTTP/2 + Protocol Buffers): tipado, binário, eficiente. Ideal para comunicação interna de alta performance entre serviços. Suporta streaming bidirecional.
  • Mensageria (Kafka, RabbitMQ, SQS): desacoplamento temporal; o produtor não espera o consumidor. Suporta replay (Kafka) e roteamento complexo.

Aula 2 · comparaçãoSíncrona × Assíncrona — Acoplamento

CritérioComunicação SíncronaComunicação Assíncrona
DisponibilidadeAmbos precisam estar up ao mesmo tempoProdutor envia; consumidor processa quando disponível
Acoplamento temporalAlto — falha do downstream causa falha no upstreamBaixo — desacoplamento temporal via broker
Acoplamento de contratoAPI explícita (contrato forte entre cliente e servidor)Esquema de mensagem (contrato menos rígido em tempo de execução)
LatênciaResposta imediata (se o servidor responde)Eventual — o chamador não espera a resposta
ComplexidadeMais simples de implementar e depurarMais complexo: ordering, idempotência, dead-letter queues
Quando usarLeituras, operações que precisam de resposta imediataEscrita, eventos de domínio, workloads de longa duração
⚠ Pegadinha: request-response ≠ sempre síncrono

É possível implementar request-response assíncrono: o cliente envia uma mensagem a uma fila, inclui um reply-to channel, e aguarda a resposta em outro canal. O padrão é assíncrono no transporte mas simula semântica de chamada. Não confunda o padrão de interação (request-response vs. event) com o mecanismo (HTTP vs. mensageria).

Questão 3

Um time está projetando um fluxo de "processar pagamento" em microsserviços. O serviço de Pedidos chama o serviço de Pagamentos via REST e aguarda a confirmação antes de prosseguir. Qual é o principal risco desta abordagem?

  • AO serviço de Pagamentos não conseguirá escalar independentemente.
  • BREST não é suportado para comunicação interna entre microsserviços.
  • CO serviço de Pedidos precisará compartilhar banco de dados com Pagamentos.
  • DAlto acoplamento temporal: se o serviço de Pagamentos estiver indisponível, o serviço de Pedidos também falha.
Comunicação síncrona cria acoplamento temporal — a disponibilidade do Pedidos depende diretamente da disponibilidade do Pagamentos. Se Pagamentos sair, Pedidos falha junto. (A) está errado: escalabilidade independente não é impedida por REST. (B) é falso: REST é o protocolo mais comum. (C) não tem relação com o protocolo de comunicação.

Aula 2 · garantiasIdempotência & Garantias de Entrega

Em sistemas distribuídos, a rede pode duplicar ou perder mensagens. A estratégia correta depende da garantia de entrega que o broker oferece:

Garantias de entrega

  • At-most-once (no máximo uma vez): pode perder mensagens; nunca duplica. Adequado para métricas não críticas.
  • At-least-once (pelo menos uma vez): nunca perde; pode duplicar. O consumidor deve ser idempotente. É o padrão mais comum em sistemas de negócio.
  • Exactly-once (exatamente uma vez): sem perda e sem duplicata. Muito caro de implementar; só Kafka (com transactions) e poucos brokers suportam de forma nativa. Prefira at-least-once + idempotência.
⚠ Idempotência não é opcional com at-least-once

Se o broker garante at-least-once, o consumidor deve ser idempotente — processar a mesma mensagem duas vezes deve produzir o mesmo resultado que processá-la uma vez. Técnicas: chave de idempotência, verificar se o evento já foi processado antes de agir, ou usar operações naturalmente idempotentes (atualizar com valor absoluto, não incremento).

Aula 3API Gateway

O API Gateway é o ponto de entrada único (single entry point) para os clientes externos. Sem ele, clientes precisariam conhecer e chamar cada microsserviço individualmente — o que expõe detalhes internos, multiplica chamadas de rede e dificulta cross-cutting concerns.

API Gateway roteia, agrega e aplica cross-cutting concerns antes de encaminhar para os microsserviços downstream.

Responsabilidades do API Gateway

  • Roteamento de requisições: encaminha cada request para o serviço correto com base em path, método ou header.
  • Composição/Agregação: une respostas de múltiplos serviços em uma única resposta para o cliente (evita N round-trips).
  • Autenticação & Autorização: valida tokens (JWT, OAuth2) antes de encaminhar.
  • Rate limiting & Throttling: protege os serviços downstream de sobrecargas.
  • SSL termination: encerra TLS no gateway; comunicação interna pode ser mais simples.
  • Logging, tracing & monitoring: ponto centralizado para observabilidade.
  • Transformação de protocolo: ex.: REST externo → gRPC interno.
⚠ API Gateway pode virar gargalo e God Object

Se o API Gateway começa a conter lógica de negócio (regras de validação, cálculos), torna-se um gargalo e um ponto único de falha sofisticado. Ele deve conter cross-cutting concerns, não regras de domínio. Um gateway monolítico que orquestra tudo reproduz o problema do ESB do SOA.

Aula 3 · BFFBFF — Backend for Frontend

O padrão Backend for Frontend (BFF) — cunhado por Sam Newman — resolve um problema do API Gateway genérico: clientes diferentes (web, mobile, third-party) têm necessidades distintas de dados e formatos. Um único gateway genérico precisa servir todos, e o resultado são compromissos ruins para todos.

CritérioAPI Gateway genéricoBFF (por tipo de cliente)
InstânciasUma única para todos os clientesUma por tipo de cliente (Web BFF, Mobile BFF, Public API BFF)
ResponsabilidadeRoteamento + cross-cutting (genérico)Adaptação de dados + composição para aquele cliente específico
EvoluçãoQualquer mudança afeta todos os clientesCada BFF evolui com o time/cliente que o consome
Autonomia do timeBaixa — time centralizado gerencia o gatewayAlta — time do cliente controla seu BFF
OverheadMenor (uma instância)Maior (N instâncias + manutenção por time)
Quando usarQuando os clientes têm necessidades similaresQuando há clientes com formatos/dados muito distintos
💡 BFF não substitui o API Gateway — geralmente coexistem

É comum ter um API Gateway na borda (TLS, autenticação, rate limiting) com BFFs atrás dele. O Gateway trata os cross-cutting concerns globais; cada BFF adapta os dados para o seu tipo de cliente antes de compor a resposta.

Questão 4

Uma empresa tem um aplicativo mobile iOS e uma SPA web com necessidades de dados muito diferentes. O time de mobile precisa de endpoints otimizados para baixo consumo de dados, enquanto o web precisa de agregações mais ricas. Qual padrão é mais adequado?

  • ABFF (Backend for Frontend): um BFF para mobile e outro para web, cada um adaptado para o seu cliente.
  • BAPI Gateway genérico: um único ponto de entrada que serve todos os clientes com o mesmo contrato.
  • COs clientes chamam os microsserviços diretamente, sem gateway.
  • DGraphQL Federation no lugar de API Gateway ou BFF.
BFF é a resposta canônica quando clientes têm necessidades muito diferentes. (B) resultaria num gateway "engordado" com lógica de adaptação para todos os clientes, acoplando a evolução de mobile e web. (C) expõe os serviços internos e multiplica round-trips. (D) é uma alternativa válida em alguns contextos, mas não é o padrão canônico da questão.
Questão 5

Qual das seguintes responsabilidades NÃO pertence ao API Gateway e sim a uma camada de negócio downstream?

  • AValidação de token JWT e autenticação do cliente.
  • BRate limiting e throttling por cliente.
  • CCalcular o desconto de um pedido com base nas regras de fidelidade do cliente.
  • DRoteamento do request para o microsserviço correto baseado no path.
Calcular desconto de fidelidade é regra de negócio — pertence ao microsserviço de Pedidos ou Promoções, nunca ao gateway. (A), (B) e (D) são cross-cutting concerns legítimos do API Gateway.

Aula 4Modelo de API para Microsserviços

A API é o contrato público de um microsserviço. Uma vez publicada, qualquer quebra de contrato quebra os consumidores. A gestão de contratos é um problema central em sistemas distribuídos.

Versionamento de API

  • Versionamento na URL (/v1/orders, /v2/orders): simples e visível, mas proliferação de versões pode ser custosa.
  • Versionamento por header (Accept: application/vnd.uxwp.v2+json): mais RESTful, mas menos descoberto por clientes.
  • Evolução compatível (non-breaking changes): adicionar campos opcionais, novos endpoints — compatível com versões anteriores sem versão nova.
  • Breaking changes exigem: nova versão + período de coexistência + deprecação da versão antiga.

Consumer-Driven Contracts (CDC)

Em vez do produtor definir a API e os consumidores se adaptarem, o padrão Consumer-Driven Contracts (Pact, Spring Cloud Contract) inverte: cada consumidor especifica o que precisa da API; o produtor garante que satisfaz todos os contratos. Detecta breaking changes automaticamente no CI.

  • Consumidor escreve um contract (que request faz e o que espera receber).
  • Produtor roda os contratos de todos os consumidores como testes.
  • Se o produtor quebra o contrato de qualquer consumidor, o build falha.
⚠ OpenAPI descreve, CDC garante

OpenAPI/Swagger documenta a API — é um contrato de documentação. Consumer-Driven Contracts garantem compatibilidade em tempo de CI — é um contrato de comportamento executável. São complementares, não substitutos.

Aula 5Implementando Queries

Em um monólito, uma query pode fazer JOIN entre tabelas de qualquer módulo. Em microsserviços, cada serviço tem seu próprio banco — joins distribuídos via SQL são proibidos. Como, então, exibir dados que cruzam serviços?

✗ Anti-padrão: Banco Compartilhado para fazer JOIN

Dar acesso de múltiplos serviços ao mesmo banco para permitir JOINs quebra o isolamento do Database-per-Service. Você volta ao problema do monólito: mudanças de schema de um serviço afetam todos os outros que leem aquele banco.

Aqui, o ponto essencial é entender por que ele existe: queries que cruzam serviços não podem usar JOIN de banco — CQRS mantém um read model separado atualizado por eventos.

Questão 6

Um relatório precisa combinar dados de Pedidos, Clientes e Inventário em tempo real. Usando microsserviços com database-per-service, qual abordagem de query está sendo usada se o sistema chama os três serviços separadamente e une as respostas na camada de aplicação?

  • ACQRS — o sistema mantém um read model separado para consultas complexas.
  • BAPI Composition — chama múltiplos serviços e une os resultados em memória.
  • CEvent Sourcing — reconstrói o estado a partir do log de eventos.
  • DShared Database — os serviços compartilham o banco para permitir o JOIN.
Chamar N serviços e unir as respostas na camada de aplicação é exatamente API Composition. (A) seria CQRS se houvesse um read model pré-construído por eventos. (C) Event Sourcing trata de persistência, não de query federation. (D) é o anti-padrão a ser evitado.
Questão 7

Uma empresa tem um microsserviço de Pedidos e outro de Clientes, cada um com seu banco. O time precisa de uma tela de dashboard que liste pedidos com nome do cliente e status em tempo real, com filtros e paginação eficiente. API Composition não é suficiente. Qual estratégia resolve?

  • ACriar uma tabela compartilhada entre os dois bancos para o dashboard.
  • BFazer o serviço de Pedidos consumir diretamente o banco do serviço de Clientes.
  • CUsar API Composition com paginação manual na camada de aplicação.
  • DCQRS: manter um read model dedicado para o dashboard, alimentado por eventos dos dois serviços.
Quando API Composition não é suficiente (paginação, filtros complexos, performance), CQRS é a resposta: um read model denormalized, alimentado por eventos, otimizado para as queries do dashboard. (A) e (B) violam o isolamento de Database-per-Service. (C) API Composition com paginação manual é ineficiente e problemático para grandes volumes.

Barramento central do SOA que orquestra, transforma e roteia mensagens entre serviços.
Business Capability
Capacidade organizacional estável (o que a empresa faz) usada como critério de decomposição de serviços.
Bounded Context
Fronteira de DDD onde um modelo de domínio e sua linguagem ubíqua são válidos; critério DDD de decomposição de serviços.
Acoplamento Temporal
Dependência de disponibilidade simultânea entre serviços, causada pela comunicação síncrona.
At-least-once delivery
Garantia de entrega de mensagem: nunca perde, mas pode duplicar. Exige consumidores idempotentes.
Idempotência
Propriedade de uma operação que produz o mesmo resultado independentemente de quantas vezes é executada.
API Gateway
Ponto de entrada único para clientes externos; lida com roteamento, cross-cutting concerns (auth, rate limit, logging).
BFF (Backend for Frontend)
Variação do API Gateway: um backend dedicado por tipo de cliente, que adapta e compõe dados para aquele cliente específico.
Consumer-Driven Contract
Padrão onde o consumidor define o contrato que o produtor deve satisfazer; detecta breaking changes no CI.
API Composition
Padrão de query que chama múltiplos serviços e une as respostas em memória para montar o resultado final.
CQRS (Command Query Responsibility Segregation)
Padrão que separa os modelos de escrita (commands) e leitura (queries) em stores distintos, alimentando o read model por eventos.

Véspera da provaPegadinhas & checklist final

🎯 Releia antes de entregar a prova
  • Monólito distribuído = serviços separados mas acoplados — é anti-padrão, não um estilo válido.
  • SOA vs. Microsserviços: SOA tem ESB ("smart pipe"); microsserviços têm "smart endpoints, dumb pipes". Não são sinônimos.
  • Business capability (o que a empresa faz) ≠ bounded context (fronteira de modelo/linguagem do DDD) — são dois critérios distintos de decomposição.
  • Síncrono = acoplamento temporal alto; assíncrono = desacoplamento temporal via broker.
  • API Gateway faz cross-cutting concerns; BFF faz adaptação específica por tipo de cliente. Podem coexistir na mesma arquitetura.
  • API Gateway não deve conter lógica de negócio — senão vira ESB disfarçado.
  • at-least-once = pode duplicar; consumidor deve ser idempotente.
  • API Composition = une respostas em memória (simples, consistência forte, mas ineficiente para volumes grandes).
  • CQRS = read model separado, alimentado por eventos (consistência eventual, alta performance para queries complexas). Detalhado no Tópico 07.
  • Banco compartilhado entre serviços para fazer JOIN é anti-padrão — viola Database-per-Service.
  • OpenAPI documenta; Consumer-Driven Contract valida no CI — são complementares.
  • gRPC = binário, tipado, eficiente; REST = textual (JSON), human-readable, mais fácil para APIs públicas.
