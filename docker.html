Tópico 04 · Docker

Docker & Containerização

Container é um processo isolado do host que compartilha o kernel do sistema operacional — não uma máquina virtual. Docker empacota a aplicação e suas dependências numa imagem imutável que roda igual em qualquer lugar ("build once, run anywhere"), resolvendo o clássico "funciona na minha máquina". Da imagem ao cluster gerenciado: Dockerfile → imagem → container → orquestração → ECS.

🎯 Como Docker cai na prova

Espere: (1) container × VM — kernel compartilhado vs hypervisor/SO convidado (quase certo); (2) imagem × container — molde imutável vs instância em execução; (3) CMD × ENTRYPOINT e o papel das instruções do Dockerfile; (4) volume × bind mount; (5) Compose × Swarm × Kubernetes e os objetos do K8s (pod, deployment, service); (6) multi-stage build e boas práticas (não rodar como root, evitar latest, ordem das camadas); (7) ECS: task definition × task × service e Fargate × EC2.

FundamentosO que é Docker

Docker é uma plataforma de containerização: empacota código, runtime, bibliotecas e configurações numa única unidade portável — a imagem — que executa como um container, um processo isolado do restante do sistema. O isolamento é uma feature do kernel Linux, não uma virtualização de hardware.

Os dois pilares do isolamento (kernel Linux)

  • Namespaces — o que o processo enxerga. Isolam visão de PIDs, rede, montagens, usuários, hostname. Cada container "acha" que tem seu próprio SO.
  • cgroups (control groups) — o que o processo pode usar. Limitam e medem CPU, memória, I/O por container.
  • Union filesystem (overlay) — empilha camadas read-only da imagem + uma camada gravável do container.
TL;DR
  • Container = processo isolado que compartilha o kernel do host.
  • Isolamento vem de namespaces (visão) + cgroups (limites de recurso).
  • Imagem é o molde imutável; container é a instância em execução.

Distinção centralContainer × Máquina Virtual

É a distinção mais cobrada. A diferença fundamental: a VM virtualiza o hardware e carrega um SO convidado completo sobre um hypervisor; o container virtualiza o SO e compartilha o kernel do host, sem SO convidado.

⚠ Pegadinha

"Cada container tem seu próprio sistema operacional" é falso. O container compartilha o kernel do host; o que ele tem de próprio é o userland (bibliotecas, binários) da imagem. Quem carrega um SO convidado completo com kernel próprio é a VM. Por isso containers Linux precisam de um kernel Linux (no Windows/macOS, o Docker roda uma VM Linux leve por baixo).

Questão

Qual é a diferença fundamental entre um container e uma máquina virtual?

  • AContainers usam mais memória e bootam mais devagar que VMs.
  • BCada container roda seu próprio sistema operacional convidado sobre um hypervisor.
  • CContainers compartilham o kernel do SO host (virtualizam o SO); VMs virtualizam o hardware e carregam um SO convidado completo.
  • DNão há diferença técnica; "container" é apenas o nome moderno para VM.
Container = virtualização no nível do SO, kernel compartilhado, leve e rápido. (A) inverte os fatos (containers são mais leves/rápidos). (B) descreve a VM (hypervisor + SO convidado). (D) confunde dois conceitos distintos.

Distinção centralImagem × Container

Outra troca clássica de prova. A imagem é um artefato imutável e estático (um molde, empacotado em camadas); o container é uma instância em execução daquela imagem, com uma camada gravável própria por cima.

💡 Analogia que ajuda na prova

Imagem está para container assim como classe está para objeto (ou receita para prato): de uma imagem você cria vários containers independentes. docker run = instanciar a imagem.

ArquiteturaEngine: daemon, CLI e API

O Docker Engine é cliente-servidor. A arquitetura é mais cobrada na forma de "quem faz o quê":

  • Docker daemon (dockerd) — processo servidor de longa duração que constrói imagens, executa e gerencia containers, redes e volumes.
  • Docker CLI (docker) — cliente de linha de comando que envia ordens ao daemon pela REST API.
  • Registry — repositório de imagens (Docker Hub, Amazon ECR). push envia, pull baixa.

GerênciaImagens, camadas & cache

Uma imagem é uma pilha de camadas (layers) read-only, uma por instrução do Dockerfile que altera o filesystem. As camadas são empilhadas por um union filesystem; o container adiciona no topo uma fina camada gravável (copy-on-write). Camadas são compartilhadas e cacheadas entre imagens — economizam disco e aceleram o build.

Camada gravável (container) mudanças em runtime — efêmeras, somem com o rm
Layer · CMD/COPY app read-only — código da aplicação
Layer · RUN deps read-only — dependências instaladas
Layer · FROM base read-only — imagem base (ex.: node:18-alpine)
Imagem = camadas read-only (compartilháveis/cacheáveis). Só a camada gravável do topo é por-container e some no rm.
⚠ Pegadinha — cache invalida em cascata

Quando uma camada muda, todas as camadas seguintes são reconstruídas (o cache invalida em cascata). Por isso copie o package.json e instale dependências antes de copiar o código-fonte: o código muda toda hora, as dependências não. Inverter a ordem joga fora o cache do npm install a cada build.

⚠ Pegadinha — EXPOSE não publica porta

EXPOSE 8080 é documentação/metadado: não abre nem mapeia porta nenhuma. Para realmente publicar é preciso docker run -p 8080:8080 (host:container). Trocar EXPOSE por "publica a porta para o host" é alternativa errada típica.

Distinção centralCMD × ENTRYPOINT

Confusão garantida em prova. Ambas dizem o que roda no start, mas com papéis distintos:

CritérioCMDENTRYPOINT
PapelComando/argumentos padrão (default).O executável fixo do container.
Argumentos no runSubstituem totalmente o CMD.São anexados como argumentos ao ENTRYPOINT.

💡 Combinando os dois

O padrão idiomático é ENTRYPOINT = o executável fixo e CMD = os argumentos default. Ex.: ENTRYPOINT ["python","app.py"] + CMD ["--port","8080"]. Rodar docker run img --port 9000 troca só os argumentos (CMD), mantendo o executável.

Questão

Um Dockerfile tem ENTRYPOINT ["python","app.py"] e CMD ["--debug"]. O que acontece ao rodar docker run minha-img --port 9000?

  • AO comando vira --port 9000 e o ENTRYPOINT é ignorado.
  • BExecuta python app.py --port 9000: o argumento do run substitui o CMD e é anexado ao ENTRYPOINT.
  • CExecuta python app.py --debug --port 9000, somando CMD e o argumento.
  • DDá erro: não se pode passar argumentos quando há ENTRYPOINT.
Argumentos do run substituem o CMD e são anexados ao ENTRYPOINT. (A) ignora o ENTRYPOINT, que é fixo. (C) erra ao somar (o --debug foi substituído). (D) é falso — passar argumentos é o uso normal do ENTRYPOINT.

GerênciaVolumes × Bind Mounts

A camada gravável do container é efêmera — some com o rm. Para persistir ou compartilhar dados há dois mecanismos, comparados em prova:

CritérioVolumeBind Mount
Onde ficaEm área gerenciada pelo Docker (/var/lib/docker/volumes).Em um caminho qualquer do host escolhido por você.
GerênciaPelo Docker (docker volume create/ls/rm).Pelo sistema de arquivos do host.
PortabilidadeAlta — desacoplado da estrutura do host.Baixa — depende do layout do host.
Uso recomendadoProdução: dados de banco, persistência durável.Desenvolvimento: montar o código-fonte para hot-reload.
⚠ Pegadinha

Dados gravados dentro do container (sem volume/mount) não persistem: vão para a camada gravável efêmera e somem ao remover o container. Para dados duráveis em produção, a recomendação é volume (gerenciado pelo Docker), não bind mount.

Questão

Você precisa que os dados de um PostgreSQL em container sobrevivam à recriação do container, em produção. Qual a abordagem recomendada?

  • AUsar um volume gerenciado pelo Docker, montado no diretório de dados do banco.
  • BGravar tudo no filesystem do container; o Docker persiste automaticamente.
  • CUsar um bind mount apontando para um caminho do host — é a opção mais portável para produção.
  • DAumentar o tamanho da imagem para caber os dados.
Volume é o mecanismo de persistência recomendado e portável para produção. (B) é falso — a camada do container é efêmera. (C) inverte: bind mount é menos portável (acoplado ao host), indicado para desenvolvimento. (D) confunde imagem (read-only) com dados de runtime.

GerênciaRedes, portas & registries

  • Redes: drivers bridge (padrão, containers no mesmo host se enxergam por nome), host (usa a pilha de rede do host) e none (sem rede). Em uma rede definida pelo usuário, containers resolvem uns aos outros por nome de serviço (DNS interno).
  • Portas: -p host:container publica a porta. EXPOSE apenas documenta.
  • Registries: imagens vivem em um registry (Docker Hub público, ou privado como Amazon ECR). docker push/pull sincronizam. Tags identificam versões (app:1.2.0).

OrquestraçãoPor que orquestrar

Rodar um container é fácil; rodar centenas em vários hosts exige um orquestrador. Ele cuida de: scheduling (onde rodar), scaling (subir/descer réplicas), self-healing (recriar containers mortos), service discovery e load balancing, rolling updates/rollback e gestão de configuração/secrets.

Distinção centralCompose × Swarm × Kubernetes

Os três são confundidos. O eixo de distinção é escopo: Compose orquestra em um host (dev); Swarm e Kubernetes orquestram um cluster (multi-host, produção).

FerramentaEscopoPara que serveQuando usar
Docker ComposeUm único host.Definir e subir múltiplos containers juntos via um docker-compose.yml.Desenvolvimento local e ambientes simples.
Docker SwarmCluster (multi-host).Orquestrador nativo do Docker, simples de configurar.Clusters pequenos/médios, quando a simplicidade vale mais que recursos.
Kubernetes (K8s)Cluster (multi-host).Orquestrador padrão de mercado: rico, extensível, complexo.Produção em escala, com auto-scaling, self-healing avançado, ecossistema.
⚠ Pegadinha — Compose não é orquestrador de cluster

Docker Compose ≠ Kubernetes. Compose é uma ferramenta para definir e rodar multi-container em um host (foco em dev), sem clustering, self-healing ou scaling multi-nó. Quem orquestra cluster é o Swarm ou o Kubernetes. Atribuir auto-scaling de cluster ao Compose é erro clássico.

Questão

Qual afirmação distingue corretamente Docker Compose de Kubernetes?

  • AAmbos são orquestradores de cluster equivalentes; a escolha é só de sintaxe.
  • BCompose faz auto-scaling e self-healing em vários nós; Kubernetes só roda em um host.
  • CKubernetes serve apenas para desenvolvimento local; Compose é para produção em escala.
  • DCompose define/sobe múltiplos containers em um único host (foco em dev); Kubernetes orquestra containers em um cluster multi-host com scaling e self-healing.
O eixo é escopo: Compose = um host; K8s = cluster. (A) os iguala indevidamente. (B) e (C) invertem completamente os papéis das duas ferramentas.

OrquestraçãoConceitos de Kubernetes

Mesmo em prova de Docker, os objetos básicos do K8s costumam aparecer:

ObjetoÉ
PodA menor unidade deployável: um ou mais containers que compartilham rede e armazenamento. (No K8s você não roda containers soltos, mas pods.)
ReplicaSetMantém um número-alvo de réplicas de um pod sempre rodando (self-healing).
DeploymentGerencia ReplicaSets de forma declarativa; faz rolling update e rollback.
ServiceEndpoint de rede estável (IP/DNS) que faz load balancing entre os pods, que são efêmeros.
💡 Por que existe o Service

Pods nascem e morrem (e mudam de IP). O Service dá um nome/IP fixo e distribui o tráfego entre as réplicas atuais — desacoplando quem chama de quantos e quais pods existem no momento.

PráticaMelhores práticas de imagem

Imagens pequenas, rápidas e limpas

  • Imagem base mínima: prefira alpine, slim ou distroless — menos peso e menor superfície de ataque.
  • .dockerignore: evite enviar node_modules, .git, segredos e lixo ao contexto de build (build mais rápido e seguro).
  • Um processo por container: cada container faz uma coisa (web, db, cache em containers separados). Facilita escalar e observar.
  • Tags explícitas, não latest: fixe versões (app:1.4.2) para builds reproduzíveis.
  • Ordem das instruções: o que muda pouco (deps) vem antes do que muda muito (código), para aproveitar o cache de layers.
  • Multi-stage build: separe o ambiente de build do artefato final.
Mnemônico — imagem enxuta
"Base mínima · Ignore (.dockerignore) · Ordem do cache · Multi-stage" → BIOM
  • Os quatro movimentos que mais reduzem tamanho, tempo de build e superfície de ataque.
✗ Anti-prática — usar latest em produção

Depender da tag latest em produção quebra a reprodutibilidade: dois deploys do "mesmo" latest podem puxar imagens diferentes, e o rollback fica impreciso. Fixe sempre uma versão imutável (ou um digest @sha256:...).

PráticaMulti-stage build

O multi-stage build usa vários FROM no mesmo Dockerfile: um stage de build (com compiladores, SDKs, dependências de dev) gera o artefato; o stage final, partindo de uma base mínima, copia só o artefato e descarta todo o peso de build. Resultado: imagem final pequena e sem ferramentas de compilação.

dockerfile
# --- Stage 1: build (pesado, descartado) ---
FROM node:18-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci                 # deps antes do código → cache
COPY . .
RUN npm run build          # gera /app/dist

# --- Stage 2: imagem final (mínima) ---
FROM node:18-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
RUN addgroup -S app && adduser -S app -G app
USER app                   # não roda como root
EXPOSE 3000
CMD ["node", "dist/server.js"]
💡 O ganho do multi-stage

Compiladores, devDependencies e arquivos intermediários ficam só no stage de build e nunca entram na imagem final. Você ganha tamanho menor, build mais limpo e menos superfície de ataque — sem precisar de scripts manuais de limpeza.

Questão

Qual é o principal benefício de um multi-stage build?

  • APermite rodar vários containers a partir de um único Dockerfile, em paralelo.
  • BSubstitui a necessidade de um registry para distribuir a imagem.
  • CSepara o ambiente de build do artefato final, copiando só o necessário para uma imagem final pequena e sem ferramentas de compilação.
  • DFaz o container compartilhar o kernel do host de forma mais eficiente.
Multi-stage isola o build (pesado) da imagem final (mínima), reduzindo tamanho e superfície de ataque. (A) confunde com orquestração. (B) registry é outro assunto. (D) o compartilhamento de kernel é inerente a todo container, não vem do multi-stage.

PráticaSolução de problemas

O trio de debug

  • docker logs <container> — primeira parada: vê o stdout/stderr do processo principal. Use -f para acompanhar ao vivo.
  • docker exec -it <container> sh — abre um shell dentro do container em execução para inspecionar o ambiente.
  • docker inspect <container|imagem> — metadados em JSON: rede, montagens, variáveis, config — para entender como foi criado.
💡 Container que sobe e morre

Se o container sai imediatamente, lembre: ele vive enquanto o processo principal (PID 1) viver. App que roda em background, ou comando que termina, derruba o container. Olhe os logs e cheque o CMD/ENTRYPOINT.

SegurançaSegurança de contêineres

Como o container compartilha o kernel, descuidos têm impacto direto no host. Princípios cobrados:

Defesa em profundidade

  • Não rodar como root — defina um USER não privilegiado. Container root + escape = host comprometido (least privilege).
  • Base mínima / distroless — menos pacotes = menor superfície de ataque e menos CVEs.
  • Scan de vulnerabilidades — analise imagens (Trivy, Snyk, ECR scan) no pipeline.
  • Secrets fora da imagem — nunca embuta senha/token via ENV ou COPY; eles ficam nas camadas. Use secret manager / variáveis injetadas em runtime.
  • Imagens confiáveis / assinadas — use fontes oficiais e verificação de assinatura (Docker Content Trust / cosign).
✗ Anti-prática — rodar como root e enfiar secrets na imagem

Rodar o processo como root dá ao processo privilégios totais dentro do container (e risco ao host num escape). E embutir senha/token via ENV ou COPY grava o segredo numa camada da imagem — qualquer um com a imagem extrai. Use USER não-root e injete secrets em runtime.

Questão

Qual é a melhor forma de fornecer uma senha de banco a um container, do ponto de vista de segurança?

  • ADefinir ENV DB_PASS=... no Dockerfile para a senha viajar junto com a imagem.
  • BInjetar o segredo em runtime (secret manager / variável passada no deploy), mantendo-o fora das camadas da imagem.
  • CCOPY senha.txt para dentro da imagem e ler o arquivo no app.
  • DRodar o container como root para ter permissão de acessar a senha.
Segredos devem ficar fora da imagem e ser injetados em runtime. (A) e (C) gravam o segredo numa camada — extraível por quem tiver a imagem. (D) é irrelevante para o problema e ainda viola o least privilege.

Nuvem · AWSElastic Container Service (ECS)

O ECS é o orquestrador de containers gerenciado da AWS. Hierarquia de objetos (memorize a ordem):

Task Definition
o "molde" (imagem, CPU, mem, portas)
→ instancia →
Task
execução de 1+ container
← mantém N ←
Service
N tasks + LB + self-heal
↳ roda em ↳
Cluster
capacidade (Fargate/EC2)
Task Definition é o molde (≈ Dockerfile do ECS); a Task é a instância; o Service mantém N tasks rodando.
  • Cluster — agrupamento lógico de capacidade de computação onde as tasks rodam.
  • Task Definition — blueprint: qual imagem, CPU/memória, portas, variáveis, role. É o "molde".
  • Task — uma instância em execução de uma task definition (um ou mais containers juntos).
  • Service — mantém um número desejado de tasks no ar, com load balancer e self-healing (≈ Deployment do K8s).
  • ECR — Elastic Container Registry: onde o ECS puxa as imagens (o "Docker Hub privado" da AWS).

Fargate × EC2 launch type

O launch type decide quem provê e gerencia os servidores onde as tasks rodam:

CritérioFargateEC2
ModeloServerless: a AWS provê e gerencia a infra.Você gerencia as instâncias EC2 do cluster.
Responsabilidade do SO/patchDa AWS — você não vê o servidor.Sua — patch, scaling e capacidade das instâncias.
CobrançaPor vCPU/memória da task enquanto roda.Pelas instâncias EC2 provisionadas (rodando ou não).
ControleMenos controle, menos operação.Controle total (GPU, tipos específicos, daemons no host).
Quando usarSimplicidade, cargas variáveis, menos ops.Controle fino, custo otimizável em alta densidade, requisitos especiais.
💡 ECS × EKS (comparação leve)

ECS é o orquestrador proprietário da AWS, mais simples e integrado. EKS (Elastic Kubernetes Service) é Kubernetes gerenciado — escolha-o quando você quer o ecossistema/portabilidade do K8s. Ambos podem usar Fargate como capacidade.

Questão

Sua equipe quer rodar containers no ECS sem gerenciar nenhum servidor, pagando apenas pelos recursos da task enquanto ela executa. Qual launch type?

  • AFargate — modelo serverless: a AWS gerencia a infra e você paga por vCPU/memória da task.
  • BEC2 — porque é o único que não cobra pelas instâncias provisionadas.
  • CNenhum: ECS sempre exige que você mantenha um cluster de VMs próprio.
  • DEKS, pois é o único modo serverless do ECS.
Fargate é o launch type serverless: sem servidores para gerenciar, cobrança por recurso da task. (B) inverte — o EC2 cobra pelas instâncias provisionadas. (C) é falso (Fargate existe justamente para isso). (D) confunde EKS (Kubernetes gerenciado), que não é um launch type do ECS.

Imagem
Artefato imutável em camadas que serve de molde para containers.
Namespaces
Recurso do kernel que isola a visão do processo (PID, rede, mounts).
cgroups
Limitam e medem os recursos (CPU, memória, I/O) de um container.
Layer (camada)
Unidade read-only da imagem, criada por instrução; compartilhável e cacheável.
Dockerfile
Receita declarativa que descreve como construir a imagem.
CMD
Comando/argumentos default do container; substituível no run.
ENTRYPOINT
Executável fixo do container; args do run são anexados a ele.
Volume
Persistência gerenciada pelo Docker, recomendada para dados em produção.
Bind mount
Monta um caminho do host no container; acoplado ao host, útil em dev.
Registry
Repositório de imagens (Docker Hub, Amazon ECR); push/pull.
Multi-stage build
Dockerfile com vários FROM para separar build do artefato final mínimo.
Pod
Menor unidade deployável do Kubernetes; 1+ containers que compartilham rede/storage.
Task Definition (ECS)
Blueprint da task: imagem, CPU/memória, portas; instanciada como Task.
Fargate
Launch type serverless do ECS/EKS: a AWS gerencia a infraestrutura.

Véspera da provaPegadinhas & checklist final

🎯 Releia antes de entregar a prova
  • Container compartilha o kernel do host (não tem SO próprio); a VM é que carrega SO convidado + hypervisor.
  • Imagem = molde imutável; container = instância em execução (≈ classe/objeto).
  • Namespaces = visão isolada; cgroups = limites de recurso.
  • CMD é substituível pelos args do run; ENTRYPOINT é fixo e recebe os args anexados.
  • EXPOSE só documenta — quem publica porta é o -p host:container.
  • Mudar uma camada invalida as seguintes: copie deps antes do código (cache).
  • Volume (gerenciado, produção) × bind mount (host, dev); camada do container é efêmera.
  • Compose = 1 host (dev); Swarm/Kubernetes = cluster (produção). Compose não é orquestrador de cluster.
  • K8s: Pod (menor unidade) → Deployment (réplicas/rolling) → Service (endpoint estável + LB).
  • Multi-stage separa build do artefato → imagem pequena, sem ferramentas de build.
  • Segurança: não rodar como root (USER), base mínima/distroless, secrets fora da imagem, evitar latest.
  • ECS: Task Definition (molde) → Task (instância) → Service (N tasks + LB). Fargate = serverless; EC2 = você gerencia as instâncias.
