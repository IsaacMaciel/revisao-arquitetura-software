Tópico 05 · DevOps · CI/CD

DevOps — IaC & CI/CD

DevOps não é uma ferramenta nem um cargo — é uma cultura que une desenvolvimento e operações para entregar valor de forma contínua, rápida e segura. Seu motor técnico é o pipeline de CI/CD: automação que leva código do commit à produção, com testes e portas de qualidade no caminho. Infraestrutura vira código (IaC), entregas viram rotina e o medo de fazer deploy desaparece.

🎯 Como DevOps/CI-CD cai na prova

Espere: (1) a distinção exata entre Continuous Integration × Continuous Delivery × Continuous Deployment (a diferença é o deploy em produção: manual vs automático) — quase certo; (2) estratégias de deploy (blue-green × canary × rolling) — qual reduz risco como; (3) a hierarquia do GitHub Actions (workflow → job → step → action; o que é runner/trigger); (4) a pirâmide de testes (base = unitários, topo = e2e) e por que invertê-la é antipadrão; (5) qualidade de código (análise estática, quality gate, SAST × DAST, code coverage); (6) CALMS e os 3 caminhos do DevOps.

Aula 1 · fundamentosO que é DevOps

DevOps é uma cultura e conjunto de práticas que aproxima Development e Operations para reduzir o tempo entre escrever código e ele rodar em produção — sem sacrificar estabilidade. Combate os silos tradicionais ("o dev joga o código por cima do muro e a operação que se vire") com responsabilidade compartilhada, automação e feedback rápido.

O que DevOps NÃO é (pegadinhas comuns)

  • Não é uma ferramenta (Jenkins, GitHub Actions, Docker são habilitadores, não "o DevOps").
  • Não é um cargo isolado ("o time de DevOps") — idealmente é responsabilidade de todos.
  • Não é só automação: é cultura + automação + medição + compartilhamento.
  • Não é sinônimo de CI/CD — CI/CD é a prática técnica central que dá vida à cultura DevOps.
TL;DR
  • DevOps = cultura de colaboração Dev+Ops + automação + feedback contínuo.
  • Objetivo: entregar valor rápido, frequente e confiável, derrubando silos.
  • CI/CD é o pipeline que materializa essa cultura tecnicamente.

Aula 1 · culturaCALMS & os Três Caminhos

O modelo CALMS (popularizado por Jez Humble) descreve os cinco pilares de uma cultura DevOps madura:

LetraPilarSignifica
CCultureColaboração, responsabilidade compartilhada, sem culpa (blameless).
AAutomationAutomatizar build, teste, deploy e provisionamento (IaC).
LLeanFluxo enxuto, lotes pequenos, eliminar desperdício.
MMeasurementMedir tudo (métricas, monitoramento, DORA) para melhorar.
SSharingCompartilhar conhecimento, ferramentas e feedback entre times.
Mnemônico — os 5 pilares
Culture · Automation · Lean · Measurement · Sharing = CALMS
  • "Quem faz DevOps fica CALM(S)" — calmo, porque o deploy deixou de ser um evento de pânico.

O The DevOps Handbook (Kim, Humble, Debois, Willis) organiza tudo em Três Caminhos:

CaminhoPrincípioFoco na prática
1º — FlowFluxo (esquerda → direita)Acelerar a entrega de Dev para Ops: lotes pequenos, automação, limitar WIP, pipeline rápido.
2º — FeedbackFeedback (direita → esquerda)Encurtar e amplificar loops: detectar e corrigir problemas cedo (fail fast, monitoramento, telemetria).
3º — Aprendizado contínuoContinual Learning & ExperimentationCultura de experimentação, repetição, aprender com falhas (post-mortems blameless).
Questão

No The DevOps Handbook, qual a ordem e o foco dos Três Caminhos?

  • A1º Feedback, 2º Flow, 3º Aprendizado — começa medindo antes de produzir.
  • B1º Automação, 2º Cultura, 3º Compartilhamento — é o mesmo que CALMS.
  • C1º Flow (Dev→Ops), 2º Feedback (Ops→Dev), 3º Aprendizado e experimentação contínuos.
  • D1º Deploy, 2º Rollback, 3º Monitoramento — o ciclo de entrega.
A ordem é Flow → Feedback → Aprendizado contínuo. (A) inverte os dois primeiros; (B) confunde com o modelo CALMS (que são pilares, não os caminhos); (D) lista etapas operacionais, não os caminhos do Handbook.

Aula 1 · o conceito mais cobradoCI × Continuous Delivery × Continuous Deployment

Esta é a distinção que mais cai. Os três se encadeiam, e a sigla "CD" é ambígua de propósito — pode significar Delivery ou Deployment:

PráticaO que automatizaAté onde vai automaticamenteDeploy em produção é…
Continuous Integration (CI)Integrar código frequentemente: a cada push, roda build + testes automatizados.Até gerar um artefato validado (build verde).— (não chega a produção)
Continuous Delivery (CD)Tudo do CI + manter o artefato sempre pronto para ir a produção (deploy automatizado até staging).Até o ambiente de staging/pré-produção; o release de produção fica a um clique.Manual — decisão de negócio aperta o botão.
Continuous Deployment (CD)Tudo do Delivery, mas sem o botão: toda mudança que passa nos testes vai a produção sozinha.Até produção, automaticamente.Automático — nenhuma intervenção humana.
⚠ Pegadinha — Delivery NÃO é Deployment

A diferença única e decisiva entre Continuous Delivery e Continuous Deployment é o deploy em produção: no Delivery ele é manual (aprovação/clique humano — o software está pronto para entregar, mas alguém decide quando); no Deployment ele é automático (toda mudança aprovada nos testes sobe sozinha). Frase-âncora: "Todo Deployment é um Delivery, mas nem todo Delivery é um Deployment."

💡 A regra de ouro do CI

CI sem testes automatizados não é CI — é só "rodar build". O coração do CI é integrar cedo e com frequência (idealmente várias vezes ao dia, em main) e ter uma suíte de testes que dá o veredito em minutos. Branches longevas que ficam dias sem integrar são o oposto de CI (merge hell).

Questão

Uma equipe tem um pipeline que builda, testa e implanta automaticamente em staging; a ida para produção exige um clique de aprovação de um gerente. Qual prática melhor descreve isso?

  • AContinuous Deployment — porque o deploy é totalmente automatizado.
  • BContinuous Delivery — o artefato está sempre pronto, mas o deploy em produção é uma decisão manual.
  • CContinuous Integration — porque há build e testes no pipeline.
  • DDevOps puro — não é nenhuma das três.
Clique manual para produção = Continuous Delivery. (A) erra porque Deployment exige produção automática, sem clique; (C) descreve só a primeira etapa — CI para no artefato, não chega a staging/produção; (D) DevOps é a cultura, não uma das três práticas técnicas.
Questão

Qual afirmação sobre Continuous Integration está correta?

  • ACI integra mudanças com frequência em um branch principal, disparando build e testes automatizados a cada integração.
  • BCI implanta automaticamente cada commit em produção.
  • CCI é a prática de manter feature branches longevas e integrá-las só no fim do sprint.
  • DCI dispensa testes, pois apenas verifica se o código compila.
CI = integrar cedo/frequente + build e testes automáticos. (B) descreve Continuous Deployment; (C) é o oposto de CI (gera merge hell); (D) CI sem testes não cumpre seu propósito — o que valida a integração são os testes.

Aula 1 · pipelineO pipeline e seus estágios

O pipeline de CI/CD é a sequência automatizada de estágios que uma mudança atravessa, do commit à produção. Cada estágio só roda se o anterior passou — é o princípio fail fast: falhe cedo, barato e visível.

Commit / Push
→
Build
→
Test
unit · integração · quality gate
→
Artefato
→
Deploy staging
→
Deploy prod
Fail fast: se qualquer estágio falha, o pipeline para e dá feedback imediato — nada avança quebrado. O artefato é gerado uma vez e promovido entre ambientes (build once, deploy many).

Conceitos-chave do pipeline

  • Artefato (build artifact): o pacote imutável gerado pelo build (jar, imagem Docker, bundle). Princípio build once, deploy many — o mesmo artefato é promovido entre ambientes; nunca se rebuilda por ambiente.
  • Ambientes & promotion: dev → staging/QA → produção. "Promover" = mover o artefato já testado para o próximo ambiente, com config externa ao binário.
  • Fail fast: os estágios mais rápidos e baratos (lint, unit) vêm primeiro; os caros (e2e, deploy) por último.
  • Rollback: capacidade de voltar à versão anterior rapidamente se um deploy der problema (reverter o artefato/imagem ou trocar o roteamento).
  • Idempotência & repetibilidade: rodar o pipeline duas vezes com o mesmo input produz o mesmo resultado.

Aula 1 · integraçãoTrunk-based × feature branch

A estratégia de branches afeta diretamente o "Continuous" do CI. Duas abordagens centrais:

CritérioTrunk-Based DevelopmentFeature Branch (longeva)
Onde integraDireto em main (ou branches de vida curtíssima < 1 dia).Em branches que vivem dias/semanas até o merge.
Frequência de mergeVárias vezes ao dia.Esparsa — só quando a feature "termina".
Risco de conflitoBaixo (lotes pequenos).Alto (merge hell, integração tardia).
Aderência ao CIAlta — é o ideal para CI verdadeiro.Baixa — adia a integração, contraria o "Continuous".
Features incompletasProtegidas por feature flags.Escondidas no branch.
⚠ Pegadinha — CI exige integração frequente

"Continuous Integration" e "trabalhar em feature branches por semanas" são incompatíveis. Quanto mais tempo o código fica fora do tronco, maior o conflito de integração. Por isso o trunk-based (com feature flags para esconder o inacabado) é a estratégia mais alinhada ao CI.

Aula 1 · releaseEstratégias de deploy

Como colocar uma nova versão em produção minimizando risco e downtime. As três mais cobradas:

EstratégiaComo funcionaVantagem distintivaRollback
Blue-GreenDois ambientes idênticos: blue (atual) e green (novo). Sobe a nova versão no green e troca todo o tráfego de uma vez.Zero-downtime; rollback instantâneo (volta o tráfego pro blue).Imediato — basta redirecionar para o ambiente antigo.
CanaryLibera a nova versão para uma pequena fração de usuários (ex.: 5%), monitora métricas e aumenta gradualmente.Limita o "raio de impacto" de uma falha; valida com tráfego real.Rápido — corta o tráfego dos poucos usuários afetados.
RollingSubstitui as instâncias aos poucos, em lotes (ex.: 2 de 10 por vez) até trocar todas. Não há ambiente duplicado.Não precisa do dobro de infraestrutura.Mais lento — precisa reverter instância por instância; coexistem duas versões durante a transição.
💡 A diferença que a prova explora

Blue-Green troca 100% do tráfego de uma vez (precisa de dois ambientes completos). Canary expõe a nova versão a uma porcentagem crescente de usuários (foco em reduzir risco com tráfego real). Rolling substitui instâncias em lotes sem duplicar o ambiente. Não confunda "gradual por % de usuários" (canary) com "gradual por instâncias" (rolling).

Questão

Você quer liberar uma nova versão para apenas 5% dos usuários, observar erros e latência por algumas horas e só então expandir para 100%. Qual estratégia de deploy é essa?

  • ABlue-Green — sobe a nova versão em paralelo e troca o tráfego de uma vez.
  • BRolling — substitui as instâncias em lotes.
  • CCanary — libera para uma fração de usuários e expande gradualmente conforme as métricas.
  • DBig-bang — implanta tudo para todos simultaneamente.
Liberar para uma fração de usuários e crescer monitorando = Canary. (A) Blue-Green troca 100% de uma vez (não há fração de usuários); (B) Rolling é gradual por instâncias, não por porcentagem de usuários; (D) big-bang é o oposto — máximo risco, sem gradualidade.

Aula 1 · infraIaC como prática DevOps

Infrastructure as Code (IaC) é tratar a infraestrutura (servidores, redes, bancos, clusters) como código versionado em vez de cliques manuais. É o pilar "Automation" do CALMS aplicado a Ops. (Terraform e Docker têm páginas próprias — Tópicos 03 e 04; aqui IaC entra como peça do pipeline DevOps.)

Por que IaC importa no pipeline

  • Versionada: a infra mora no Git, com histórico, review e rollback como qualquer código.
  • Idempotência: aplicar a mesma definição N vezes leva ao mesmo estado — não cria recursos duplicados. Distingue a abordagem declarativa (descrevo o estado desejado; ex.: Terraform) da imperativa (descrevo os passos).
  • Reprodutibilidade: elimina o "funciona na minha máquina"/snowflake servers — ambientes idênticos sob demanda.
  • Provisionamento no pipeline: o CI/CD pode criar/atualizar a infra antes de implantar o app (containers como unidade de deploy).
⚠ Idempotência vs "rodar de novo"

Idempotente não quer dizer "não faz nada na segunda vez" — quer dizer que o estado final é o mesmo independentemente de quantas vezes você aplica. Um script imperativo que faz criar_servidor sem checar duplica recursos; um IaC declarativo converge para o estado desejado.

Aula 2 · GitHubGitHub Actions — a hierarquia

O GitHub Actions é a plataforma de CI/CD nativa do GitHub. Saber a hierarquia exata (e o que cada peça é) cai direto:

ConceitoÉ…Contém / relação
WorkflowProcesso automatizado definido num arquivo YAML em .github/workflows/.Contém um ou mais jobs; é disparado por um trigger.
Trigger (on)O evento que dispara o workflow (push, pull_request, schedule, workflow_dispatch…).Pertence ao workflow.
JobConjunto de steps que roda numa mesma máquina (runner). Jobs rodam em paralelo por padrão (use needs para sequenciar).Contém steps; executa num runner.
StepUma tarefa única dentro de um job: roda um comando (run) ou usa uma action (uses).Steps de um mesmo job rodam em sequência e compartilham o filesystem.
ActionUnidade reutilizável empacotada (ex.: actions/checkout) chamada por um step via uses.Invocada por um step.
RunnerA máquina (hosted pelo GitHub ou self-hosted) que executa um job.Executa um job por vez.
 
yaml .github/workflows/ci.yml
name: CI
on:                          # trigger
  push:
    branches: [main]
  pull_request:

jobs:
  test:                       # job
    runs-on: ubuntu-latest   # runner
    strategy:
      matrix:                 # matrix build: roda em várias versões
        node: [16, 18, 20]
    steps:                    # steps rodam em sequência
      - uses: actions/checkout@v4          # action reutilizável
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
      - run: npm ci                       # step de comando
      - run: npm test
        env:
          API_KEY: ${{ secrets.API_KEY }}      # secret, nunca em texto puro
Questão

No GitHub Actions, qual sequência descreve corretamente a hierarquia de cima para baixo?

  • AStep → Job → Workflow → Action (steps agrupam jobs).
  • BJob → Workflow → Step → Runner (jobs contêm workflows).
  • CAction → Step → Workflow → Job (actions contêm tudo).
  • DWorkflow → Job → Step → (cada step pode usar uma Action), rodando num Runner.
A hierarquia é Workflow ⊃ Job ⊃ Step, e cada step pode invocar uma Action; o job roda num Runner. As demais invertem a relação de continência (um workflow contém jobs, não o contrário; um job contém steps, não o contrário).

Aula 2 · governançaBranch protection, PR reviews & required checks

O GitHub transforma o pipeline em porta de qualidade do merge com regras de proteção de branch:

Mecanismos de proteção

  • Branch protection rules: proíbem push direto em main; tudo entra via Pull Request.
  • Required reviews: exige aprovação de N revisores (e/ou de code owners) antes do merge.
  • Required status checks: o merge só libera se os checks do CI (build, testes, lint, quality gate) ficarem verdes — o pipeline vira porta de entrada.
  • Up-to-date branch: exige que a branch esteja atualizada com main antes de mergear.
  • Linear history / no force-push: protege o histórico.
💡 O CI como guardião do merge

Com required status checks, código que quebra os testes não consegue ser mergeado em main. É assim que "testes como porta de merge" (próxima seção) se materializa no GitHub — a configuração de proteção liga o resultado do pipeline ao botão de merge.

Aula 2 · práticasConventional Commits, secrets & reuso

Boas práticas no GitHub

  • Conventional Commits: mensagens padronizadas (feat:, fix:, chore:, docs:…) que permitem changelog e versionamento semântico automáticos.
  • Secrets: credenciais ficam em GitHub Secrets (criptografados), nunca em texto puro no YAML nem no repositório. Acessadas via ${{ secrets.NOME }}; não são expostas em logs nem para PRs de forks.
  • Matrix builds: rodam o mesmo job em combinações (várias versões de SO/runtime) em paralelo — amplia cobertura sem duplicar YAML.
  • Reusable workflows: workflows chamados por outros (workflow_call), evitando copiar/colar pipeline entre repositórios (DRY de pipeline).
Questão

Sua aplicação precisa de uma chave de API para rodar os testes no CI. Qual é a prática correta no GitHub Actions?

  • AColocar a chave em texto puro no arquivo ci.yml versionado.
  • BArmazenar em GitHub Secrets e referenciá-la via ${{ secrets.API_KEY }} no workflow.
  • CHardcodar a chave dentro do código-fonte da aplicação.
  • DImprimir a chave nos logs do job para facilitar o debug.
Segredos vão em GitHub Secrets (criptografados) e são injetados por referência. (A) e (C) expõem a credencial no repositório (vazamento); (D) imprimir em log é justamente o que o mascaramento de secrets tenta evitar — nunca logar segredos.

Aula 3 · testes no CIA pirâmide de testes

A pirâmide de testes (Mike Cohn) orienta a proporção de cada tipo de teste no pipeline: muitos rápidos e baratos na base, poucos lentos e caros no topo.

topo E2E / UI — poucos, lentos, caros, frágeis. Validam o sistema inteiro.
meio Integração — quantidade média. Testam módulos/serviços conversando (DB, API).
base Unitários — muitos, rápidos, baratos, estáveis. Testam unidades isoladas.
Base larga (unitários) → topo estreito (e2e). Inverter — muitos e2e e poucos unitários — é o antipadrão "cone de sorvete" (ice-cream cone): suíte lenta e instável.
NívelEscopoVelocidade / custoQuantidade
UnitáriosUma unidade isolada (função/classe), sem dependências externas.Muito rápidos / baratos.Muitos (base).
IntegraçãoVárias unidades juntas + recursos reais (banco, fila, API).Médios.Quantidade média.
E2E / UIO sistema inteiro pela ótica do usuário (browser, fluxo completo).Lentos / caros / frágeis.Poucos (topo).
⚠ Pegadinha — o cone de sorvete

O antipadrão é a pirâmide invertida ("ice-cream cone"): poucos testes unitários e muitos e2e. Resultado: feedback lento, builds instáveis (flaky) e CI que ninguém confia. A base larga de unitários é o que dá ao pipeline um veredito rápido e confiável.

Questão

Segundo a pirâmide de testes, qual configuração de suíte é a recomendada?

  • AMuitos testes unitários (base), quantidade média de integração, poucos e2e (topo).
  • BMuitos e2e na base, poucos unitários no topo — para cobrir o sistema completo.
  • CApenas testes e2e, pois cobrem todos os níveis de uma vez.
  • DQuantidades iguais de cada tipo, para equilíbrio.
A pirâmide pede base larga de unitários e topo estreito de e2e. (B) é o antipadrão "cone de sorvete" (invertido); (C) só e2e = suíte lenta, frágil e cara; (D) ignora a relação custo/velocidade entre os níveis.

Aula 3 · porta de qualidadeQuality gate & testes como porta de merge

Rodar testes no pipeline só tem valor se um resultado ruim bloqueia o avanço. O quality gate é o conjunto de critérios objetivos (testes passando, cobertura mínima, zero vulnerabilidades críticas, sem code smells acima do limite) que a mudança precisa cumprir para prosseguir/mergear.

Como os testes viram porta de merge

  • O job de testes roda a cada PR/push (CI).
  • O resultado vira um required status check no branch protection.
  • Falhou → o botão de merge fica bloqueado; passou → libera.
  • O quality gate pode somar regras de cobertura e de análise estática (SonarQube), não só "passou/falhou".
💡 Conexão com Clean Architecture (Tópico 02)

Os testes do pipeline seguem a regra F.I.R.S.T. (Fast, Independent, Repeatable, Self-validating, Timely) — especialmente Fast e Self-validating, que tornam o CI rápido e automático. O TDD (Red→Green→Refactor) produz justamente a base de unitários da pirâmide. Veja a página 02 · Clean Architecture.

Aula 4 · qualidadeAnálise estática, linters & SonarQube

Além dos testes (que executam o código), o pipeline avalia a qualidade do código-fonte sem rodá-lo — a análise estática:

Ferramentas e conceitos

  • Linter: verifica estilo, padrões e erros prováveis (ESLint, Flake8). Roda como step do CI.
  • Análise estática (SonarQube): detecta code smells, bugs, duplicação, complexidade e calcula o débito técnico.
  • Code coverage: % de linhas/ramos exercitados pelos testes. É um indicador, não garantia de qualidade — 100% de cobertura com asserções fracas não significa código correto.
  • Code smells: sinais de design ruim (métodos longos, duplicação, classes grandes) — não são bugs, mas aumentam o custo de manutenção.
  • Débito técnico: o "custo" acumulado de atalhos no código; o quality gate impede que ele cresça sem controle.
⚠ Cobertura alta ≠ código bom

Code coverage mede o que foi executado pelos testes, não se foi verificado corretamente. Dá para ter 95% de cobertura sem nenhuma asserção significativa. Use cobertura como piso (quality gate), não como prova de qualidade.

Aula 4 · segurançaSecurity scanning & dependências

Segurança "shift-left" entra no pipeline (DevSecOps). Distinção que cai: SAST × DAST.

TécnicaO que analisaQuandoAnalogia
SAST (Static App Security Testing)O código-fonte parado (caixa-branca) — procura vulnerabilidades no código.Cedo, no build/CI (não precisa rodar a app).Revisar a planta da casa.
DAST (Dynamic App Security Testing)A aplicação em execução (caixa-preta) — ataca a app rodando.Mais tarde, contra um ambiente de teste em execução.Testar as fechaduras da casa pronta.

Higiene de dependências

  • Dependabot: monitora dependências e abre PRs automáticos para versões vulneráveis/desatualizadas.
  • SCA (Software Composition Analysis): varre dependências de terceiros em busca de CVEs conhecidas.
  • Secret scanning: detecta credenciais acidentalmente commitadas.
  • Tudo pode virar quality gate: vulnerabilidade crítica → pipeline barra o merge.
Questão

Qual é a diferença entre SAST e DAST?

  • ASAST testa a aplicação em execução; DAST analisa o código-fonte parado.
  • BAmbos exigem a aplicação rodando; a diferença é só a ferramenta.
  • CSAST analisa o código-fonte estaticamente (caixa-branca, sem executar); DAST testa a aplicação em execução (caixa-preta).
  • DSAST é análise de cobertura de testes; DAST é análise de dependências.
SAST = estático/código parado (caixa-branca); DAST = dinâmico/app rodando (caixa-preta). (A) inverte os dois; (B) erra porque SAST justamente não roda a aplicação; (D) confunde com coverage e SCA — nenhum dos dois é SAST/DAST.

Blue-Green: dois ambientes, troca 100% do tráfego de uma vez. Canary: libera para uma % crescente de usuários.
O que é deploy Rolling?
clique
Substitui as instâncias em lotes até trocar todas, sem ambiente duplicado. Duas versões coexistem durante a transição.
Hierarquia do GitHub Actions?
clique
Workflow ⊃ Job ⊃ Step; cada step pode usar uma Action; o job roda num Runner; disparado por um trigger (on).
Jobs e steps: paralelos ou sequenciais?
clique
Jobs: paralelos por padrão (use needs para sequenciar). Steps dentro de um job: sempre em sequência.
Como fica a pirâmide de testes?
clique
Base larga de unitários, meio de integração, topo estreito de e2e. Inverter = antipadrão "cone de sorvete".
SAST × DAST?
clique
SAST: código-fonte parado (caixa-branca, sem rodar). DAST: aplicação em execução (caixa-preta).
O que é "build once, deploy many"?
clique
Gerar o artefato uma única vez e promovê-lo entre ambientes (config externa), nunca rebuildar por ambiente.
Idempotência em IaC?
clique
Aplicar a mesma definição N vezes leva ao mesmo estado final — sem duplicar recursos. Típico da abordagem declarativa.
Code coverage prova qualidade?
clique
Não. Mede o que os testes executaram, não se verificaram corretamente. É um piso de quality gate, não garantia.

Véspera da provaPegadinhas & checklist final

🎯 Releia antes de entregar a prova
  • Delivery × Deployment: a única diferença é o deploy em produção — Delivery = manual; Deployment = automático.
  • "Todo Deployment é um Delivery, mas nem todo Delivery é um Deployment."
  • CI para no artefato validado; não chega a staging nem a produção sozinho.
  • DevOps é cultura, não ferramenta nem cargo; CALMS = Culture, Automation, Lean, Measurement, Sharing.
  • Os Três Caminhos: 1º Flow, 2º Feedback, 3º Aprendizado contínuo (não confundir com CALMS).
  • Blue-Green = troca 100% de uma vez (2 ambientes); Canary = % crescente de usuários; Rolling = instâncias em lotes.
  • GitHub Actions: Workflow ⊃ Job ⊃ Step; step usa Action; job roda em Runner; disparado por trigger (on).
  • Jobs são paralelos por padrão; steps de um job são sequenciais.
  • Pirâmide de testes: base de unitários, topo de e2e. Inverter = "cone de sorvete" (antipadrão).
  • Quality gate + required status checks = testes viram porta de merge.
  • SAST = estático/caixa-branca (código parado); DAST = dinâmico/caixa-preta (app rodando).
  • Code coverage não prova qualidade — só mede o que foi executado.
  • Trunk-based é o que mais combina com CI; feature branches longevas geram merge hell.
  • Secrets em GitHub Secrets, nunca em texto puro no YAML ou no código.
